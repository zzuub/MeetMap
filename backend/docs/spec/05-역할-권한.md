## 5. 역할과 권한

**핵심 원칙: 소셜 로그인은 "신원"만 준다. "권한"은 서버가 부여한다** ([dev-plan 3.1][plan]). 역할은 가입한 입구가 정하고(D-01), 서버는 매 요청 권한을 다시 판정한다.

### 5.1 역할과 상태

| 역할 | 누구 | 만들어지는 길 | 근거 |
| --- | --- | --- | --- |
| `USER` | 소개팅을 찾는 사람 | 첫 소셜 로그인에 계정이 생기고 곧바로 `ACTIVE` | [dev-plan 3.3][plan] · D-01 |
| `PROVIDER` | 주최사 담당자 | ① 가입 신청 → `PENDING` → 운영자 승인 ② 운영자 초대 수락 → 곧바로 `ACTIVE` | D-01 |
| `ADMIN` | MeetMap 운영자 | 초대 또는 시드만. 가입 화면이 없다 — 누가 발급하나는 O-19 | [dev-plan 3.4][plan] |

```
USER      첫 소셜 로그인 ─────────────▶ ACTIVE ⇄ SUSPENDED
PROVIDER  가입 신청 ──▶ PENDING ─승인─▶ ACTIVE ⇄ SUSPENDED
                           └──반려──▶ REJECTED        재신청은 O-16
          초대 수락 ─────────────────▶ ACTIVE
ADMIN     초대 수락 · 시드 ───────────▶ ACTIVE ⇄ SUSPENDED
계정      정상 ──탈퇴──▶ 탈퇴                         멤버십과 별개 (O-13)
```

- `ACTIVE ⇄ SUSPENDED` 는 운영자가 바꾼다 — 회원 관리의 `정상`·`정지` ([목업 AdminManage][mk-adminm]).
- 탈퇴는 본인 또는 운영자가 한다. USER 의 탈퇴 화면은 아직 없다 ([FE 16장][fe14]).
- **상태 변경은 다음 요청부터 막힌다** — 목업은 "상태 변경은 즉시 적용되며 활동 로그에 기록됩니다"라고 적었다. 토큰이 살아 있어도 막는 방식은 O-32.
- USER 의 `isNewUser` 는 상태가 아니라 파생값이다 — 필수 약관 동의 전의 USER (4.11).

### 5.2 인증 — 역할마다 입구가 다르다

| 역할 | 입구 | 로그인 수단 | 근거 |
| --- | --- | --- | --- |
| `USER` | 사용자 앱 온보딩 | 카카오 · 네이버 · 구글 | [FE 3.1][fe03] |
| `PROVIDER` | 파트너 로그인 · 가입 신청 | 이메일·비밀번호 (+ 연동한 소셜) | D-01 · [목업 Provider][mk-prov] |
| `ADMIN` | 운영 도구 | 이메일·비밀번호 + 2FA | [dev-plan 3.4][plan] · D-09 |

1. **역할은 입구가 정한다.** 서버는 가입 요청이 어느 경로로 왔는지로 역할을 정한다. 요청 본문의 역할 값은 믿지 않는다 — `role: "ADMIN"` 한 줄이 권한 상승이 된다 ([dev-plan 3.3][plan] · [decisions 4.5][dec]).
2. **소셜 로그인의 목적은 서버가 서명한 OAuth `state` 로만 전달한다.** 목적은 둘뿐이다 — USER 로그인, 그리고 로그인한 계정에 소셜 연동. 주최사 가입은 소셜을 쓰지 않으므로 `PROVIDER` 가입 의도는 `state` 에 없다(FE `AuthIntent` 갱신 → O-37). `ADMIN` 은 처음부터 없다 ([decisions 4.5][dec]).
3. **입구와 계정의 역할이 다르면 로그인하지 않는다** (제안). USER 입구로 들어온 소셜 신원이 주최사 계정에 연동돼 있으면 거절한다. USER 계정을 새로 만들지도 않는다 — 소셜 신원 하나는 계정 하나에만 묶인다 (D-01).
4. **토큰의 역할·상태는 믿지 않는다.** 토큰은 `sub`·`role`·`status`·`isNewUser`·`nickname` 을 싣는다 — 프론트가 화면을 가르는 데 쓴다([FE `session.ts`][sess]). 서버는 토큰 값만으로 쓰기를 허락하지 않는다 (O-32).
5. **표면을 섞지 않는다.** 사용자·주최사·운영 API 의 토큰은 서로의 표면에서 통하지 않는다 (3.6).

### 5.3 게스트 허용 범위

[dev-plan 3.5][plan] 기본안 — **탐색은 열고 개인화는 로그인** — 으로 쓴다. FE 16장에서 아직 확정되지 않았다 (O-21).

| 게스트가 | 되나 | 서버에서 |
| --- | --- | --- |
| 홈 · 탐색 · 지도 · 상세 · 검색 · 인기 검색어 · 주최사 페이지 · 주최사 후기 | ✅ | 인증 주체 축(`eligibleOnly`·`maxPrice`·가격 정렬)을 해석하지 않는다 — 게스트는 전건을 본다 ([FE 6.4][fe05]) |
| 비교 · id 묶음 조회 | ✅ | 공개 회차 데이터라 막지 않는다 (제안). 화면(`/compare`·`/likes`)을 로그인 뒤에 두는 것은 프론트의 판단이다 ([FE `access.ts`][access]) |
| 신청 URL 이동 기록 | ✅ | 계정 없이 남긴다 — 게스트가 외부 이동까지 가는 것이 Phase 1 완료 조건이다 ([dev-plan Phase 1 DoD][plan]) |
| 주최사 가입 신청 | ✅ | 신청이 곧 계정 생성이다 (D-01) |
| 역지오코딩 | ❌ | 로그인한 USER 만 (제안). 위치 권한 화면은 가입 퍼널 안에 있고, 외부 지오코딩 비용이 드는 조회를 열어 두면 남용된다 |
| 찜 · 알림 · 프로필 · 약관 · 후기 작성 · 신고 | ❌ | `401` |

### 5.5 소유권 규칙

1. **범위는 토큰에서 꺼낸다.** `/users/me/**` 의 "나"는 경로가 아니라 인증 주체다. 요청 본문·경로에 든 계정 id·주최사 id 로 범위를 넓히지 않는다.
2. **주최사 범위는 담당 연결의 주최사다** (4.12). 주최사 표면의 모든 회차·후기·통계 요청은 그 주최사 소속인지 서버가 확인한다. 남의 주최사 리소스에는 `404` 로 답한다 — 있는지조차 알리지 않는다 (제안).
3. **귀속은 서버가 붙인다.** 후기의 `providerId` 는 회차에서 가져온다([FE 13장][fe11]). 개정본의 주최사도 담당 연결에서 가져온다.
4. **자격도 서버가 계산한다.** USER 신고는 "그 후기의 회차에 참여 인증했나", PROVIDER 신고·답글은 "그 후기의 회차가 자기 주최사 것인가"를 서버가 판정한다 (D-05).

### 5.6 매 요청 재검증

- **프론트 라우트 가드는 UX 가드이지 보안 경계가 아니다** ([decisions 4.12][dec] · [FE `access.ts`][access] 주석). 가드를 통과했다는 사실에 기대는 서버 코드를 쓰지 않는다.
- **게스트 게이트도 서버가 스스로 한다.** 프론트는 게스트에게 가격 정렬 요청을 만들지 않지만([decisions 4.30][dec]) 서버는 그 요청이 와도 스스로 판단한다 — 응답 규칙은 O-08.
- **판정 순서** (제안): 토큰 유효 → 계정 상태(탈퇴 아님) → 멤버십(역할·상태) → 표면 일치 → 소유권. 실패는 `401` / `403` / `404` 로 답하고, 오류 코드 체계는 10장에서 정한다.
