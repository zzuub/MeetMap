### 6.13 계정

#### P-01 가입 신청

| 칸 | 내용 |
| --- | --- |
| 입력 | 로그인 이메일 · 비밀번호, 상호 · 사업자등록번호 · 담당자명 · 연락처 · 운영 지역 ([목업 AdminManage][mk-adminm] 신청 카드) |
| 검증 | 이메일 중복이면 `409`. 비밀번호 규칙 O-35. 사업자등록번호는 형식만 본다 — 진위 확인 O-52, 사업자가 없는 개인 주최자 O-17. 주최사용 약관·개인정보 동의 항목은 O-49 |
| 처리 | 한 트랜잭션에 계정 + 비밀번호 + PROVIDER 멤버십(`PENDING`) + 가입 신청 (3.4). 이메일 인증을 거칠지는 O-65 |
| 결과 | `PENDING` 세션 — 가입 신청 상태(R-35)만 볼 수 있다 ([dev-plan 3.5][plan] `/provider/pending`) |
| 근거 | D-01 · [dev-plan 3.3][plan] (사업자 정보 폼 — `정산 계좌`는 받지 않는다, D-03) |

#### P-02 초대 수락 · 최초 비밀번호 설정

| 칸 | 내용 |
| --- | --- |
| 입력 | 초대 토큰, 메일로 받은 임시 비밀번호, 새 비밀번호 ([목업 Provider][mk-prov] 최초 비밀번호 설정) |
| 검증 | 토큰이 없거나 만료·사용됨이면 `409`. 새 비밀번호는 영문 대소문자·숫자·특수문자 중 3종 이상, 8~20자, 이전 비밀번호 재사용 불가 — 목업 문구. 세부는 O-35, 임시 비밀번호 방식 자체는 O-34 |
| 처리 | 한 트랜잭션에 계정(초대의 이메일) + 비밀번호 + PROVIDER 멤버십(`ACTIVE`) + **초대가 가리키는 주최사와 담당 연결** + 초대 소진 — 소진과 활성화가 갈리면 같은 초대로 두 번 들어온다 (3.4) |
| 결과 | `ACTIVE` 세션. 운영자가 대신 만들어 둔 주최사 프로필을 이 계정이 넘겨받는다 (D-01) |

#### P-03 로그인 · 비밀번호 찾기

| 칸 | 내용 |
| --- | --- |
| 로그인 | 이메일·비밀번호. `로그인 상태 유지`를 켜면 세션을 길게 준다 — 기간 O-71. 실패 잠금 O-35. `PENDING` 은 신청 상태만, `REJECTED` 는 O-28, 정지·탈퇴는 거절 (5.4) |
| 소셜 로그인 | 연동해 둔 소셜로도 들어온다. **파트너 입구의 `state` 목적으로만** 받고, 신원이 PROVIDER 계정에 묶여 있어야 한다. **계정을 만들지 않는다** — USER 입구로 들어온 같은 신원은 거절된다 (W-01 · 5.2) |
| 비밀번호 찾기 | 목업엔 링크만 있다. 1회용 재설정 링크를 계정 이메일로 보낸다 (제안). 가입 여부를 드러내지 않게 **있든 없든 같은 응답**을 준다 (제안) |

#### P-07 계정 정보 · 비밀번호 · 알림 수신

| 칸 | 내용 |
| --- | --- |
| 계정 정보 | 담당자명 · 연락처를 바꾼다. **계정 이메일은 바꿀 수 없다** — 운영자만 바꾼다(A-08) ([목업 ProviderManage][mk-provm]) |
| 비밀번호 | 현재 비밀번호를 확인하고 바꾼다. 규칙은 P-02 와 같다. 바꾸면 다른 세션을 끊는다 (제안) |
| 알림 수신 | 검수 결과 · 주간 성과 리포트 · 계약 만료 사전 안내 셋. 목업의 `지원서 접수 알림`은 받지 않는다 (D-02) |

#### P-08 소셜 연동 · 해제

| 칸 | 내용 |
| --- | --- |
| 연동 | `state` 목적 `연동` + 계정 id 로 소셜 인증을 거쳐 로그인 수단을 더한다. 그 신원이 **다른 계정에 이미 묶여 있으면 `409`** — 소셜 신원 하나는 계정 하나다 (D-01) |
| 해제 | 소셜 로그인 수단만 뗀다. 비밀번호는 뗄 수 없다 (4.11) |

### 6.14 소개팅

#### P-04 등록 요청 · P-05 수정 요청

| 칸 | 내용 |
| --- | --- |
| 입력 | 목업 등록 4단계 — **기본 정보**(제목, 대표 이미지, 소개) · **일정·가격**(일자, 시작 시각, 남·여 참가비) · **참가 조건**(출생연도 범위, 남·여 정원, 장소 주소·상세 주소) · **신청 URL** ([목업 Provider][mk-prov]) |
| 받지 않는 것 | 시간대(시작 시각에서 파생), 성별 조건(`genderPolicy` 폐기) — D-06. 요청에 와도 쓰지 않는다 |
| 폼에 없는 것 | 분위기·직업군(O-03), 장소명(O-25), 짧은 제목(O-51), 참석자 리스트 링크(O-73) |
| 검증 | 제목 40자 이하 · **대표 이미지와 남·여 참가비 필수**(D-06) · 출생연도 From ≤ To · 정원 0 이상, 둘 다 0 은 거절 · 신청 URL 은 http(s) · 개최 시각이 지금 이후 (제안). 주최사의 `정보 등록` 동의가 유효하지 않으면 `409`, `이미지 사용` 동의가 없는데 이미지가 오면 `409` (4.4) |
| 처리 | 1. 주소를 좌표로 바꾼다 — **트랜잭션 전에**(3.4). 구는 좌표로 판정하고(제안) 정밀도는 `EXACT`, 지역(`area`) 산정은 O-02<br>2. P-04: 신규 개정본(`검수 대기`)을 만든다. 공개본은 없다<br>3. P-05: 공개된 회차의 수정 개정본을 만든다. **공개본은 승인 전까지 그대로 노출된다**. 이미 검수 대기 개정본이 있으면 새 것으로 바꿔 끼운다 (4.6) |
| 결과 | 개정본과 그 상태. 검수 결과는 메일로 안내한다 (8장) |
| 예외 | P-05 의 대상이 지난 회차면 `409` (제안) |
| 근거 | [목업 Provider·ProviderManage][mk-provm] "승인 완료된 소개팅을 수정하면 재검수 대상이 됩니다. 검수 완료 전까지 기존 내용이 노출됩니다" |

#### P-06 모집 상태 · 정원

| 칸 | 내용 |
| --- | --- |
| 입력 | 모집 상태(`신청 가능`·`마감`), 남·여 정원 — 목업은 두 값을 한 버튼으로 저장한다 |
| 처리 | 공개본의 두 값을 **재검수 없이 즉시** 바꾼다. 목업의 저장 문구가 근거다 — 정원 화면은 "모집 상태와 정원 … 이 반영되었습니다", 수정 화면은 "재검수 후 반영됩니다"로 갈린다 → **O-04 해소**. 규모(`scale`)는 정원에서 다시 파생된다 |
| 예외 | 지난 회차를 `신청 가능`으로 되돌리거나 정원을 바꾸면 `409` — 개최 시각이 지나면 자동 마감이다 (D-07). 정원이 둘 다 0 이면 `400` |
| 근거 | [목업 ProviderManage][mk-provm] 지원현황·정원 — 지원·선발 수치는 받지도 보여주지도 않는다 (D-02) |

### 6.15 후기

#### P-09 답글 · P-10 후기 신고

| 칸 | 내용 |
| --- | --- |
| 자격 | 그 후기가 **자기 주최사 회차**의 후기다 (D-05 · 5.5) |
| P-09 처리 | 후기당 하나로 두고 `PUT` 으로 만들거나 고친다 (제안 — 개수·수정·삭제 규칙은 O-11). 사용자 화면에 답글을 그리는 것은 FE 사양 추가가 필요하다 (O-41) |
| P-10 처리 | 사유 넷 중 하나 + 내용. 신고 + 신고 건을 한 트랜잭션에 (W-10 과 같다). **주최사의 신고만으로는 후기를 숨기지 않는다** — 나쁜 후기를 신고로 가리는 길이 열린다. 숨김·삭제는 운영자가 판단한다 (D-05) |
| 예외 | 같은 후기를 두 번 신고하면 `409` |
