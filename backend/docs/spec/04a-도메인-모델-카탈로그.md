## 4. 도메인 모델

### 4.1 프론트 타입 ≠ 테이블

[FE 12장][fe10] 의 타입은 **화면이 받는 모양**이다. 서버는 응답 필드마다 어디서 오는 값인지를 먼저 정한다.

| 종류 | 뜻 | 예 | 저장 |
| --- | --- | --- | --- |
| 저장값 | 입력으로 받아 저장한다 | `title` `birthYearFrom` `malePrice` | 한다 |
| 파생값 | 저장값에서 계산한다 | `scale` `timeSlot` `dateLabel` 응답용 `status` | **하지 않는다** (조회 성능용 사본은 제안 수준) |
| 집계값 | 여러 행에서 모은다 | 주최사 `rating` `reviewCount` `ratingScore`, `popularity` | 집계 테이블 |
| 요청값 | 누가·어디서 묻느냐로 바뀐다 | `isLiked` `distanceKm` | **하지 않는다** |

- **타입 하나가 테이블 여럿이다.** `EventSummary` = 회차 + 주최사 이름 + 찜 여부, 정렬에는 평점 집계가 더 붙는다. 조립은 조회 전용 쿼리가 한다 (3.3 규칙 2).
- **표시 문자열은 서버가 만든다** — `dateLabel`(`9/5(토)`)·`timeLabel`(`19:30`)은 KST 로 만든 파생값이다 ([FE 12장][fe10]).
- **시각은 UTC 로 저장하고 (제안) KST 로 판정한다.** KST 판정은 프론트 규칙이다 — 이번 주·오늘·시간대를 실행 환경의 타임존과 무관하게 KST 로 센다 ([`derive.ts`][derive]). 저장 형식은 그 규칙이 정하지 않는다.
- **id 는 문자열로 내려간다**([FE 12장][fe10]). 내부 키는 BIGINT 순번을 문자열로 직렬화한다 (제안).

### 4.2 엔티티 한눈에

```
주최사 ─┬─ 동의·계약 기록 (이력)
        ├─ 반복 규칙 ──(생성)──▶ 회차
        ├─ 회차 (공개본) ─┬─ 개정본 ── 검수 결정
        │                ├─ 이미지 · 분위기 · 직업군
        │                └─ 참여 인증 ── 후기 ─┬─ 태그
        │                                     ├─ 답글
        │                                     └─ 신고 → 04b
        └─ 평점 집계 (후기에서 파생)
```

| 엔티티 | 모듈 | 관계 |
| --- | --- | --- |
| 주최사 | `provider` | 계정과는 담당 연결로 이어진다 (04b) |
| 동의·계약 기록 | `provider` | 주최사 1 : N (이력) |
| 회차 (공개본) | `event` | 주최사 N : 1 |
| 개정본 · 검수 결정 | `event` | 회차 1 : N. 신규 등록은 회차 없이 시작한다 |
| 반복 규칙 | `event` | 주최사 N : 1, 회차 1 : N |
| 회차 이미지 · 분위기 · 직업군 | `event` | 회차 1 : N |
| 참여 인증 | `review` | 계정 × 회차 |
| 후기 · 후기 태그 · 답글 | `review` | 회차 N : 1, 주최사 N : 1 |
| 평점 집계 | `review` | 주최사 1 : 1 |

### 4.3 주최사

| 필드 | 종류 | 제약 · 규칙 | 근거 |
| --- | --- | --- | --- |
| 이름 `name` | 저장 | 필수. 검색 대상이다 | [FE 11.1][fe09] |
| 한 줄 소개 `tagline` | 저장 | 필수(FE 타입 non-null). **주최사에게 받아 적는다** — 인스타 bio 를 옮기지 않는다 | [dev-plan 4장 #15][plan] |
| 소개 본문 `description` | 저장 | `null` 허용 — 컨택 직후라 못 받은 주최사 | [FE 12장][fe10] |
| 인스타그램 `instagramUrl` | 저장 | 필수 | [FE 12장][fe10] |
| 주최사 등록일 `registeredAt` | 저장 | 운영자가 대신 등록한 날. 셀프 가입한 주최사는 **가입 승인일**로 둔다 (제안 — FE 는 단계 ①만 정의했다) | 앞 문장만 [FE 12장][fe10] |
| 사업자 정보 | 저장 | 상호·사업자등록번호·대표자명·사업장 주소. **선택** — 단계 ①의 주최사에는 없다. 가입 신청에서는 필수(O-17) | [목업 Admin][mk-admin] |
| 담당자 정보 | 저장 | 담당자명·연락처. 주최사 계정이 스스로 고친다 | [목업 ProviderManage][mk-provm] |
| 공개 여부 | 저장 | 공개 / 비공개(운영자 조치). 비공개면 주최사 페이지와 그 회차가 어디에도 나가지 않는다 (제안) | — |
| `rating` `reviewCount` `ratingScore` | 집계 | 4.8 평점 집계 | [FE 7.4][fe06] |

- **주최사는 계정 없이 존재한다.** 단계 ①은 운영자가 대신 만든 주최사뿐이다.
- **같은 주최사를 둘로 만들지 않는다.** 가입 승인·초대 수락 때 기존 프로필과 연결한다 — 둘로 갈리면 후기와 평점이 쪼개진다 (D-01).

### 4.4 동의 · 계약 기록

한 기록에 동의와 계약을 함께 담는다 (D-03 · D-04).

| 부분 | 항목 | 효과 | 근거 |
| --- | --- | --- | --- |
| **동의** | 정보 등록 | 없으면 그 주최사 회차를 공개하지 않는다 | [FE 7.2][fe06] · [decisions 4.18][dec] |
| | 이미지 사용 | 없으면 이미지를 저장·노출하지 않는다 → `thumbnailUrl` 이 `null` (정상 경로) | 상동 |
| | 참석자 리스트 표시 | 없으면 `attendeeListUrl` 이 `null` | [FE 7.2][fe06] |
| **사용 범위** | 서비스 내 노출 · 추천 영역 노출 · 외부 마케팅 | **기록만 한다.** 홈 섹션 규칙에는 반영하지 않는다. 검수의 `이미지 저작권 확인`이 이 범위를 기준으로 본다 | D-04 · [목업 ProviderManage][mk-provm] |
| **계약** | 시작일·종료일, 정산 방식(텍스트), 비고 | 기록·조회만. 없어도 된다 — 단계 ①은 계약 없이 동의만으로 등록한다 | D-03 · [목업 Admin][mk-admin] |
| **증빙** | 받은 경로·일시·자료 | 형식 TBD | O-15 |

- **바뀔 때마다 새 행을 쌓는다**(적용 시작 시각). 지우지 않는다 — 분쟁 때 "그때 무엇을 허락했나"의 유일한 근거다 (제안).
- 동의 철회 시 공개 회차·이미지 처리는 O-14, 계약 만료 시 처리는 O-50.

### 4.6 개정본 · 검수

주최사의 등록·수정은 **개정본**으로 들어오고, 승인될 때 공개본에 반영된다 — "검수 완료 전까지 기존 내용이 노출됩니다" ([목업 ProviderManage][mk-provm]).

| 필드 | 규칙 | 근거 |
| --- | --- | --- |
| 대상 회차 | 신규 등록이면 없다 | — |
| 종류 | 신규 등록 / 수정 | [목업 Provider·ProviderManage][mk-prov] |
| 내용 | 4.5 의 저장값 중 **검수 대상 필드 전부**의 사본 | — |
| 상태 | `검수 대기` / `승인` / `반려` | [목업 Admin][mk-admin] |
| 제출자 · 제출 시각 | 목업의 `접수` 시각 | 상동 |
| 확인 항목 | 이미지 저작권 확인 · 초상권 동의 확인 · 문구 과장·허위 표현 없음 · 신청 URL 정상 연결 — **넷 다 확인해야 승인** | 상동 |
| 반려 사유 | 이미지 계약 범위 초과 · 초상권 미확인 · 문구 과장 표현 · 신청 URL 오류 중 하나 + 상세 사유. **주최사에게 그대로 전달된다** | 상동 |
| 결정자 · 결정 시각 | — | — |

- **즉시 반영 필드와 검수 필드를 나눈다** — 모집 상태와 정원은 즉시(P-06 · O-04 해소), 나머지는 검수를 거친다.
- **회차 하나에 검수 대기 개정본은 하나다.** 대기 중에 새 수정 요청이 오면 대기 개정본을 바꿔 끼운다 (제안) — 둘이 쌓이면 어느 것이 이기는지 모호해진다.
- **운영자의 대신 등록·수정도 개정본을 남긴다**(자동 승인, 결정자 = 본인). 누가 무엇을 바꿨는지가 한 줄 이력으로 모인다 (제안).

### 4.7 반복 규칙

- 주최사, 회차 틀(4.5 저장값), 규칙(요일·시각·주기), 시작일·종료일. 몇 주 앞까지 만드나는 O-20.
- **만들어진 회차는 독립된 회차다.** 모집 상태·정원·가격을 회차마다 바꾼다 — 회차는 1회성이다 ([decisions 4.19][dec]).
- MVP1 에서 쓰는 사람은 운영자다 ([dev-plan P6-2b][plan]). 주최사도 쓰나는 O-20.

| `tagCategories` | 파생 | 태그에서 | [FE 12장][fe10] |
| 상태 | 저장 | `게시` / `보류`(O-09) / `삭제` | [목업 AdminManage][mk-adminm] |

- **참여 인증된 (계정, 회차)마다 1건이다** (제안) — FE 10.1 `작성할 후기 N건`이 참여한 회차당 1건을 전제한다.
- **참여 인증**은 (계정, 회차, 인증 시각, 방식)이다. 방식 O-01. 후기 작성과 USER 신고의 자격이다 (D-05).
- **답글**은 (후기, 작성 계정, 본문, 시각, 상태)다. 자기 주최사 회차의 후기에만 단다 (D-05). 개수·수정·삭제 O-11.
- 작성자의 후기 수정·삭제는 O-12.

**평점 집계 (주최사당 한 행)**

| 값 | 규칙 | 근거 |
| --- | --- | --- |
| 후기 수 `n` · 평점합 · 점수별 분포(1~5) | `게시` 후기만 센다 (제안 — FE 는 후기 상태를 정의하지 않았다. 보류 포함 여부 O-09) | 집계 항목만 [FE 10.4][fe08] |
| 인기 태그 | 많이 달린 태그 Top 5 | [FE 10.4][fe08] |
| `rating` | 평점합 ÷ n. **n < 5 이면 `null`** — 임계는 서버가 적용해 내려보낸다 | [FE 12장][fe10] · [FE 7.4][fe06] |
| `ratingScore` | `(10 × 4.3 + 평점합) / (10 + n)` — C = 10, m = 4.3. 응답에는 싣되 **화면에 노출하지 않는 값**이다 | [FE 6.2][fe05] · [decisions 4.20][dec] |

- 후기 상태가 바뀌는 트랜잭션에서 함께 증감한다 (3.4). 산출 상세·상수 교체는 7장.

### 4.9 삭제 · 이력 보존 (카탈로그)

**이 표의 삭제 방식은 전부 제안이다.** 프론트 문서는 삭제를 정한 적이 없다 — 이유 칸의 출처는 판단의 전제이지 삭제 규칙의 출처가 아니다.

| 엔티티 | 지우는 방식 | 이유 |
| --- | --- | --- |
| 주최사 | **지우지 않는다.** 비공개로 내린다 | 후기·평점·회차가 주최사에 쌓여 있다 ([decisions 4.19][dec]) |
| 동의·계약 기록 | 지우지 않는다 (이력) | 분쟁 근거 (제안) |
| 회차 (공개된 적 있음) | **지우지 않는다.** 비공개로 내린다 | 후기·찜·이동 기록이 가리킨다. `eventId` 가 남아야 재집계할 수 있다 ([decisions 4.19][dec]) |
| 개정본 · 검수 결정 | 지우지 않는다 | 반려 사유는 주최사에게 전달된 기록이다 |
| 반복 규칙 | 종료 처리 | 만든 회차는 남는다 |
| 후기 | 운영자 삭제는 `삭제` 상태(비노출)로 두고 행은 남긴다 (제안) | 신고 처리의 증거 · 작성자 삭제는 O-12 |
| 평점 집계 | 언제든 후기에서 다시 만든다 | 파생값이다 |
| 이미지 | 동의 철회 시 O-14 | — |
