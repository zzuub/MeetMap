## 3. 서비스 경계

### 3.1 배포 형태 — 모듈러 모놀리스 (제안)

**앱 하나, DB 하나로 시작한다.** Spring Boot 앱 하나(`backend/meetmap`)와 MariaDB 하나에, 모듈을 `com.domain.meetmap.<모듈>` 패키지로 나눈다.

| 판단 | 근거 |
| --- | --- |
| 서비스를 처음부터 쪼개지 않는다 | 떼어 낼 대상이 **`payment-service` 하나로 정해져 있다** ([dev-plan 1장][plan] 확장 메모 · [FE 6.3][fe05] 비즈니스 메모 · D-03). 나머지를 네트워크로 나누면 조인·트랜잭션을 잃는 비용만 생긴다 |
| 대신 모듈 경계를 지킨다 | FE 13장은 API 목록이 "백엔드 서비스 경계와 1:1 대응"한다고 적었다 — **이 장의 모듈이 그 경계다.** 나중에 떼어도 API 경로가 바뀌지 않게 모듈과 경로를 맞춘다 (3.6) |

### 3.2 모듈과 책임 (제안)

| 모듈 | 책임 | 소유 데이터 → 4장 | 경로 |
| --- | --- | --- | --- |
| `account` | 로그인(소셜·비밀번호·2FA), 토큰, 소셜 연동, 초대 | 계정, 로그인 수단, 멤버십, 초대 | `/auth/**` |
| `user` | USER 프로필, 약관 동의, 선호 지역, 알림 설정, 찜 | 프로필, 약관 이력, 선호 지역, 알림 설정, 찜 | `/users/me/**` |
| `provider` | 주최사 프로필, 동의·계약 기록, 가입 신청, 담당 계정 연결 | 주최사, 동의·계약 기록, 가입 신청, 담당 연결 | `/providers/{id}` |
| `event` | 회차 공개본·개정본·검수·반복 규칙, 목록 조회 | 회차, 개정본, 검수 결정, 반복 규칙, 이미지, 태그 | `/events/**` |
| `review` | 후기, 답글, 참여 인증, 주최사 평점 집계 | 후기, 답글, 참여 인증, 평점 집계 | `/events/{id}/reviews` 외 |
| `moderation` | 신고 접수, 신고 건 처리 | 신고, 신고 건 | 6c~6e |
| `notification` | 알림함, 발송(앱 푸시·메일), 방해 금지 시간 | 알림 | `/users/me/notifications/**` |
| `search` | 검색, 인기 검색어 | 검색 기록, 인기 검색어 스냅샷 | `/events/search` · `/search/**` |
| `tracking` | 신청 URL 이동·조회 기록, 통계 집계 | 이동 기록, 조회 기록, 통계 | `/events/{id}/outbound-click` |
| `geo` | 주소→좌표, 역지오코딩, 지역 마스터 | 지역·구 마스터 | `/geo/**` |
| `audit` | 운영자 행위 기록 | 활동 로그 | 운영 API 조회만 |
| `common` | 에러 코드, 시간(KST), 커서 페이지 | — | — |
| ~~`payment`~~ | **만들지 않는다** → 3.5 | — | — |

도메인 마스터는 **쓰는 모듈이 갖는다** — 지역·구는 `geo`, 분위기·직업군 추천은 `event`, 후기 태그는 `review`, 신고 사유는 `moderation`. 원본을 코드 상수로 둘지 테이블로 둘지는 O-31.

### 3.3 의존 규칙 (제안)

1. **쓰기는 소유 모듈만 한다.** 다른 모듈의 테이블을 직접 바꾸지 않고, 그 모듈의 서비스를 부른다.
2. **화면을 그리는 조회는 조인해도 된다.** 탐색 목록은 회차 + 주최사명 + 정렬 점수 + 찜 여부를 한 번에 그린다. 한 DB 안의 조인이 가장 싸고, 모듈마다 따로 불러 합치면 커서 페이지가 어긋난다. 단 **분리 대상(`payment`)은 이 조인에 끼지 않는다.**
3. **부수 효과는 커밋 뒤 도메인 이벤트로 넘긴다.** 알림·메일·통계·검색 반영이 그렇다 — 롤백된 일의 알림이 나가면 안 된다. 발행 신뢰성(아웃박스 여부)은 O-30.
4. **여러 모듈을 한 트랜잭션에 묶는 유스케이스는 모듈 위의 유스케이스 계층이 조율한다.** 가입 승인·초대 수락은 계정(`account`)과 주최사 연결(`provider`)을 같이 바꾸는데, 두 모듈이 서로를 부르게 두면 순환이 생긴다.
5. **운영자 행위는 `audit` 를 같은 트랜잭션에서 부른다.** 모든 모듈이 동기로 부를 수 있는 유일한 의존이다 — 기록 없는 운영자 행위가 생기지 않게.

| 모듈 | 동기로 부르는 모듈 | 부르지 않는 것 (조회 조립이 대신한다) |
| --- | --- | --- |
| `event` | `provider`(동의 범위 확인), `geo`(주소→좌표·구 판정), `audit` | `review`(평점), `user`(찜) |
| `review` | `event`(회차의 주최사·개최 시각) | `provider` |
| `moderation` | `review`(후기 상태 변경), `audit` | — |
| `user` | `event`(찜 대상 존재 확인) | — |
| `tracking` · `search` | `event`(존재 확인·조회) | — |
| `notification` | 없음 — 이벤트만 받는다 | — |

경계를 무엇으로 검사할지(ArchUnit / Spring Modulith)는 O-29.

### 3.4 트랜잭션 경계

**원칙 (제안)**
- 유스케이스 하나가 DB 트랜잭션 하나다.
- **외부 호출은 트랜잭션 밖에서 한다** — OAuth·지오코딩·이미지 저장소·메일·푸시. DB 커넥션을 네트워크 대기에 묶지 않는다. 결과가 저장에 필요하면(주소→좌표) 트랜잭션 **전에** 부른다.
- 운영자 행위와 그 활동 로그는 같은 트랜잭션이다.

아래 표도 **제안**이다 — 출처가 있는 칸에만 출처를 붙였다.

| 유스케이스 | 한 트랜잭션 안 | 커밋 뒤 | 여기서 자르는 이유 |
| --- | --- | --- | --- |
| USER 첫 소셜 로그인 | 계정 + 로그인 수단 + USER 멤버십 | 토큰 발급 | 로그인 수단 없는 반쪽 계정을 막는다 |
| 약관 동의 | 약관 이력 (+ 마케팅 동의) | 갱신된 토큰 전달 | `isNewUser` 가 약관 이력에서 파생되므로 둘이 어긋날 수 없다 ([decisions 4.43·4.50][dec]) |
| 프로필 / 선호 지역 저장 | 프로필 + 선호 지역 / 선호 지역만 | — | 선호 지역은 프로필 없이도 받는다 ([`endpoints.ts`][ep]) |
| 찜 설정·해제 | 찜 한 행 | 통계 | `PUT`/`DELETE` 멱등 ([decisions 4.59][dec]) |
| 신청 URL 이동 기록 | 이동 기록 한 행, **단독** | 통계 | 실패해도 사용자의 이동을 막지 않는다 ([FE 7.3][fe06]) |
| 후기 작성 | 후기 + 태그 + 주최사 평점 집계 증분 | — | 평점의 후기 수와 목록의 후기 수가 어긋나지 않게 — 표시 임계 5건이 이 수에 걸린다 |
| 답글 / 신고 | 답글 / 신고 + 신고 건 | 알림 (O-11) | — |
| 주최사 가입 신청 | 계정 + 비밀번호 + PROVIDER 멤버십(`PENDING`) + 가입 신청 | — | — |
| 가입 승인 | 멤버십 `ACTIVE` + 주최사 연결(기존 프로필 / 새 프로필) + 활동 로그 | 승인 메일 | 주최사와 연결되지 않은 활성 계정은 할 수 있는 일이 없다 |
| 초대 발급 | 초대 + 활동 로그 | 초대 메일 | 메일 실패가 초대를 되돌리지 않게 — 재발송한다 |
| 초대 수락 | 비밀번호 설정 + 멤버십 `ACTIVE` + 주최사 연결 + 초대 소진 | — | 소진과 활성화가 갈리면 같은 초대로 두 번 들어온다 |
| 등록·수정 요청 | 개정본(검수 대기) | — | 공개본은 건드리지 않는다 |
| 검수 승인 | 개정본 승인 + 공개본 반영 + 검수 결정 + 활동 로그 | 주최사 메일, 관심지역 신규 알림, 검색 반영 | 공개본과 검수 이력이 갈리지 않게 |
| 검수 반려 | 개정본 반려 + 사유 + 활동 로그 | 주최사 메일 | — |
| 모집 상태·정원 변경 | 공개본의 해당 필드 | — | 재검수 없이 즉시 반영 — 목업 정원 화면의 저장 문구가 근거다 (O-04 해소 · P-06) |
| 운영자 대신 등록·수정 | 개정본(자동 승인) + 공개본 + 활동 로그 | 관심지역 신규 알림 | 운영자의 변경도 이력에 남긴다 (4a) |
| 반복 회차 생성 (배치) | **회차 한 건씩** | 알림 | 한 건의 실패가 나머지를 막지 않게 |
| 회원 상태 변경 | 멤버십·계정 상태 + 활동 로그 | 세션 무효화 (O-32) | — |
| 후기 보류·삭제 (운영자) | 후기 상태 + 평점 집계 증감(O-09) + 신고 건 상태 + 활동 로그 | 신고자·작성자에게 결과 안내 | — |

### 3.5 payment-service 분리 전제

결제는 MVP2~3 에 별도 서비스로 들어온다. **지금 코드는 만들지 않는다.** 대신 떼어 낼 때 끊을 자리가 한 곳에 모이게 둔다.

| 지금 해 두는 것 | 어떻게 | 근거 |
| --- | --- | --- |
| 신청 진입을 한 경로로 | 모든 신청은 `POST /events/{id}/outbound-click` 을 지난다. 결제가 붙으면 **이 경로의 뒤만** 바뀐다(외부 이동 → 내부 주문) | [`endpoints.ts`][ep] 머리 주석 |
| 가격은 카탈로그 정보다 | `malePrice`·`femalePrice` 는 주최사가 공지한 참가비를 옮겨 적은 **표시값**이다. **결제 금액의 원본으로 쓰지 않는다** — 결제가 붙으면 주문 금액은 `payment-service` 가 갖는다 (제안) | 값의 성격만 출처가 있다 — 운영자가 등록할 때 신청 폼에서 확인해 채우고([dev-plan P6-2][plan]), 확보하지 못하면 `null` 이다([FE 12장][fe10]). 결제에 쓰지 않는다는 판단 자체의 출처는 없다 |
| 계약 기록은 `provider` 에 | 정산 조건은 텍스트로 기록만 한다(D-03). 그 기록을 `provider` 에 두고, 청구가 붙으면 `payment-service` 가 **읽는 쪽**이 되게 한다 (제안) | D-03 |
| 사용자 키는 하나 | 모듈 밖으로 나가는 사용자 식별자는 계정 id 하나다 (제안) | — |
| 이동 기록은 사실만 | "보냈다"만 담는다. 결제 여부·금액을 섞지 않는다 | D-02 |

**지금 만들지 않는 것**: 주문·결제·환불·정산 테이블, PG 연동, 정산 계좌 수집(dev-plan 3.3 가입 폼 → O-38), 청구서.

**분리할 때 함께 바뀌는 것**: ① 신청 URL 이동률의 정의 — 내부 결제는 이동이 아니라 주문으로 잡힌다 ② FE 7.3 외부 이동 모달 — 결제 주체가 바뀌면 "결제를 대행하지 않습니다" 고지 자체가 바뀐다.

### 3.6 API 표면

| 표면 | 경로 | 부르는 곳 | 인증 | 근거 |
| --- | --- | --- | --- | --- |
| 사용자 | `/auth/**` `/users/me/**` `/events/**` `/providers/{id}/**` `/search/**` `/geo/**` | USER 앱 (게스트 포함) | 소셜 로그인 토큰. 게스트 허용 경로가 있다 (5장) | [FE 13장][fe11] · [`endpoints.ts`][ep] — **경로 그대로** |
| 주최사 | `/partner/**` (가안) | 주최사 백오피스 | 이메일·비밀번호 로그인, `PROVIDER` | 목업의 "파트너". 공개 페이지 `/providers/{id}` 와 한 글자 차이라 다른 말을 쓴다 |
| 운영 | `/admin/**` (가안) | 운영 도구 | 이메일·비밀번호 + 2FA, `ADMIN` | [dev-plan 3.4][plan] · D-09 |

- **경로는 역할을 약속하지 않는다.** 서버는 표면마다 역할·상태를 다시 검사하고, 한 표면의 토큰으로 다른 표면을 부를 수 없다 (5장).
- springdoc 은 표면별 그룹 셋으로 나눠 `/docs` 에서 고르게 한다 (제안). 요청/응답 스키마의 원본은 그쪽이다.
