## 1. 범위와 비범위

### 1.1 MVP1 의 경계 — 성장 단계로 자른다

MeetMap 은 **인스타그램에 흩어진 로테이션 소개팅을 모아 비교·탐색하게 해주는 중개 플랫폼**이다. 소개팅을 주최하지 않고, 신청·결제는 주최사 페이지로 보낸다 ([dev-plan 헤더][plan] · [FE 7.3][fe06]).

| 성장 단계 | 누가 소개팅을 올리나 | MVP | 서버에 생기는 것 |
| --- | --- | --- | --- |
| ① 운영자 대신 등록 — **지금** | 운영자가 주최사에 컨택·동의를 받고 대신 등록 | **MVP1** | 운영자 등록·반복 일정·동의 기록 |
| ② 주최사 셀프서비스 | 주최사가 가입 신청 → 승인 → 직접 등록 → 운영자 검수 | **MVP1** | 주최사 가입·등록 요청·검수·통계 |
| ③ 결제 내재화 + 정산 | — | **MVP2~3** | 별도 `payment-service` (3.5) |

- ①·② 의 근거는 [dev-plan 1장][plan] 의 성장 단계와 Phase 0~7, ③ 은 같은 장의 비즈니스 확장 메모와 D-03 이다.
- 개발 순서는 `USER → ADMIN → PROVIDER` 다 — ADMIN 이 PROVIDER 의 승인 게이트라서다 ([dev-plan 1장][plan]). 이 문서의 장 순서와는 무관하다.

### 1.2 서버가 하는 일

| 영역 | 서버의 책임 | 근거 | 상세 |
| --- | --- | --- | --- |
| 카탈로그 조회 | 홈 3섹션(**모집 중만** — 서버 책임), 탐색 목록(필터·정렬·커서·총건수), 지도 마커, 상세, id 묶음 조회, 비교, 검색·인기 검색어 | [FE 13장][fe11] · [decisions 4.23][dec] · [4.62][dec] | 6a |
| 지난 회차 제외 | 개최 시각이 지난 회차를 탐색·검색·지도 목록에서 뺀다. 상세·찜 목록·주최사 후기에는 남긴다 | D-08 | 6a, 7장 |
| 주최사 | 소개 페이지, 후기 목록, 평점 요약(표시 임계 5건 적용) | [FE 7.4][fe06] · [FE 10.4][fe08] | 6a |
| 인증 주체 해석 | `eligibleOnly`·`maxPrice`·가격 정렬을 **가입을 마친 USER 의 기본 정보**(성별·출생연도)로 해석한다. 게스트·가입 미완료면 해석하지 않는다. `isLiked` 는 요청한 USER 의 찜으로 채운다 | [FE 13장][fe11] · [decisions 4.44][dec] · D-14 | 7장 |
| 서버 산출 | 주최사 평점·`ratingScore`·규모·시간대·자동 마감·표시 문자열(KST) | [FE 12장][fe10] · D-07 | 7장 |
| 계정 | USER 소셜 3종 / PROVIDER 이메일 가입 + 승인 + 소셜 연동 / ADMIN 초대 + 2FA | D-01 · D-09 | 5장 |
| USER 개인화 | 약관 동의, **기본 정보(성별·출생연도 — 가입 필수)**, 프로필, 선호 지역, 찜, 알림함, 알림 설정 | [FE 3·10장][fe03] · D-14 | 6b, 6c |
| 후기 | 작성(참여 인증 필요 — O-01), 주최사 답글, 신고 | [FE 10.5][fe08] · D-05 | 6c~6e |
| 주최사 셀프서비스 | 가입 신청, 등록·수정 요청(재검수), 모집 상태, 정원, 통계(조회·찜·신청 URL 이동), 계약 조회 | [목업 Provider·ProviderManage][mk-prov] | 6b, 6d |
| 운영 | 초대 발급, 가입 승인, 소개팅 검수, 대신 등록·반복 일정, 회원 상태, 후기·신고 처리, 활동 로그, 동의·계약 기록 | [목업 Admin·AdminManage][mk-admin] · [dev-plan Phase 6][plan] | 6b, 6e |
| 신청 URL 이동 기록 | 사용자를 주최사 신청 페이지로 보낸 사실을 남기고 통계로 모은다 | [FE 7.3][fe06] · [`endpoints.ts`][ep] | 6c, 9장 |
| 비동기 | 알림 발송, 반복 회차 생성, 집계 갱신, 주최사 메일 | [FE 10.3][fe08] · [목업 ProviderManage][mk-provm] | 8장 |
| 외부 연동 | 카카오·네이버·구글 OAuth, 지오코딩, 이미지 저장소, 메일 | — | 9장 |

### 1.3 서버가 하지 않는 일

| 하지 않는 것 | 대신 하는 것 | 근거 |
| --- | --- | --- |
| **신청 접수·결제 대행** | 신청 URL 로 보내고 그 **이동**만 기록한다 | [FE 7.3][fe06] "결제를 대행하지 않는 중개 플랫폼" · [dev-plan 1장][plan] |
| 지원·선발 현황 (지원 수, 선발 수, 지원서 접수 알림) | 신청 URL 이동 수만 보여준다 | D-02 — 서버가 이 숫자를 얻을 경로가 없다 |
| 청구·수납·정산 | 계약 정보(기간·허가 범위·정산 방식)를 **기록·조회**만 한다 | D-03 — MVP2~3 |
| 참석자 리스트 저장 (이미지·개별 행) | 집계값(출생연도 범위·직업군·남녀 정원) + 동의한 주최사의 원본 링크 | [FE 7.2][fe06] · [decisions 4.33][dec] |
| 사용자 좌표 저장 | 역지오코딩 요청 **본문**으로 받아 쓰고 버린다 | [FE 4.1][fe03] · [decisions 4.54][dec] |
| 인스타그램 크롤링·무단 등록 | 컨택 → 동의 → 등록. 동의 범위를 기록한다 | [decisions 4.18][dec] · [인수인계 2장][handoff] |
| 비교함 서버 저장 | 클라이언트 `localStorage` (서버 저장 여부는 FE 16장 미결 그대로) | [FE 2.4][fe02] |
| 최근 검색어 저장 | 클라이언트 `localStorage` | [FE 2.4][fe02] |
| USER 이메일·비밀번호 가입 | 소셜 3종 전용 | [FE 3.1][fe03] · D-01 |
| 한 계정의 여러 역할 (역할 전환) | 계정 하나에 역할 하나 | D-01 |
| 서울 외 지역 데이터 | `province` 는 `SEOUL` 고정. 시/도 → 구 2단 구조만 미리 둔다 | [FE 6.1·6.3][fe05] |
| 마감·지난 회차의 신청 URL 차단 | 막지 않는다. 프론트 모달이 알린다 | [decisions 4.37][dec] · D-07 |
| 잔여석·성비·마감임박 알림 등 폐기된 기능 | — | 2.3 폐기된 용어 |

> **한 줄로 줄이면** (제안 — 위 표에서 뽑아낸 정리다) — 서버는 **MeetMap 이 원본을 갖지 못한 사실**(신청·선발·결제, 참석자 개인, 사용자 위치)을 저장하지 않고, 원본이 있는 곳으로 보낸다. 위 표의 신청·결제 대행, 지원·선발 현황, 참석자 리스트, 사용자 좌표 네 줄이 이 원칙의 사례다. 청구·수납은 원본이 없어서가 아니라 단계를 미룬 것이고(D-03), 크롤링 금지는 동의 원칙이다. 새 기능이 이 선을 넘으면 1장부터 다시 본다.

### 1.4 범위가 바뀌는 조건

| 조건 | 바뀌는 것 | 근거 |
| --- | --- | --- |
| 서울 외 지역으로 확장 | 결제 내재화(`payment-service`) 착수. `province` 활성 | [dev-plan 1장][plan] 확장 메모 |
| 이용자 증가 | 청구·수납(정산)을 MeetMap 이 직접 한다 — 배민 방식 | D-03 |
| 주최사 셀프서비스 정착 | 마감 상태를 신뢰할 수 있게 되므로 마감 회차 신청을 막을지 다시 본다 | [decisions 4.37][dec] 번복 조건 |
| 상품 유형 분화 (소셜링·파티·1:1) | 카테고리 축 부활 검토 | [decisions 4.6][dec] 번복 조건 |
