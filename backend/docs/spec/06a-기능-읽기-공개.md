## 6. 기능 상세

### 6.0 서식 — 6a~6e 공통

| 칸 | 적는 것 |
| --- | --- |
| ID | `R` 읽기 · `W` USER 쓰기 · `P` PROVIDER 쓰기 · `A` ADMIN 쓰기 + 번호 |
| 주체 · 선행조건 | 누가 부르나(5.4), 무엇이 먼저 참이어야 하나 |
| 입력 | **뜻만** 적는다. 필드 이름·타입·예시는 springdoc 이 원본이다 |
| 검증 → 처리 → 결과 | 서버가 거르는 것, 하는 일의 순서, 돌려주는 것의 뜻 |
| 예외 | `400` 입력 오류 · `401` 미인증 · `403` 권한 없음 · `404` 없음(남의 것 포함 — 5.5) · `409` 상태 충돌. 오류 코드 체계는 10장 |

권한 판정은 모든 유스케이스에서 5.6 의 순서를 따르므로 칸마다 되풀이하지 않는다.

### 6.1 노출 조건 — 읽기 경로 전부가 쓴다

| 이름 | 조건 | 근거 |
| --- | --- | --- |
| **노출 가능** | 회차 공개 ∧ 주최사 공개 ∧ 주최사의 `정보 등록` 동의가 유효 | 4.3 · 4.5 공개 여부(제안) · 동의 효과는 [FE 7.2][fe06] |
| **목록 노출** | 노출 가능 ∧ **개최 시각 전** | D-08 |
| **모집 중** | 목록 노출 ∧ 선언한 모집 상태가 `신청 가능` | [decisions 4.23][dec] · D-07 |
| 응답의 `status` | 선언이 `마감`이거나 개최 시각이 지났으면 `마감`. 마감 사유를 함께 싣는다 | D-07 · O-42 |

- 목록 응답의 회차마다 `isLiked` 를 요청한 USER 의 찜으로 채운다 — 찜 id 목록(R-22)과 같은 기준이고, 기본 정보와 무관하다 ([`endpoints.ts`][ep]). `distanceKm` 은 MVP1 에서 늘 `null` 이다 — 좌표를 받는 조회가 없다 ([decisions 4.53][dec]).
- 인증 주체 축(`eligibleOnly`·`maxPrice`·가격 정렬)은 **가입을 마친 USER 에게만** 해석하고, 게스트·가입 미완료면 오류가 아니라 **무시**한다 ([decisions 4.27·4.44][dec] · D-13 · D-14). 축의 뜻은 7장.

### 6.3 유스케이스

#### R-01 홈 피드

| 칸 | 내용 |
| --- | --- |
| 입력 | 없음. **좌표를 받지 않는다** (D-11) — FE 13장의 `?lat&lng` 는 좌표를 URL 에 싣지 않는다는 원칙([decisions 4.54][dec])과 어긋나고, 프론트도 지금 비워 보낸다([decisions 4.53][dec]) → O-59 |
| 처리 | 1. 모집 중 회차를 모은다 — **세 섹션 모두**. 홈에는 상태 필터가 없어 거르는 것이 서버 책임이다<br>2. A 이번 주 인기: KST 이번 주(월~일) 개최 + `popularity` 내림차순, 6건<br>3. B 내 나이대: 인증 주체의 출생연도가 참가 연령 범위에 드는 회차, 최신순 6건. 게스트·가입 미완료면 빈 목록<br>4. C 새로 등록된: 등록일 내림차순, 4건<br>5. 추천 기준 문구의 지역명(`baseAreaLabel`) — 산출 규칙 O-66 |
| 결과 | 세 섹션 + 지역명. 빈 섹션은 빈 목록이다 — 줄을 그리지 않는 것은 화면의 몫이다 |
| 근거 | [FE 5.3][fe04] · [decisions 4.23][dec] · [FE 5-5][fe04] |

#### R-02 탐색 목록

| 칸 | 내용 |
| --- | --- |
| 입력 | 조회 축 14개 — 시/도·구·일정·시간대·규모·모집 상태·가격 상한·자격·정렬·분위기·지역·주최사·커서·개수 ([FE 6.1][fe05]) |
| 검증 | 마스터·열거 밖의 값은 `400` (제안) — 프론트가 파싱에서 이미 기본값으로 떨어뜨리므로([FE 6.1][fe05]) 서버에 오는 모르는 값은 클라이언트 결함이다. 시/도는 `SEOUL` 만, 가격 상한은 `PRICE_CAPS` 값만 받는다 |
| 처리 | 1. 목록 노출 회차에서 축별로 거른다 (뜻은 7.5)<br>2. 정렬한다 (7.4). 동률은 id 로 고정한다 (제안) — 커서가 흔들리지 않게<br>3. 커서로 자르고 조건에 맞는 **전체 건수**를 센다<br>4. **첫 페이지에 패싯을 싣는다** (D-11) — 시간대별·구별 건수를 **자기 축만 풀고** 센다. 목록과 한 스냅샷에서 세야 선택한 구의 건수가 결과 수와 같다 ([decisions 4.28][dec] 이 근본 해결로 적은 모양 → O-60) |
| 결과 | 회차 요약 목록, 다음 커서, 전체 건수, (첫 페이지) 패싯. 페이지 크기 O-56 |
| 예외 | 잘못된 커서 `400` (제안) — 재시도할 수 없는 실패라 프론트가 `더 보기` 를 거둔다 ([decisions 4.40][dec]) |
| 근거 | [FE 6.1~6.5][fe05] · [FE 13장][fe11] · [decisions 4.25·4.27·4.28][dec] |

#### R-03 지도 마커

| 칸 | 내용 |
| --- | --- |
| 입력 | R-02 의 거르기 축 + 뷰포트 범위(`bbox`) |
| 처리 | R-02 와 **같은 거르기**에 뷰포트 안인 것만. 페이지 없이 돌려준다 — 마커 소스는 목록과 같아야 한다 ([FE 6.6][fe05]) |
| 결과 | 마커용 회차 요약 — 위치 정밀도와 역 이름을 반드시 싣는다(마커 모양·시트 문구) |
| 예외 | 범위 형식 오류 `400`. 마커 수 상한·클러스터링 O-57 |
| 근거 | [FE 6.6][fe05] · [FE 13장][fe11]. 화면은 P3-1 에서 붙는다 |

#### R-04 소개팅 상세

| 칸 | 내용 |
| --- | --- |
| 처리 | 1. 노출 가능이면 **지난 회차도 연다** (D-08)<br>2. 주최사 블록: 이름·한 줄 소개·평점(표시 임계 적용)·후기 수. `ratingScore` 는 싣지 않는다 — 12장 `EventProviderDetail` 대로다(FE 13장의 표기는 O-64)<br>3. 장소는 정밀도별로: `EXACT` 만 장소명·주소, `STATION` 은 역 이름, `DISTRICT` 는 구 ([FE 7.1][fe06])<br>4. 참석자 리스트 링크는 표시 동의가 있을 때만 ([FE 7.2][fe06])<br>5. 조회 기록을 남긴다(정의 O-05). 기록 실패가 응답을 막지 않는다 (제안) |
| 예외 | 없는 id · 노출 불가 `404` |
| 근거 | [FE 7.1·7.2][fe06] · [FE 12장][fe10] · [decisions 4.33][dec] |

#### R-05 id 묶음 조회

| 칸 | 내용 |
| --- | --- |
| 입력 | 회차 id 목록. 개수 상한 O-36. 빈 목록은 `400` (제안) — 프론트는 빈 요청을 보내지 않는다 ([decisions 4.62][dec]) |
| 처리 | **상태·개최 시각으로 거르지 않는다** — 찜한 소개팅은 마감·지난 뒤에도 남는다. 없는 id 와 노출 불가 회차는 **조용히 뺀다**(`200`). 순서는 약속하지 않고 `isLiked` 는 채우지 않아도 된다 |
| 근거 | [`endpoints.ts`][ep] `event.batch` · [decisions 4.62][dec] · [FE 9장][fe07] |

#### R-06 비교

| 칸 | 내용 |
| --- | --- |
| 입력 | 회차 id 최대 3개 ([FE 8장][fe07]) |
| 처리 | 회차 요약마다 주최사 평점(표시 임계 적용)·후기 수를 붙인다 — 비교표의 `주최사 평점` 행이다. 없는 id·노출 불가는 R-05 처럼 뺀다. `가성비`·`가까움`·`후기 좋음` 배지 판정은 화면의 몫이다 |
| 예외 | 3개 초과 `400` |
| 근거 | [FE 8장][fe07] · [FE 13장][fe11] "클라이언트 조합도 가능" — 서버 엔드포인트를 두는 것은 평점을 한 번에 싣기 위해서다 (제안) |

#### R-07 검색

| 칸 | 내용 |
| --- | --- |
| 입력 | 검색어 하나 |
| 검증 | 앞뒤 공백 제거·연속 공백 한 칸으로 **정규화한 뒤** 비면 `400` (제안) — 프론트와 같은 규칙으로 읽는다 |
| 처리 | 1. **목록 노출** 회차에서 찾는다 — 지난 회차는 빠진다 (D-08 → O-63)<br>2. 소개팅명·지역(`area`)·주최사명 **각각**에서 대소문자를 무시한 부분 문자열로 찾는다. 필드를 이어 붙인 문자열에서 찾지 않는다<br>3. **모집 상태로 거르지 않는다** — 마감 회차도 내린다<br>4. 검색 기록을 남긴다(검색어·시각, 계정 없음 — 4.15) |
| 결과 | 회차 요약 배열. 순서를 약속하지 않고 페이지도 없다 — 상한 O-58 |
| 근거 | [FE 11.1][fe09] · [`endpoints.ts`][ep] `event.search` · [decisions 4.66·4.70][dec] |

#### R-08 인기 검색어

| 칸 | 내용 |
| --- | --- |
| 처리 | 가장 최근 **스냅샷**을 돌려준다. 스냅샷은 배치가 만든다(간격 가안 1시간 — 8장) |
| 결과 | 순위 순서 배열(1위가 첫째, 순위 필드는 따로 없다), 6개 이하, 검색어마다 직전 스냅샷의 순위(없었으면 `null`), 스냅샷 시각(오프셋 포함) |
| 스냅샷 규칙 | **결과 보장** — 스냅샷을 만들 때 **다음 스냅샷까지 개최 전인** 회차로 1건 이상 나오는 검색어만 올린다 (제안). 지난 회차가 검색에서 빠지므로(D-08) "지금 1건"은 한 시간 안에 0건이 될 수 있다. 회차가 비공개·삭제되며 생기는 틈은 다음 스냅샷까지 남고, 프론트가 관측한다 ([decisions 4.68][dec])<br>**거르기** — 개인정보(이름·연락처)·욕설은 서버가 거른다. 금칙어·운영자 수동 제외·최소 검색 수는 O-55 |
| 근거 | [FE 11.1][fe09] · [`endpoints.ts`][ep] `search.trending` · [decisions 4.68][dec] |

#### R-09 주최사 소개

| 칸 | 내용 |
| --- | --- |
| 처리 | 한 번에 내린다 — FE 13장이 이 모양을 적었고, FE 12장도 "나뉘는 것은 프론트의 타입 경계"라고 허락했다<br>1. 프로필: 이름·한 줄 소개·인스타그램·소개 본문·등록일<br>2. 평점 요약: 평균 평점 `rating`(**5건 미만이면 `null`** — FE 12장 `ProviderSummary.rating` 이 이미 정한 규칙)·후기 수·점수별 분포·인기 태그 Top 5. 후기 목록 화면의 요약 블록(`ReviewSummary`)도 이 값을 쓴다 — `ReviewSummary.average` 에도 같은 임계를 건다 (D-11 · O-62)<br>3. 모집 중 회차를 **개최일 가까운 순**으로 ([FE 7.4][fe06])<br>4. 최근 후기 3건 — 카드 모양은 R-10 과 같다<br>`ratingScore` 는 싣지 않는다 (D-11) — 정렬을 서버가 하므로 화면에 쓸 곳이 없다 (O-61) |
| 예외 | 없는 주최사 · 비공개 `404` |
| 근거 | [FE 7.4][fe06] · [FE 10.4][fe08] · [FE 12장][fe10] · [FE 13장][fe11] |

#### R-10 주최사 후기 목록

| 칸 | 내용 |
| --- | --- |
| 입력 | 분류(`전체`·`분위기`·`진행`·`장소`), 커서 |
| 처리 | 1. 그 주최사 **모든 회차**의 `게시` 후기 ([decisions 4.19][dec]). 분류는 그 분류의 태그가 하나라도 달린 후기다 (제안)<br>2. 최신순 (제안 — 주최사 소개의 `최근 후기 3건`과 같은 축)<br>3. 후기마다 회차명·작성일·작성자 표시·주최사 답글(D-05 · O-41)과, 요청자가 이 후기를 신고할 수 있는지를 싣는다 (제안 — 자격은 서버가 계산한다, 5.5) |
| 결과 | 커서 페이지. 평점 요약은 R-09 가 준다 |
| 예외 | 없는 주최사 · 비공개 `404`, 모르는 분류 `400` |
| 근거 | [FE 10.4][fe08] · [FE 13장][fe11] |
