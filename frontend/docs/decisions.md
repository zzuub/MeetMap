## 4.1 FSD 레이어 경계를 ESLint 로 강제한다

`app → widgets → features → entities → shared` 단방향. 역방향·동일 레이어 참조 금지.

**왜**: 문서로만 두면 지켜지지 않는다. `eslint.config.mjs` 의 `no-restricted-imports` 로 막아 빌드 전에 걸리게 했다.

**부작용**: 동일 레이어 참조가 막히므로, 여러 entity 가 공유하는 데이터는 `shared` 로 올라갈 수밖에 없다 → 4.2 의 원인.

## 4.2 `shared/config` 에 도메인 마스터 데이터를 둔다 (`shared` 원칙의 예외)

`AREAS` · `SEOUL_DISTRICTS` · `MOOD_TAGS` · `REVIEW_TAGS` · `TIME_SLOTS` · `JOB_GROUPS`. (`CATEGORIES` 는 4.6 으로 삭제됐다)

**왜**: `src/README.md` 는 `shared` 를 "도메인 지식이 없는 자원"이라 정의하므로 표면적으로 충돌한다. 그러나 **옮길 곳이 없다.** `AREAS` 는 event(개최 지역)와 user(선호 지역)가 함께 쓴다. `entities/event` 에 두면 `entities/user` 가 참조해야 하는데 그건 4.1 이 금지한다.

**한계**: 값의 목록만 둔다. 도메인 규칙·판정 함수는 두지 않는다.

**번복 조건**: 백엔드가 마스터 API 를 제공하면 이 파일은 타입 소스 겸 fallback 으로 축소된다.

## 4.6 도메인 재정의 — 목업에 있으나 실재하지 않는 값을 걷어낸다 (2026-09-01)

제품 정의가 **"인스타그램에 개인 단위로 흩어진 로테이션 소개팅을 모아 비교·탐색하게 하는 플랫폼"** 으로 확정됐다. 실제 주최사 운영 방식을 조사한 결과, 목업이 전제한 값 중 **도메인에 존재하지 않는 것**이 드러났다.

| 삭제·변경 | 이유 |
| --- | --- |
| `category` **삭제** | 상품 종류가 로테이션 소개팅 하나다. 취미 카테고리(와인/전시/러닝)는 성립하지 않고, 게시물에서 **추출 자체가 안 된다** |
| `remainingSeats` **삭제**, `EventStatus` 3→2 (`신청 가능`/`마감`) | 선착순이 아니라 **주최사가 지원자를 심사해 선발**한다. 마감을 선언하기 전까지 계속 받으므로 잔여 좌석이라는 값이 없다 |
| `femaleRatio` **삭제** → `maleCapacity`/`femaleCapacity` | 정원이 남녀 고정(7:7, 15:15)이라 성비는 항상 50%다 |
| `minAge`/`maxAge` → `birthYearFrom`/`birthYearTo` | 주최사는 나이가 아니라 **출생연도**로 모집한다 (`90~96년생`) |
| `price` → `malePrice`/`femalePrice` (nullable) | 남녀 가격이 다르다. 가격이 신청 폼 안에만 있어 등록 시 확보하지 못하는 건이 있다 |
| `applyDeadline` **삭제**, 마감임박 알림 삭제 | 별도 신청 마감일이 없다. 발송 트리거를 정의할 수 없다 |
| `genderPolicy` **삭제** | 남녀 정원이 애초에 분리 모집이라 별도 정책 필드가 불필요. dev-plan blocking #4 해소 |
| `TimeSlot` 3→4 (`MORNING`/`AFTERNOON`/`DINNER`/`LATE_NIGHT`) | 삭제한 카테고리 축을 대신한다 |
| `locationPrecision` **신설** | 정확한 주소가 없는 소개팅이 상당수다. 동 → 지하철역 → 구 순으로 핀을 내리고 정밀도를 표시한다 |
| `jobGroups` **신설** | 참석자 정보의 공통 축은 연령대·직업군·남녀 정원 세 가지다 |

**필터 축 선정 기준**: *모든 주최사 게시물에서 결측 없이 얻을 수 있는가.* 내가 손으로 등록하는 단계라 이게 절대적이다. 반쯤 빈 필터는 켜는 순간 멀쩡한 소개팅을 숨겨서 없느니만 못하다. 이 기준으로 카테고리는 탈락하고, 시간대·정원·날짜·지역이 1급 축이 됐다.

**연령을 필터가 아니라 자격으로 올린 이유**: 92년생이 `95~02년생 전용`을 봐도 의미가 없다. 온보딩에서 받은 출생연도로 처음부터 걸러 보여주고(`eligibleOnly`), 넓히고 싶을 때 끄게 한다.

**참석자 리스트**: 인스타에 공개돼 있어도 그대로 쓰지 않는다. 이미지는 주최사 저작물이고, 개별 참석자는 **그 주최사 계정에** 공개 동의한 것이다. MVP1은 **집계값만** 저장·표시하고, 원본은 아웃링크로 보낸다 (기능정의서 7.2).

**번복 조건**: 주최사 셀프서비스(Phase 7) 진입 후 상품 유형이 실제로 분화하면(예: 소셜링/파티/1:1) 그때 카테고리 축을 다시 만든다.

**코드 반영**: 2026-09-02 P1-0 에서 타입·상수·목데이터·목 API 를 교체했다(3장). 화면(`EventCard` 이하)은 P1-1 부터다.

## 4.3 목/실 API 를 인터페이스 하나로 분기한다

계약은 `entities/event/model/ports.ts` 의 `EventApi`, 구현은 `api/` 에 mock 과 http 둘. 분기는 `eventApi.ts` 마지막 한 줄 + `NEXT_PUBLIC_USE_MOCK`.

**왜**: 백엔드가 비어 있어 프론트가 기다릴 수 없다. 화면은 계약만 알므로 실 API 전환이 환경변수 한 줄이 된다. 컴포넌트에 `if (USE_MOCK)` 을 쓰지 않는다.

**검증됨**: `USE_MOCK=false` 빌드에서 목 데이터가 JS 산출물에 남지 않는다(서버 0 / 클라이언트 0). 트리셰이킹 정상.

## 4.4 계정과 역할을 분리한다 (`Account` 1:N `Membership`)

**왜**: 같은 사람이 개인 회원이면서 주최사 담당자일 수 있다. 계정에 `role` 컬럼 하나를 박으면 나중에 계정을 새로 파야 한다.

**단**: UI 에서는 한 번에 하나의 역할만 활성화한다.

## 4.5 ADMIN 은 소셜 로그인을 쓰지 않는다

`AuthIntent` 유니온에서 `ADMIN` 을 의도적으로 제외했다.

**왜**: ① 소셜 계정 하나가 털리면 운영자 권한이 통째로 넘어간다 ② 퇴사자 계정 회수를 우리가 통제할 수 없다(계정 소유권이 개인에게 있다) ③ 2FA·IP 제한 같은 내부 통제를 소셜 위에 얹기 어렵다.

역할 의도는 **서버가 서명한 OAuth `state`** 로만 전달한다. 콜백 바디의 `role` 을 믿으면 `role: "ADMIN"` 한 줄이 권한 상승이 된다.

## 4.7 서버 렌더에서는 fetch 에 `signal` 을 붙이지 않는다

**왜**: Next 는 한 렌더 안의 동일 GET 요청을 메모이즈하는데, **`signal` 을 넘기면 이 메모이제이션이 꺼진다**(공식 문서). 타임아웃에는 `signal` 이 필요하므로 둘은 양립하지 않는다.

**측정**: 같은 URL 을 코드에서 2번 호출할 때 — signal 있음 → 네트워크 2회 / signal 없음 → **1회**.

**결론**: 브라우저는 기본 타임아웃(메모이제이션 대상이 아님), 서버는 `timeoutMs` 를 명시할 때만. 서버 타임아웃은 게이트웨이 계층의 책임으로 본다.

## 4.8 `Sheet` / `Modal` 은 `document.body` 로 포털한다

**왜**: `position: fixed` 는 조상에 `transform` / `filter` / `backdrop-filter` / `contain` / `will-change` 가 하나라도 있으면 뷰포트가 아니라 **그 조상** 기준이 된다. 이미 `backdrop-blur` 를 헤더·하단내비에서 쓰고 있고, Phase 3 지도 컨테이너에서 터질 예정이었다.

**측정**: 조상에 `transform` 을 넣었을 때 — 제자리 렌더 `320×200, top:2467`(화면 밖) / 포털 `375×812, top:0`.

**부수 효과**: SSR 게이팅이 필요해졌다. `useEffect(() => setMounted(true), [])` 는 이펙트 내 동기 setState 라 린트에 걸리므로 `useIsClient`(`useSyncExternalStore`)를 썼다.

## 4.9 `Intl.DateTimeFormat` 인스턴스를 공유한다

**왜**: 생성자가 로케일 데이터를 해석해 무겁다. 호출마다 만들면 탐색 리스트 20건 × (날짜+시간) = 렌더당 40개 단명 객체.

**측정**: 12,000회 호출 — 호출마다 생성 667ms / 인스턴스 공유 62ms. **10.8배**.

## 4.10 Vitest 를 쓰되 jsdom 은 붙이지 않는다

**왜**: 현재 테스트 대상이 순수 함수뿐이라 DOM 이 필요 없다. 실행이 빠르고 의존성도 줄어든다. React 컴포넌트 테스트가 필요해지면 그때 `jsdom` + `@testing-library/react` 를 추가하고 `environmentMatchGlobs` 로 파일별로 나눈다.

⚠️ **jsdom 없이도 렌더 결과를 볼 수 있는 경우가 있다** — 포털·클라이언트 훅을 거치지 않는 순수 컴포넌트는 `react-dom/server` 로 렌더해 검사한다. 7.3 법적 고지가 실제로 그려지는지를 그렇게 잠갔다 (4.38).

**통과하는 테스트를 믿지 않는다**: 새 테스트를 넣을 때는 **일부러 코드를 깨뜨려 실패하는지 확인**한다(변이 테스트). 이 관행을 유지한다.

## 4.11 의존성은 정확한 버전으로 고정한다 (캐럿 미사용)

**왜**: create-next-app 의 기존 컨벤션을 유지한다. 락파일이 커밋되어 있고 CI 가 `npm ci` 를 쓰므로 재현성은 어느 쪽이든 같지만, 업그레이드를 명시적 행위로 남긴다.

## 4.12 `proxy.ts` 는 UX 가드이지 보안 경계가 아니다

> 원래 4.6 이었으나 4.6(도메인 재정의)과 번호가 겹쳐 2026-09-02 에 4.12 로 옮겼다. 내용은 그대로다.

**왜**: 토큰 서명을 검증하지 않는다. 엣지에서 검증하려면 공개키 배포가 필요한데 그 복잡도만큼의 이득이 없다 — 위조 토큰으로 화면을 열어도 데이터는 서버가 막는다.

## 4.13 `stationName` 을 `EventSummary` 에 추가한다 (기능정의서 12장 초과) (2026-09-02)

12장에 없는 필드를 하나 넣었다. `locationPrecision === 'STATION'` 일 때의 기준 역명이다.

**왜**: 6.6 지도 마커 시트가 `○○역 인근` 을 표시해야 하는데, 마커 시트가 받는 것은 `EventSummary` 다. 12장의 `venueName` 은 (a) `EventDetail` 에만 있고 (b) `EXACT` 전용이라 역명을 담을 자리가 없다. `DISTRICT` 는 `district` 라벨로 그릴 수 있지만 `STATION` 은 근거가 될 값 자체가 모델에 없었다.

**검토한 대안**:

| 안 | 기각 이유 |
| --- | --- |
| `venueName` 의 의미를 넓혀 역명도 담는다 | "장소명"과 "기준 역명"은 다른 값이다. `EventDetail` 전용이라는 문제도 그대로 남는다 |
| `locationLabel` 하나로 3종을 서버가 문자열로 내린다 | 정밀도별 마커 모양 분기(6.6)와 라벨이 한 값에 섞여, 화면이 정밀도를 다시 파싱하게 된다 |
| 필드를 넣지 않고 `STATION` 을 `DISTRICT` 처럼 구 이름으로 표시 | 정밀도를 구분하는 목적 자체가 사라진다. 사용자가 헛걸음하는 것을 막는 장치다 |

**후속**: 코드가 문서보다 앞선 상태를 오래 두면 다음 대조 때 "누락"으로 오검된다. **2026-09-02 기능정의서 12장 `EventSummary` 에 `stationName` 을 반영**해 드리프트를 닫았다(PR #10 리뷰 지적). 7.1 장소 행·6.6 마커 시트도 라벨 출처를 필드명으로 명시했다.

**번복 조건**: `venueName` 을 `EventSummary` 로 올리고 정밀도별 의미를 부여하기로 하면 이 필드는 사라진다.

## 4.14 남녀 정원은 동수를 전제하되 필드는 둘로 유지한다 (2026-09-02)

로테이션 소개팅은 주최사가 `7:7`·`15:15` 처럼 정원을 고정해 남녀를 따로 모집한다. **`maleCapacity === femaleCapacity` 다.**

**그런데 필드를 하나로 합치지 않았다.** 한쪽만 추가 모집하는 회차 같은 예외가 나중에 들어와도 스키마를 바꾸지 않고 담기 위해서다. 판정 함수도 그 경우에 답을 낸다 — `deriveScale` 은 큰 쪽, `isEligible` 은 내 성별 쪽만 본다.

**`deriveScale` 이 합계가 아니라 한쪽 정원 기준인 이유**: 동수 전제에서는 6.4 의 `5:5 이하 / 6:6~9:9 / 10:10 이상` 표기를 변환 없이 그대로 경계로 쓸 수 있다. 합계로 옮기면 `10:9`(=19) 같은 값이 6.4 의 어느 칸에도 정확히 안 맞는 회색 구간이 생긴다. 비대칭이 들어오면 **큰 쪽**으로 판정한다 — "한쪽이라도 10명을 모집하면 대규모"가 사용자가 체감하는 규모에 가깝다.

**문서 정합**: 12장의 `scale` 주석이 "정원 합계 기준"으로 적혀 있어 6.4 본문(`5:5`/`10:10`)과 표현이 어긋났다. 동수 전제에서는 같은 말이고 비대칭에서만 갈린다. **2026-09-02 12장을 "한쪽 정원 기준"으로 통일**했다(PR #10 리뷰 지적).

> ⚠️ **P1-2 배지 작업 때 볼 함정.** `scale` 이 큰 쪽 기준이라, 비대칭 건이 들어오면 `남 20 · 여 1` 이 `대규모` 배지를 단다. 그런데 여성 사용자가 실제로 신청할 수 있는 자리는 1석이다. `대규모` 라벨은 "내 성별도 많이 온다"는 기대를 주는데 반대일 수 있다.
>
> 동수 전제가 유지되는 동안은 드러나지 않는다. 비대칭이 실제로 들어오면 **배지를 내 성별 정원 기준으로 바꾸거나, 배지 옆에 `남 N · 여 N` 을 항상 붙여** 오해를 막는다. 지금 미리 만들지는 않는다 — 존재하지 않는 데이터를 위한 분기다.

**번복 조건**: 비대칭 정원이 흔해지면 화면 표기(`남 N · 여 N`)와 규모 라벨을 다시 본다. 목 데이터가 동수라는 사실은 테스트가 지킨다.

## 4.15 직업군은 닫힌 마스터가 아니라 자유 입력 태그다 (2026-09-02)

`JOB_GROUPS` 8종은 **강제 마스터가 아니라 등록 폼에서 먼저 제안하는 추천 태그**다. 저장되는 값은 주최사·운영자가 입력한 원문이고, 그래서 `jobGroups` 는 `string[]` 이며 이 배열에서 파생한 유니온 타입을 두지 않는다.

**왜**: 주최사마다 표기가 제각각인데 8종을 강제하면 등록할 때마다 "이건 어디에 넣지"가 생긴다. 지금은 운영자가 대신 등록하는 단계라 이 마찰이 곧 등록 속도다. 게다가 직업군은 **필터 축이 아니다** — 6.4 필터 3층에 직업군 그룹이 없고, "모든 게시물에서 결측 없이 얻을 수 있는가"라는 축 선정 기준(4.6)에도 미달한다. 표시 전용이면 정규화 압력이 낮다.

**대신 UI 가 표기 수렴 압력을 만든다** (P6-2 / P7-2 등록 폼의 책임):

- 기존 태그를 **사용 빈도순**으로 먼저 노출하고, 새 태그는 한 단계 더 눌러 만든다 (노션 select 방식). 이게 없으면 그냥 자유 텍스트고 `대기업`/`대기업 재직`/`대기업(IT)` 이 각각 다른 태그로 쌓여 소개팅끼리 비교가 안 된다
- **회사명·학교명은 받지 않는다.** 직업"군" 단위여야 한다 — `삼성전자 DS부문` 같은 값은 날짜·소규모 인원과 결합하면 참석자가 식별되고, 그러면 7.2 의 집계값 원칙을 어긴다
- 건당 개수 상한 3~4개 (상세 정보 카드 한 줄)

**번복 조건**: 직업군을 필터·검색 축으로 승격하면 그때 정규화 매핑을 둔다. 그 경우에도 **원문은 보존**한다 — 매핑 규칙이 틀렸을 때 되돌릴 근거가 원문뿐이다.

## 4.16 카드는 stretched link 로 만들고 액션은 슬롯으로 비운다 (2026-09-02)

카드 전체가 상세로 가는 링크인데 그 안에 찜 버튼이 있다. 이걸 만드는 방법이 셋이고, 두 개는 함정이다.

| 방법 | 문제 |
| --- | --- |
| `<a>` 안에 `<button>` 중첩 | **HTML 무효.** 스크린리더가 둘을 한 덩어리로 읽어 찜 버튼에 도달할 수 없다 |
| 카드에 `div + onClick`, 버튼에 `stopPropagation` | 15장이 금지한 패턴. 키보드로 카드에 도달할 수 없고, 6.5 가 요구한 `stopPropagation` 은 이 방법을 쓸 때만 필요한 것이다 |
| **제목 링크의 `::after` 를 카드 전체로 늘린다** ← 채택 | 카드 하나에 탭 스톱 하나, 액션에 하나. 클릭 이벤트가 애초에 겹치지 않는다 |

`<article className="relative">` 가 유일한 positioned 조상이고, 제목의 `<Link>` 가 `after:absolute after:inset-0` 을 단다. 액션은 `z-10` 으로 그 위에 올린다.

**주의 — 카드 안에 `relative` 를 더 두면 히트 영역이 그쪽으로 잘린다.** `EventThumbnail` 도 `relative` 지만 링크의 **조상이 아니라 형제**라 안전하다. 이 조건이 깨지면 조용히 링크 영역만 줄어들고 화면은 멀쩡해 보인다. 5 variant 전부 카드 3개 지점(좌상단·중앙·우하단)이 `/events/{id}` 로 히트되는지 브라우저에서 확인했다.

**액션 버튼은 `action` prop 으로 비웠다.** `entities` 는 `features` 를 import 할 수 없으므로(FSD) 찜(`features/event-like`)·신청(`features/event-apply`) 버튼을 카드가 직접 만들 수 없다. 놓이는 **자리만** variant 가 정한다 — `feature`/`ratio` 썸네일 우상단, `compact` 우측 열, `list` 우하단(6.5), `sheet` 하단 가격 옆(6.6).

**번복 조건**: 카드 안에 링크가 둘 이상 필요해지면(예: 주최사명을 눌러 주최사 페이지로) stretched link 는 성립하지 않는다. 그때는 카드를 링크로 감싸지 않고 제목만 링크로 두는 쪽으로 되돌린다.

## 4.17 카드 조각은 타이포를 부모에 위임한다 (2026-09-02)

`CapacityText`·`PriceText`·`BirthYearRangeText` 는 **크기·색 기본값을 갖지 않는다.** `className` 을 그대로 붙이고 폰트는 부모에서 상속받는다.

**왜**: `cn()` 은 문자열 결합만 하고 Tailwind 클래스 충돌을 해결하지 않는다(알려진 부채). 조각에 `text-[12px]` 를 박아두면 `list` 는 12px, `sheet` 는 16px 로 쓰고 싶을 때 `text-[16px]` 를 넘겨도 **어느 쪽이 이길지 클래스 순서가 아니라 스타일시트 순서가 정한다.** 화면마다 다르게 깨지고 원인이 안 보인다.

세리프(`Numeric`) 래핑은 반대로 **조각이 강제한다.** 가격·정원 숫자에 세리프를 쓰는 것은 디자인 규칙(2.2)이지 호출자의 선택이 아니다.

**번복 조건**: `tailwind-merge` 를 도입하면 이 제약이 사라진다. 그때 조각에 기본 타이포를 되돌려도 된다.

## 4.18 `thumbnailUrl` 을 nullable 로 바꾼다 (기능정의서 12장 갱신) (2026-09-02)

`EventSummary.thumbnailUrl: string` → `string | null`. 12장도 같이 고쳤다.

**왜**: 주최사 등록은 **동의 기반**이고 동의 범위가 `정보 등록` / `이미지 사용` / `참석자 리스트 표시` 셋으로 나뉜다(7.2). 정보 등록만 허락하고 이미지는 주지 않는 주최사가 실재한다. 즉 **이미지가 없는 것은 오류가 아니라 정상 경로**다. `string` 으로 두면 화면이 "URL 은 항상 있다"를 전제로 짜이고, 빈 문자열이나 존재하지 않는 경로 같은 센티넬이 슬그머니 생긴다.

이미지가 없다고 소개팅을 목록에서 빼지 않는다 — 그러면 컨택이 덜 진행된 주최사의 소개팅이 통째로 사라지고, 그게 곧 MVP1 카탈로그의 상당 부분이다.

`EventThumbnail` 이 두 갈래를 같은 대체 표시로 떨어뜨린다.

- `null` — **요청 자체를 보내지 않는다**
- 로드 실패(원본이 내려감·URL 깨짐) — `onError` 로 받는다

대체 표시는 회색 빈 상자가 아니라 **주최사 이름으로 톤을 정한 색 블록**이다. 이미지 없는 카드가 목록에 여러 장 이어질 때 전부 같은 상자면 서로 구분되지 않는다. 이름 → 톤 매핑은 순수 함수라 서버·클라이언트가 같은 답을 내고(하이드레이션 안전), 같은 주최사는 어디서나 같은 색이다. 폭이 좁은 썸네일(92px 이하)은 컨테이너 쿼리로 이름을 숨기고 마크만 남긴다.

**남은 것**: `public/mock/` 이 없어 나머지 목 7건의 `/mock/*.jpg` 가 `_next/image` 400 을 낸다(건당 srcset 3회). 대체 표시가 받아내므로 화면은 멀쩡하지만 콘솔 노이즈가 남는다. 실 이미지가 들어오면 사라진다.

**번복 조건**: 이미지 없는 건이 실제로는 거의 없다고 드러나면 `null` 을 없애는 대신 등록 시 기본 이미지를 채우는 쪽이 낫다. 그 판단은 Phase 6 등록 폼에서 한다.

## 4.19 평점은 회차가 아니라 주최사에 쌓인다 (2026-09-02)

`EventSummary.rating`·`reviewCount` 를 **삭제**하고, 평점의 귀속 단위를 주최사로 올린다. 배달 앱의 가게 리뷰와 같은 구조다 — **후기는 회차에 대해 쓰지만 주최사에 쌓인다.**

| 배민 | MeetMap |
| --- | --- |
| 가게 = 반복 주체 | 주최사 = 반복 주체 |
| 주문 = 1회성 | 소개팅 회차 = 1회성 |
| 리뷰는 주문에 대해 쓰지만 가게에 쌓인다 | 후기는 회차에 대해 쓰지만 주최사에 쌓인다 |

**왜 — 회차 평점은 정의상 성립하지 않는 값이었다.**

1. **소비 시점에 값이 없다.** 사용자가 평점을 보는 시점은 그 회차가 **열리기 전**이다. 회차는 1회성이므로 신규 회차는 예외 없이 후기 0건이다. 즉 `EventSummary.rating` 은 항상 0이거나, 0이 아니라면 그 데이터가 틀린 것이다. 목 데이터에서 `evt-003` 만 후기 0건으로 표시해 뒀는데 **실은 8건 전부가 0이어야 했다.**
2. **표본이 없다.** 정원 7:7 = 14명이고 참여 인증까지 거쳐야 후기를 쓰므로 회차당 2~4건이 현실이다. 3명이 쓴 4.0 은 정렬 축으로도 비교 축으로도 못 쓴다.
3. **주최사가 반복 주체다.** 회차가 쌓이면 표본이 는다. 그리고 처음 신청하는 사람의 실제 질문은 *"이 회차가 좋은가"* 가 아니라 **"이 주최사 믿을 만한가"** 다. 흩어진 것을 모아 비교하게 해주는 제품에서 비교 축이 주최사로 올라가는 것이 자연스럽다.

**이게 P1-1 의 관찰을 설명한다.** 카드 5종 어디에도 평점을 넣지 못한 것은 표시 항목 누락이 아니라 **모델이 그 자리에 줄 값이 없어서**였다.

**따라오는 구조 변경.**

- `provider: string` → `{ id, name }`. **id 없이는 주최사 페이지 링크도 후기 귀속도 불가능하다.** 이게 가장 큰 변경이고 카드·상세·비교함이 전부 이 필드를 지나간다
- `entities/provider/` 신설. **단 `entities/event` 는 이걸 import 할 수 없다**(FSD 동일 레이어 금지) — event 가 쓰는 최소 형태 `{ id, name }` 는 event 슬라이스가 직접 정의한다. `EventCardViewer` 와 같은 패턴이다
- `EventSummary` 는 평점을 나르지 않는다. **카드에 평점을 그리지 않기로 했으므로**(사용자 결정) 목록 응답이 평점을 실을 이유가 없다. 평점이 필요한 화면은 상세와 주최사 페이지뿐이고 둘 다 단건 조회다
- 후기 목록 라우트 분리 TBD 가 이걸로 **해소**됐다 — 회차별 후기 목록은 만들지 않는다(표본 부족으로 평점 요약·분포 막대·인기 태그가 전부 무의미해진다)

**부수 효과 — 등록 동의의 협상 카드.** 현재 성장 단계는 ①운영자가 컨택해 대신 등록하는 단계고, 주최사가 MeetMap 에 등록할 이유는 유입 하나뿐이다. "당신 소개 페이지를 만들어 드립니다, 후기가 거기 쌓입니다"가 컨택에서 내밀 카드가 된다. 4.18(이미지 동의)과 같은 맥락이다.

**번복 조건**: 회차별 편차가 주최사 편차보다 크다고 드러나면(같은 주최사인데 회차마다 만족도가 크게 갈리면) 회차 평점을 되살려야 한다. 그때도 `Review.eventId` 가 남아 있으므로 **재집계가 가능하다** — 원본을 회차 단위로 저장하는 이유가 이것이다.

## 4.20 평점 정렬은 하드 컷이 아니라 베이지안 보정을 쓴다 (2026-09-02)

탐색 정렬에 `평점 높은순`(`sort=rating`)을 추가한다. 정렬 키는 원본 평균이 아니라 **보정값**이다.

```
ratingScore = (C × m + 평점합) / (C + n)     C=10(신뢰 상수), m=4.3(전체 평균)
```

**왜 하드 컷이 아닌가.** `후기 5건 이상만 정렬 대상`으로 자르면 절벽이 생긴다 — 4건짜리는 목록에서 빠졌다가 5번째 후기가 달리는 순간 5.0 으로 1위에 점프한다. 보정식은 후기 3건·평균 5.0 을 `4.46` 으로, 후기 50건·평균 4.6 을 `4.55` 로 계산해 **표본이 적은 만점이 표본 많은 고득점을 이기지 못하게** 한다.

**이게 정렬 도입의 반대 근거를 없앴다.** 원래는 "평점순을 열면 신규 주최사가 구조적으로 맨 아래 깔린다"고 반대했는데, 보정식에서 **후기 0건 주최사는 `m` 을 그대로 받아 맨 아래가 아니라 중간에 놓인다.** 하드 컷이었다면 맨 아래였다.

**표시 임계는 별개로 5건이다.** 5건 미만이면 평점 숫자를 숨기고 `후기 N건` 만 쓴다. 5건에서도 한 사람이 평점을 0.8 흔들지만(4.6 → 3.8), 회차당 후기가 2~4건이라 10건을 요구하면 주최사 대부분이 3~4회차를 치를 때까지 평점이 안 뜬다 — 기능이 사실상 죽는다. 대신 **평점과 건수를 항상 같이 쓴다**(`4.6 (23)`).

**대가 두 가지를 알고 쓴다.**

- **표시 평점과 정렬 순위가 어긋날 수 있다.** 화면은 원본 평균, 정렬은 `ratingScore`. `ratingScore` 는 **화면에 절대 노출하지 않는다** — 두 숫자가 같이 보이면 설명할 수 없다
- **같은 주최사 회차가 뭉친다.** 목록은 소개팅인데 정렬 키는 주최사 값이라, 평점 1위 주최사가 회차를 5건 올리면 상위 5개가 그 주최사다. 지금은 2차 정렬(개최일 가까운 순)만 두고 상한은 걸지 않는다 → 5장

**되돌리기 쉬운 결정이다.** 프론트는 `ratingScore` 를 받아 정렬만 하므로 `C`·`m` 이 바뀌어도 화면 코드는 안 바뀐다.

## 4.21 평점 산식을 `entities/provider` 가 아니라 `shared/lib` 에 둔다 (2026-09-02)

`ratingScore`·`canShowRating`·`applyDisplayThreshold` 는 **주최사의 규칙인데 `shared/lib/rating.ts` 에 있다.** 상수(`RATING_PRIOR_WEIGHT`·`RATING_PRIOR_MEAN`·`REVIEW_DISPLAY_MIN_COUNT`)도 이미 `shared/config` 에 있다.

**왜**: 탐색 정렬(`sort=rating`)은 **소개팅 목록**을 주최사 평점 순으로 세운다. 즉 `entities/event` 의 목 구현이 주최사 산식을 써야 하는데, entity 끼리는 서로를 참조할 수 없다(FSD 동일 레이어 금지). 두 슬라이스가 함께 볼 수 있는 자리는 `shared` 뿐이다.

대안 세 가지를 봤고 전부 더 나빴다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 산식을 양쪽에 복사 | 목록 정렬과 주최사 페이지의 순위가 어긋난다. 그런데 **화면에서는 티가 안 난다** — 정렬은 목록에서만 보이고 평점은 상세에서만 보인다 |
| `EventProviderRef` 에 `ratingScore` 를 실어 보낸다 | 화면에 절대 노출하면 안 되는 값(4.20)을 화면이 받는 타입에 넣게 된다 |
| 이벤트 목 데이터에 정렬 키를 하드코딩 | 상수를 고치면 조용히 어긋난다 |
| FSD 의 **교차 참조**(`entities/provider/@x/rating.ts`)로 event 에만 좁게 여는 것 | 코드 위치가 "주최사의 규칙"임을 드러내는 장점은 있으나, ESLint 에 슬라이스별 예외를 관리해야 하고 예외를 한 번 열면 다음 요청이 따라온다. **평점 외의 축(진행자 등)이 `shared` 에 쌓이기 시작하면 그때 재검토한다** (2026-09-03 리뷰 제안) |

`shared/config` 에 도메인 마스터를 둔 선례(4.2)와 같은 성격이다 — 여러 레이어가 같은 답을 봐야 하는 규칙은 아래로 내린다.

**남은 중복 하나 — 이제 테스트가 막는다**: 목 주최사의 **원본 평균·후기 수**는 `entities/provider/mock/providers.ts` 와 `entities/event/mock/events.ts` 양쪽에 있다. 구조가 강제한 중복이고(entity 간 import 금지) 실서버에서는 조인 한 번이면 될 일이다.

처음에는 서로를 가리키는 주석으로만 막았는데, **주석은 방어책이 아니다.** 2026-09-03 리뷰에서 빠져나갈 구멍을 찾았다 — 레이어 경계 규칙은 `src/{shared,entities,features,widgets}/**` 에만 걸리고 `app` 은 대상에서 빠져 있다(`eslint.config.mjs` 의 `layerBoundaryRules`). 그래서 `src/app/_consistency/providerRating.test.ts` 가 **두 entity 의 공개 API 로만** 교차 검증한다. `_` 폴더는 App Router 가 라우트로 잡지 않는다.

임계 미만 주최사(후기 5건 미만)는 양쪽 다 `rating` 이 `null` 이라 값 비교로는 평균 어긋남이 안 잡힌다. 그래서 **탐색의 평점 정렬 순서가 주최사 `ratingScore` 내림차순과 일치하는지**를 함께 본다 — 보정값이 그 평균에서 나오므로 순서가 대신 잡아준다. 변이 4종(후기 수·평점·임계 미만 평균·이름)으로 전부 검출을 확인했다.

`widgets/provider-profile` 이 생기면(P5-4) 그쪽이 두 포트를 조립하는 자리이므로 테스트도 같이 옮긴다.

**번복 조건**: 평점이 주최사 외에 다른 축(예: 진행자)에도 붙게 되면 `shared` 에 두는 것이 부담스러워진다. 그때는 `entities` 위에 얇은 도메인 레이어를 두는 쪽을 검토한다.

## 4.22 카드 변형은 분기가 아니라 레이아웃 컴포넌트로 나눈다 (2026-09-02)

`EventCard` 를 파일 하나(함수 202줄, `if/if/if/return` 4갈래)에서 디렉터리로 바꿨다.

```
EventCard/
  index.tsx      변형 → 레이아웃 표 + 공통 기본값(링크 대상·게스트 판정). 함수 20줄
  types.ts       Props · 레이아웃 계약
  parts.tsx      CARD_SHELL · CardTitle(stretched link) · CardPrice · EligibilityBadge
  FeatureCard.tsx / RatioCard.tsx / CompactCard.tsx / ListCard.tsx / SheetCard.tsx
```

**왜**: 202줄 함수는 읽을 수도 리뷰할 수도 없고, 무엇보다 **변형 추가가 기존 코드를 여는 일**이었다(OCP 위반). 지금은 파일 하나 추가 + `LAYOUTS` 표 한 줄이다.

**어디에 무엇을 두는지의 경계**가 이 구조의 핵심이다.

| 자리 | 담는 것 |
| --- | --- |
| `index.tsx` | **어느 변형에나 같은 것** — 기본 링크 대상, 게스트 판정 |
| `parts.tsx` | **변형이 달라도 규칙이 같은 것** — 링크 히트 영역, 가격 기준, 자격 배지 문구 |
| 각 레이아웃 | **변형마다 다른 것** — 크기·배치·표시 항목 |

`feature` 와 `ratio` 는 배지 줄과 정원 표기만 달라서 `VerticalCardFrame` 을 공유한다. 두 변형이 더 갈라지면 프레임을 나누면 되고, 그때도 다른 세 레이아웃은 건드리지 않는다.

**주의 — `parts.tsx` 에 크기를 넣지 않는다.** 넣는 순간 레이아웃이 그 크기를 오버라이드하려 들고, `cn()` 이 Tailwind 충돌을 해결하지 못해 조용히 깨진다(4.17 과 같은 함정).

**번복 조건**: 변형이 3개 이하로 줄고 서로 거의 같아지면 파일을 나눈 값이 없다. 그때는 되돌린다.

## 4.23 홈은 마감된 소개팅을 배지로 표시하지 않고 아예 거른다 (2026-09-04)

`getHomeFeed` 의 **세 섹션 모두 `status: '신청 가능'` 만** 내린다. 그리고 `feature` 카드에서 상태 배지를 뺐다. 기능정의서 5.3 도 함께 고쳤다.

**발단**: 상태 배지가 `feature`·`list`·`sheet` 에만 있고 `ratio`·`compact` 에는 없었다(5.3 표시 항목에 없어서). 홈 섹션 B·C 에서 **마감된 소개팅이 신청 가능해 보인다.** 목 데이터의 `evt-007` 은 인기 2위라 홈 첫 화면에 실제로 떴다.

| 대안 | 왜 안 되나 |
| --- | --- |
| `ratio`·`compact` 에 상태 배지를 추가 | 표시 항목이 늘어 카드가 빽빽해지고, 무엇보다 **홈에 마감 건이 있어야 할 이유를 답하지 못한다.** 배지는 증상에 대한 처치다 |
| 섹션 A(인기)만 거른다 | 세 섹션의 규칙이 달라진다. "홈에 뜬 건 신청할 수 있다"가 성립하지 않으면 배지를 봐야 하고, 그러면 첫 번째 대안으로 돌아간다 |
| 마감 건을 흐리게(dim) 표시 | 색·명도만으로 상태를 말하게 된다(15장 위반). 라벨을 붙이면 결국 배지다 |

**왜 거르는 쪽인가**: 홈에는 **상태 필터가 없다**(5.4 — 필터는 탐색 한 곳뿐). 걷어낼 수단이 없는 자리에 걷어내야 할 것을 놓지 않는다. 마감 회차를 보고 싶으면 탐색의 상태 필터를 풀면 되고, 그쪽 기본값은 `ALL` 이라 아무것도 잃지 않는다.

**부수 효과 하나 — 배지를 뺀 것.** 세 섹션이 전부 모집 중이면 배지는 늘 같은 값이다. 같은 값만 찍히는 배지는 정보가 아니라 "없는 경우도 있나 보다"라는 잘못된 기대를 만든다.

⚠️ **`compact` 는 건드리지 않았다.** 찜 목록과 공용이고(14.1), **찜 목록에는 상태 배지가 필요하다**(9장) — 찜한 소개팅은 마감돼도 목록에서 사라지지 않기 때문이다. 홈은 마감을 받지 않으므로 홈에서는 그려지지 않는다. 배지는 P2-8(찜 목록)에서 넣는다.

**거르는 주체는 서버다 (2026-09-04 리뷰 반영).** 이 규칙은 처음에 목 구현 안에만 있었다 — `HomeFeed` 타입에도 `EventApi` 계약에도 기능정의서 13장에도 "모집 중만"이라는 말이 없었다. 그러면 실 API 로 전환한 뒤 서버가 마감 건을 섞어 내려도 **아무도 계약 위반으로 인지하지 못한다.** 홈에는 상태 배지도 없으니 화면에도 안 보인다.

세 곳에 못 박고 방어선을 하나 더 뒀다.

| 자리 | 무엇을 |
| --- | --- |
| `EventApi.getHomeFeed` · `HomeFeed` 독스트링 · 기능정의서 13장 홈 행 | "세 섹션 모두 모집 중만 — 서버 책임"을 명시 |
| `api/eventApi.ts` 의 `openSectionsOnly` | 실 API 응답에 같은 `isOpen` 을 한 번 더 태운다. **잘못 보여주는 것보다 덜 보여주는 쪽**을 고른 것이다 |
| `HOME_SECTION_KEYS` (`model/types.ts`) | 섹션 키 목록을 한곳에. `HomeFeed` 가 이 유니온을 `extends` 하므로 섹션이 늘면 타입이 새 필드를 요구하고, 방어 필터·화면 표·테스트가 함께 걸린다 |

목 구현은 `openSectionsOnly` 를 쓰지 않는다 — 거기서는 **자르기 전에** 걸러야 섹션이 6건을 채운다(서버가 할 일과 같다). 두 자리가 같은 `isOpen` 을 보므로 규칙이 두 벌이 되지는 않는다.

**이 패턴을 두 번째로 쓴 자리는 `providerRatingDisplay` 다** — 언제 이 형태를 쓰는지는 4.35 가 정한다.

**번복 조건**: 마감 회차에도 사용자가 할 일이 생기면(대기 신청, 다음 회차 알림 등) 홈에서 감추는 것이 손해가 된다. 그때는 거르기를 풀고 `ratio`·`compact` 에 상태 배지를 넣는다 — 위 첫 번째 대안으로 되돌아가는 것이다.

## 4.24 하단 탭의 두 번째는 `지도` 가 아니라 `탐색` 이다 (2026-09-05)

하단 4탭을 `홈 / **탐색** / 찜 / 마이` 로 바꿨다. href 는 `/explore?view=list` 이고 **아이콘(핀)은 그대로 뒀다.**

**발단**: 홈의 `전체보기 >` 3개가 전부 `view=list` 로 보내는데(5-8), 도착하면 하단 탭은 `지도` 가 켜졌다. 사용자가 누른 적 없는 탭이 활성화된 화면에서 리스트를 본다.

| 대안 | 왜 안 되나 |
| --- | --- |
| `지도` 탭 유지 | 라벨과 화면이 계속 어긋난다. 홈에서 탐색으로 가는 **주 경로 3개 전부**에서 매번 발생한다 |
| 탭을 5개로(`홈/탐색/지도/찜/마이`) | 2.1 의 4탭 셸 전제가 깨지고, 430px 에서 탭 하나가 86px 로 좁아진다 |
| 활성 판정을 `view=map` 일 때만으로 좁힌다 | 리스트에서는 **아무 탭도 안 켜진다** — 더 나쁘다 |

**왜 `탐색` 인가**: 하단 탭은 앱의 **최상위 영역**이고, 지도와 리스트는 서로 다른 영역이 아니라 **같은 목록을 보는 두 방식**이다(6.2 뷰 토글). 렌즈를 탭으로 올리면 위계가 어긋난다 — `지도` 탭에서 리스트로 토글하면 화면과 탭이 서로 다른 위치를 말한다. 필터·정렬·비교도 전부 리스트의 기능이라 **지도는 탐색의 부분집합**이다.

**지도를 뺀 것이 아니다.** 진입점은 둘 남는다 — 홈의 지도 프로모 카드(5-6, `내 주변 3km` 원탭)와 탐색 상단의 뷰 토글. 아이콘을 핀으로 유지한 것도 그 연상을 남기기 위해서다.

덧붙여 **Phase 1 에는 지도가 아예 없다**(P3-1). 탭에 `지도` 를 두면 그때까지 빈 화면으로 가는 탭을 하나 주는 셈이었다.

**번복 조건**: 로그에서 지도 사용이 리스트와 대등하게 나오거나, 지도에만 있는 기능(주변 알림 등)이 생겨 **독립된 목적지**가 되면 그때 5탭 또는 탭 교체를 재검토한다. 그 경우에도 뷰 토글은 남긴다.

## 4.25 URL 은 기본값을 싣지 않는다 — `eligibleOnly` 만 예외다 (2026-09-05)

탐색 필터는 URL 이 원본이다(2.4). 그래서 **직렬화가 계약**이고, 규칙은 두 줄이다.

1. **기본값은 싣지 않는다.** URL 은 공유·북마크되므로 짧아야 하고, 무엇이 실제로 걸린 조건인지 눈으로 읽혀야 한다.
2. **`eligibleOnly` 만 `=0` 을 명시한다.** 로그인 기본이 ON 이라(6.4) "파라미터 부재 = 꺼짐"으로 읽으면 **기본값을 표현할 방법이 없다.** 부재 = 기본, `=0` 이 명시적 OFF, `=1` 은 기본과 같아 압축된다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 모든 축을 항상 명시(`when=ALL&slot=ALL…`) | 공유 링크에서 무엇이 실제 조건인지 안 읽힌다. 조건 0개인 URL 과 5개인 URL 이 같은 길이가 된다 |
| 자격 토글 기본값을 OFF 로 바꾼다 | 6.4 의 "출생연도로 **처음부터 걸러 보여주고** 넓히고 싶을 때 끄게 한다"가 무너진다. 92년생에게 `95~02년생 전용` 을 먼저 보여주게 된다 |
| 칩 줄에서 자격 칩의 ✕ 를 없앤다 | 6.2 가 요구하는 개별 해제를 못 한다. 넓혀 볼 수단이 사라진다 |

⚠️ **여기서 밟기 쉬운 함정**: 칩 ✕ 해제를 `URLSearchParams.delete("eligibleOnly")` 로 짜면 파라미터가 사라져 **기본값(ON)으로 되살아난다.** 해제는 `eligibleOnly: false` 를 세팅해 `serializeExploreParams` 를 거쳐야 한다. P1-5c 가 이걸 우회하면 그대로 깨진다.

같은 이유로 **알 수 없는 값은 에러가 아니라 기본값으로 떨어뜨린다** — URL 은 사용자가 손으로 고칠 수 있고, 오타 하나로 빈 화면을 주지 않는다. 마스터 검증을 한 축이라도 빠뜨리면 조용한 빈 화면이 되는 것을 `area` 에서 실제로 겪었다(2026-09-05 코드리뷰).

**번복 조건**: 자격 토글의 기본값이 OFF 로 바뀌면 이 예외 자체가 사라진다 — 그때는 규칙 1만 남는다.

## 4.26 `초기화` 가 둘이고 지우는 대상이 다르다 (2026-09-05)

이름이 같아서 한쪽 규칙을 다른 쪽에 옮겨 붙이기 쉽다. 둘은 **다른 사양**이다.

| 버튼 | 지우는 것 | 남기는 것 | 근거 |
| --- | --- | --- | --- |
| 칩 줄의 `초기화` | 화면에 떠 있는 칩 전부 — **자격 포함** | **시간대**·지역·정렬 | 6.2 "표시 대상 전부 해제(시간대·지역은 유지)" |
| 시트의 `초기화` | 2·3층 전부 — **시간대 포함** | **자격**·지역·정렬 | 6.4 "1층 자격 토글은 초기화 대상이 아니다" |

**어긋나 보이는데 맞다.** 칩 줄은 "지금 보이는 것을 치운다"가 규칙이라 자격 칩도 대상이고, 시간대는 애초에 칩이 아니라(상단 칩 줄의 몫) 대상이 아니다. 시트는 "층"이 규칙이라 2층인 시간대는 대상이고, 1층 자격은 개인 조건이지 필터가 아니라서 대상이 아니다. **각자 자기 화면에서 보이는 것만 되돌린다**는 점에서는 같은 원칙이다.

`clearAppliedFilters` / `resetSheetFilters` 로 이름을 갈라 두고, **서로의 차이를 단언하는 테스트**를 붙였다(`시트의 초기화는 2층이라 시간대를 되돌린다 — 칩 줄 쪽과 반대다`). 한쪽을 고칠 때 다른 쪽이 따라가지 않게 하려는 것이다.

**번복 조건**: 상단 시간대 칩 줄이 없어지고 시간대가 칩 줄로 내려오면 두 버튼의 대상이 같아진다. 그때 하나로 합친다.

## 4.27 게스트 게이트는 파싱 한 곳뿐이고, 화면은 키의 유무로 읽는다 (2026-09-05)

`eligibleOnly`·`maxPrice` 는 서버가 인증 주체로 해석하는 축이라 게스트에게는 의미가 없다(6.1). `parseExploreParams` 는 게스트에게 **그 키를 아예 만들지 않는다**. P1-5 는 그 규칙을 화면에서 다시 판정하지 않고 **키의 유무를 그대로 읽는다**(`hasViewerAxes`).

| 대안 | 왜 안 되나 |
| --- | --- |
| 시트·칩 줄이 세션(`isGuest`)을 따로 받는다 | 게이트가 세 곳이 된다. 셋이 같은 답을 낸다는 보장이 없고, 언젠가 한쪽만 고쳐진다 |
| `maxPrice` 유무로 판정한다 | 상한을 안 건 로그인 사용자도 `undefined` 라 게스트와 구분되지 않는다. `eligibleOnly` 는 로그인 사용자에게 **항상 boolean** 이라(부재 = 기본 ON) 이 축만이 판별에 쓸 수 있다 |

같은 값이 카드까지 내려간다. `EventCard` 의 `eligibleOnly` 프롭이 `내 나이대 아님` 배지를 그릴지 정하고(6.5), 판정은 `marksIneligible` 한 곳이 한다 — `undefined`(축 없음·게스트) / `true`(켜짐, 남은 건이 전부 자격을 만족하므로 표시하지 않는다) / `false`(꺼짐, 표시한다).

⚠️ **조건에서 뺀 축은 키 자체를 지운다.** `{ ...query, maxPrice: undefined }` 는 키를 만들어 버리고, 그러면 게스트 조건 객체에 인증 축이 생겨 이 판정이 무너진다. 직렬화가 `undefined` 를 걸러 주기 때문에 **URL 로는 티가 안 나고**, 왕복 테스트로도 안 잡힌다 — 조건 객체를 직접 보는 테스트를 따로 뒀다(변이로 확인).

**번복 조건**: 프로필(P2-4)이 붙어 `viewer` 가 실제 값이 되면, 자격 판정의 입력이 세션이 아니라 프로필이라는 것이 코드에서도 드러난다. 그때도 게이트는 파싱 한 곳으로 유지한다 — 늘리려면 이 항목을 먼저 뒤집는다.

## 4.28 축별 건수는 현재 필터를 반영하고, 못 세면 건수를 포기한다 (2026-09-05)

시간대 칩(6.2)과 지역 시트(6.3)는 **건수 0인 값을 노출하지 않는다.** 지역 시트는 `N곳` 을 직접 그리기까지 한다. 그 건수를 무엇 기준으로 세느냐가 P1-5b 의 첫 갈림길이었다.

**현재 걸린 다른 필터를 반영한다.**

| 대안 | 왜 안 되나 |
| --- | --- |
| 전체 기준 고정 건수 | 6.3 이 "필터 시트와 별개 진입점"이라는 서술에는 더 맞고 목록도 안 흔들린다. 그러나 `소수정예` 를 걸어둔 사용자에게 `강남구 3곳` 을 보여주고 눌렀더니 0건이면 **건수가 거짓말**이 된다. 같은 화면의 시간대 칩이 이미 필터를 반영하고 있어 두 컨트롤이 다르게 동작하는 문제도 생긴다 |

**건수 UI 가 붙는 축마다 스캔이 하나씩 는다.** 지금은 시간대·지역 둘이라 둘이고, 분위기(6.4)나 동 단위 `area` 에 건수를 붙이면 셋이 된다. 규칙은 그대로 확장된다 — 새 축도 **자기 축만 비우고** 나머지 조건은 그대로 둔다. 정렬(`sort`)은 결과 집합을 바꾸지 않으므로 이 규칙 밖이다.

**자기 축만 푼다 — 그래서 스캔이 둘이다.** 시간대 건수는 `slot` 만 풀고 지역은 그대로, 지역 건수는 `district` 만 풀고 시간대는 그대로 둔다. 한 번만 긁어 둘 다 만들면 축이 서로를 못 본다 — `district=MAPO` 인데 시간대 건수를 전지역으로 세면 `오전` 칩이 떠 있는데 눌러서 0건이 나온다. 반대로 자기 축을 안 풀면 고른 값 말고는 전부 0이 되어 목록이 한 줄로 줄어든다.

**세는 방법은 긁어와 버킷팅이다** (`api/exploreFacets.ts`). 목록 응답에 패싯 카운트가 없어서다. P1-5 는 슬롯마다 `totalCount` 만 받는 방식(조회 4회)이었는데, 구는 25개라 같은 방식이면 조회 25회가 된다. 지금은 **스캔 2회**다.

| 방식 | 조회 수 | 페이로드 | 판단 |
| --- | --- | --- | --- |
| 값마다 `limit: 1` | 4 + 25 | 상수 | 구까지 오면 감당이 안 된다 |
| **긁어와 버킷팅** | **2** | 조건에 맞는 전건 | **채택.** MVP1 은 서울 단일 도시라 전건이 작다 |
| 서버 `facets` | 1 (목록에 실려 온다) | 최소 | **근본 해결.** 백엔드가 생기면 이쪽이다 |

⚠️ **넘긴 것을 로그로 남긴다.** 이 신호가 없으면 서버 패싯이 필요해진 시점을 아무도 모른다 — 화면은 고장 나지 않고 "전부 노출 + 건수 없음"으로 조용히 굳어서, 사용자 문의로만 드러난다. `scan()` 이 `null` 을 돌릴 때 `console.warn` 한 줄을 남기고, 관측 도구가 생기면 그 자리를 바꾼다 (PR #25 리뷰).

⚠️ **두 축은 따로, 그리고 지역이 먼저 죽는다.** 각 축의 스캔 크기는 *자기 축만 지운* 조건의 건수다 — 구를 좁혀도 지역 스캔은 좁아지지 않는다(그 축을 지우고 세니까). 그래서 카탈로그가 커지면 **지역 건수가 먼저** 사라진다(시간대를 고른 상태라면 반대). 한쪽만 `null` 인 것이 정상이고, 로그가 어느 축인지 말해야 하는 이유도 이것이다 (PR #25 2차 리뷰).

**선택된 구의 건수만은 스캔이 죽어도 그린다.** 그 값은 화면 결과 수와 같아서(목록이 이미 그 구로 걸러져 있다) 스캔과 무관하게 정확히 안다. 이걸 안 하면 `0곳` 이 **가장 필요한 순간에** — 왜 비었는지 설명해야 할 때 — 사라진다.

⚠️ **못 셌으면 건수를 내놓지 않는다.** 스캔 상한(`SCAN_LIMIT`)을 넘기면 버킷이 조용히 실제보다 작아져 **있는 구가 목록에서 빠지고 `N곳` 이 거짓말을 한다.** 그래서 넘친 축은 `null` 로 돌려 화면이 전부 노출하고 건수를 감추게 했다 — 침묵하는 오답보다 "못 셌다"가 낫다. 이 상한에 닿는 시점이 곧 서버 패싯이 필요해지는 시점이다.

**실 API 전환 때 같이 볼 것 하나 — 그리고 이건 아래 번복 조건이 덮지 못한다.**

"선택된 구의 건수 = 화면 결과 수" 등식은 목록 조회와 패싯 스캔이 **같은 스냅샷을 본다**는 전제에 기댄다. 화면 한 번에 요청이 **셋**이다 — 목록(`getList`) · 시간대 스캔 · 지역 스캔. 목 데이터는 불변이라 셋이 항상 같은 스냅샷을 보지만, 실 API 에서는 그 사이 회차가 마감·취소될 수 있어 **근사치로 격하된다.** 같은 화면에 두 숫자가 어긋나 보일 수 있는 유일한 경로다.

⚠️ **`exploreFacets` 내부만 갈아끼워도 이 문제는 남는다.** 아래 번복 조건은 *건수를 세는 방법*(스캔+버킷팅 → 서버 패싯)에 대한 약속이고, *목록과 패싯이 한 요청·한 트랜잭션 안에서 이뤄지는가*는 **별개의 축**이다. 서버 패싯으로 갈아탄 뒤에도 `page.tsx` 가 목록과 패싯을 따로 부르면 시간차는 그대로다 — **요청을 하나의 계약으로 묶을지(예: 응답에 `items` 와 `facets` 를 함께), 아니면 서버가 스냅샷 일관성을 보장할지**를 그때 따로 정해야 한다.

**지금 코드로 굳히지 않는 이유** — ① 목 데이터가 불변이라 이 전제가 깨지는 경로를 **재현할 수단이 없다**(고쳐도 테스트로 증명이 안 된다) ② 묶는 모양은 사실상 백엔드 API 설계 결정이라, 백엔드가 없는 지금 프론트가 먼저 정하면 실 API 가 왔을 때 다시 뜯을 확률이 높다 ③ 목 레이어에서 합쳐 봐야 같은 동기 함수가 같은 배열을 보는 건 지금과 똑같다 (PR #25 3·4차 리뷰).

**번복 조건**: 서버가 `facets` 를 내려주면 `exploreFacets` 내부만 갈아끼운다 — 호출부(`ExploreFilterBar`)와 화면 규칙은 그대로다. 카탈로그가 커져 전건 스캔이 부담이 되면 그 전에 갈아타야 하고, 그 신호가 `null` 이 뜨기 시작하는 것이다.

## 4.29 뷰 토글은 P1-6 이 아니라 지도가 생기는 P3-1 에서 붙인다 (2026-09-07)

P1-6 은 이름이 `정렬 / 뷰 토글` 인데 **정렬만 붙였다.** 6.2 의 세그먼트 `리스트 / 지도` 는 P3-1 로 넘긴다.

**부딪힌 것**: `누르면 아무 일 없는 컨트롤은 만들지 않는다` — 홈의 옛 퀵 필터 칩을 그리지 않은 이유고(5.4), P1-4 가 컨트롤바를 비워둔 이유다. 지도는 P3-1 이라 `?view=map` 은 지금 `PhasePlaceholder`(🚧)로 떨어진다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 그냥 붙인다 (자리표시자로 간다) | 토글은 **상시 노출 크롬**이다. 탐색에 들어올 때마다 절반이 지키지 못할 약속을 하고 서 있는다. 필터 칩은 최악이라도 0건을 주지만 이건 매번 같은 🚧 다 |
| 붙이되 `지도` 를 비활성으로 | 4.24 가 `지도` 탭을 뺀 이유와 같은 문제를 모양만 바꾼 것이다. 비활성 컨트롤은 "언제 켜지나"에 답하지 못한다 |
| 토글 자리에 `지도는 곧 열려요` 안내 | 탐색 상단은 조건을 거는 자리다. 로드맵 고지가 낄 자리가 아니다 |

**4.24 가 이미 같은 판단을 했다.** "Phase 1 에는 지도가 아예 없다(P3-1). 탭에 `지도` 를 두면 그때까지 빈 화면으로 가는 탭을 하나 주는 셈이었다" — 탭에 적용한 근거가 토글에 안 적용될 이유가 없다. 오히려 토글은 탐색 화면 최상단이라 더 자주 눈에 띈다.

**진입점이 사라지는 것이 아니다.** 홈 지도 프로모 카드(5-6)가 그대로 있고, `view` 축은 이미 `parseExploreParams`/`serializeExploreParams` 에 있으며 `shared/ui/SegmentedControl` 도 이미 있다(문서 주석이 이 용도를 가리킨다). P3-1 은 컨트롤 하나를 얹기만 하면 된다 — **미루는 비용이 거의 0** 이라는 것이 이 결정의 실질적 근거다.

**대신 편도 문을 닫았다.** `?view=map` 은 홈 프로모 카드로 **이미 도달 가능**한데, `page.tsx` 가 자리표시자로 조기 반환해서 그 화면에는 필터바도 토글도 없다 — 리스트로 돌아가는 화면 내 경로가 하나도 없었다. 토글을 안 붙이기로 한 이상 그 출구는 이쪽이 만들어야 해서, 자리표시자에 `리스트로 보기` 링크를 하나 넣었다. 링크는 실재하는 화면으로 가므로 위 원칙과 부딪히지 않는다.

**번복 조건**: 지도(P3-1)가 붙는 순간 이 항목은 소멸한다 — 그때 토글을 붙이고, 자리표시자와 `리스트로 보기` 링크를 같이 지운다. 그 전에라도 지도 자리표시자가 **리스트가 아닌 다른 곳**에서도 값을 갖게 되면(예: 지도 준비 알림 신청) 다시 본다.

## 4.30 게스트의 가격 정렬은 화면이 아니라 파싱에서 막는다 (2026-09-07)

`sort=priceAsc|priceDesc` 는 **사용자 성별 기준값**을 쓴다(6.2). 게스트는 성별을 모르므로 축이 성립하지 않는다. 그래서 `parseExploreParams` 가 게스트에게는 이 두 값을 **기본값(`popular`)으로 떨어뜨린다.**

| 대안 | 왜 안 되나 |
| --- | --- |
| `select` 에서 옵션만 숨긴다 | 손으로 `?sort=priceDesc` 를 붙인 게스트가 남는다. 목록은 `MOCK_VIEWER` 의 성별로 정렬되고(실 API 라면 서버가 인증 주체 없이 해석해야 하고), `select` 는 자기 옵션에 없는 값을 받아 **아무것도 선택되지 않은 상태**로 뜬다 |
| 게스트면 정렬 축을 지운다 (`eligibleOnly` 처럼) | 정렬은 기본값이 있는 축이라 키를 지울 수 없다. 지우면 `undefined` 가 되어 호출부마다 `?? DEFAULT_SORT` 를 다시 써야 한다 |

**게이트는 여전히 파싱 한 곳이다** (4.27). 화면은 `hasViewerAxes` 로 가격 옵션을 그릴지만 정하고, 값의 유효성은 판정하지 않는다 — 두 곳이 되면 언젠가 한쪽만 고쳐진다. 알 수 없는 값을 기본값으로 떨어뜨리는 6.1 규칙의 연장이기도 하다: 게스트에게 `priceAsc` 는 **알 수 없는 값**이다.

⚠️ 이건 **보안 경계가 아니다** (4.12 와 같은 결). 서버가 인증 없는 요청에 가격 정렬을 어떻게 응답할지는 별도로 정해야 한다 — 프론트는 그 요청을 만들지 않을 뿐이다.

**번복 조건**: 로그인 없이도 성별을 받는 경로가 생기면(예: 온보딩에서 게스트에게 성별만 묻는다) 축이 성립하므로 이 예외가 사라진다.

## 4.31 목 데이터의 날짜는 절대값이 아니라 이번 주 월요일 기준 상대값이다 (2026-09-07)

`MOCK_EVENTS` 의 `date`·`createdAt` 을 `kstFromThisMonday(일수, 시각)` 으로 바꿨다. 기준은 `isThisWeek` 가 보는 것과 **같은 `weekRangeKst`** 다.

**발단**: 목 데이터에 `2026-09-04T19:30:00+09:00` 같은 절대 날짜와 "날짜가 과거로 밀리면 `when=THIS_WEEK` 가 0건이 되므로 그때 갱신한다"는 주석이 함께 있었다. 갱신하는 사람이 없었고, **2026-09-07(월) 주가 넘어가면서 실제로 깨졌다** — `THIS_WEEK` 집합이 `09-04·05·06`(SMALL 1건 포함) → `09-12·13`(둘 다 STANDARD)으로 갈아엎어져 `조건을 겹쳐 걸면 AND 로 좁힌다` 가 0건으로 실패했다. CI 가 빨간 채로 PR 을 막았다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 날짜를 앞으로 민다 | diff 8줄로 끝나지만 **다음 주에 정확히 같은 방식으로 또 깨진다.** 이번이 첫 번째였을 뿐이고, "그때 갱신한다"는 주석은 이미 한 번 실패한 장치다 |
| 테스트에서 시각을 고정한다 (`applyFilters` 에 `now` 주입) | 테스트는 영구히 안정되지만 **화면의 목은 계속 과거 날짜**다. 지금도 탐색 화면이 `이번 주` 필터로 9/12~13 을 내놓는데 카드에는 9/4 가 찍혀 있어 수동 QA 가 어긋난다. 테스트만 고치고 개발 경험은 그대로 두는 선택이다 |
| 목 데이터에서 날짜 축을 뺀다 | `when`·`slot`·`isThisWeek`·홈 `새로 등록된` 이 전부 날짜를 쓴다. 축을 빼면 그 화면들을 목으로 볼 수 없다 |

**같은 함수를 기준으로 쓰는 것이 핵심이다.** `weekRangeKst` 로 앵커를 잡으므로 `phase1-notes.md` 가 문서화한 `이번 주 5건 · 그 이후 3건` 배치가 **우연이 아니라 구조로 보장된다.** 전에는 "기준일 2026-09-02(수)" 라는 주석이 그 배치를 설명했고, 그 설명이 늙는 순간 데이터도 같이 늙었다.

**한 프로세스 안에서는 불변이다.** `MOCK_EVENTS` 는 모듈 로드 때 한 번 계산되고 목록 조회와 패싯 스캔이 같은 배열 참조를 본다 — 4.28 의 스냅샷 전제는 그대로다. `now` 를 매번 읽는 형태였다면 그 전제가 깨졌을 것이다.

**주가 바뀌면 다시 만든다** (PR #27 2차 리뷰). 목 날짜를 로드 시점에 굳히면 `isThisWeek` 는 호출마다 `new Date()` 를 읽으므로, **개발 서버를 켜둔 채 주가 넘어갔을 때** 굳은 배열이 새 주 기준으로 재평가되어 결과가 틀어진다. 그래서 `getMockEvents()` 가 **주를 키로 캐시**한다 — 같은 주 안에서는 같은 배열 참조라 4.28 전제가 그대로고, 주가 바뀌는 순간에만 새로 만들어 저절로 복구된다.

⚠️ **이 실패 모드는 빈 화면이 아니라 조용히 틀린 건수다.** 처음에는 "`THIS_WEEK` 가 통째로 0건이 되니 눈에 띈다"고 적었는데, 테스트를 짜 보니 **5건이 2건**이 됐다 — 굳은 날짜 중 `그 이후` 쪽(월+12·+13)이 새 주에 들어와 버리기 때문이다. 0건이 되려면 3주는 방치해야 한다. 화면이 비면 알아채지만 5건이 2건인 것은 아무도 못 알아챈다. **"눈에 띄는 실패라 문서화만 해도 된다"는 처음 판단이 틀렸고, 그래서 코드로 고쳤다.**

⚠️ **요청마다 재계산하지 않는 것이 핵심이다.** 그렇게 하면 목록 조회와 패싯 스캔이 서로 다른 배열을 받아 4.28 전제를 이 수정이 오히려 깨뜨린다. 남는 창은 **주 경계를 사이에 둔 두 호출** 하나뿐이고, 그건 멀티 인스턴스에서 콜드 스타트 시점이 갈릴 때와 같은 크기다 — 목을 여러 인스턴스에 띄우면 그때 다시 본다.

**이 캐시가 성립하는 전제는 셋이다** (PR #27 3차 리뷰). "읽기 전용" 하나가 아니다.

| 전제 | 지금 무엇이 지키나 |
| --- | --- |
| 아무도 배열을 제자리에서 바꾸지 않는다 | **타입**. `getMockEvents(): readonly Readonly<EventDetail>[]` 이라 `.sort()` 도 `event.isLiked = true` 도 컴파일 에러다 |
| 캐시 인스턴스를 화면에 그대로 넘기지 않는다 | **`detached` 얕은 복사**. 회차를 돌려주는 API 메서드 다섯이 전부 거친다. 아래 참조 |
| 검사와 대입 사이에 `await` 가 없다 | **동기 블록**. Node 가 싱글 스레드라 요청이 몰려도 끼어들 수 없다. 이 함수에 비동기를 들이는 리팩터가 유일한 파괴 경로다 |
| 이 함수를 무는 라우트가 정적 프리렌더되지 않는다 | **`force-dynamic` 과 동적 API**. 아래 참조 |

⚠️ **`readonly` 는 배열만 막고, 필드 변형이 더 위험하다** (PR #27 4차 리뷰). 개별 `EventDetail` 은 `applyFilters`·`applySort`·`paginateArray` 어디서도 복사되지 않아 **캐시가 들고 있는 그 인스턴스**가 그대로 흘러간다. 배열 재정렬은 순서만 틀어지지만 필드 대입은 데이터 자체가 틀어진다. `Readonly<EventDetail>[]` 로 올려 최상위 필드 대입을 컴파일 타임에 막았지만 이건 **얕고**(`event.mood.push(...)` 는 여전히 통과) **컴파일 타임뿐이며**(캐스트 하나면 뚫린다), 무엇보다 **포트 밖에서는 지워진다** — `EventApi.getDetail` 이 `EventDetail` 을 약속하므로 화면은 변형 가능한 타입으로 받는다.

그래서 **응답으로 나가는 회차는 전부 얕은 복사를 거친다**(`detached`). 실 HTTP API 는 응답마다 새 객체를 주므로 이쪽이 오히려 실서버에 가깝다.

> ⚠️ **여기서 한 번 틀렸다.** 처음에는 `getDetail` 만 복사하고 "캐시 객체를 화면에 넘기는 유일한 자리"라고 적었는데, 확인해 보니 `getHomeFeed`·`getList`·`getMapMarkers`·`search` **넷 다** 같은 참조를 넘기고 있었다 — 필터·정렬·페이지네이션이 배열만 새로 만들고 원소는 통과시키기 때문이다. 게다가 `isLiked` 는 `EventDetail` 이 아니라 **`EventSummary`** 에 있어서(12장) 상세보다 **목록 카드의 찜 버튼**(6.5, `ListCard` 에 자리가 이미 있다)이 먼저 그 코드를 만든다. P2-7 이 상세만 건드릴 것이라는 전제도 틀렸던 셈이다 (PR #27 5차 리뷰).
>
> 그래서 자리마다 판단하지 않고 **나가는 경로를 전부 한 함수로 통일**했고, 테스트도 메서드를 지목하는 대신 **회차를 돌려주는 메서드를 표로 훑는다**(빠진 메서드가 있으면 커버리지 단언이 먼저 깨진다).

⚠️ **얕은 복사다.** `mood`·`jobGroups`·`images` 같은 배열 필드는 여전히 공유한다 — 깊은 복사는 목 8건짜리 스캐폴딩에 과하다. **진짜 안전장치는 쓰기 경로를 불변 갱신으로 설계하는 것**이고 그건 타입이 강제할 수 없다.

⚠️ **`/design-system` 이 실제로 이 전제를 깨고 있었다.** 리뷰는 "나중에 정적 페이지가 붙으면 위험하다"고 미래형으로 짚었지만, 확인해 보니 그 페이지가 이미 `○ (Static)` 으로 프리렌더되면서 `eventApi.getList` 를 부르고 있었다 — **빌드한 주의 날짜가 HTML 에 굳어** `/explore` 와 다른 날짜를 그린다. 카드 경계값을 눈으로 확인하는 기준 페이지가 그러면 기준이 못 된다. `export const dynamic = "force-dynamic"` 을 붙였다. `/` 와 `/explore` 는 각각 `cookies()`·`searchParams` 를 읽어 이미 동적이라 손댈 것이 없다.

⚠️ **등록일(`createdAt`)의 일수는 전부 음수여야 한다.** 이번 주 월요일 이전이라야 어느 요일에 돌려도 미래가 되지 않는다 — 부호 하나로 "아직 등록되지 않은 소개팅"이 목록에 뜬다. 상대값이 되면서 새로 생긴 실수 경로라 `등록일은 언제 돌려도 과거다` 로 잠갔다.

⚠️ **등록일의 "신선도"는 이제 불연속이다** (PR #27 리뷰). 가장 최근 등록이 `월요일 -2일` 에 고정돼 있어, 보는 요일에 따라 실제로는 2일 전(월요일)부터 8일 전(일요일)까지 흔들리고 주가 넘어가는 순간 2일 전으로 튄다 — 진짜 `createdAt` 이라면 나올 수 없는 값이다. **지금은 무해하다**: `EventSummary.createdAt` 은 정렬 키로만 쓰이고 화면에 상대 시각으로 렌더되는 곳이 없다(상대 시각은 `Notification.createdAt` 의 몫이다). 하지만 `새로 등록` 배지에 `N일 전` 을 붙이는 순간 목이 거짓말을 시작한다 — 그때는 등록일을 `now` 기준으로 옮긴다.

⚠️ **날짜에서 파생된 표시 문자열은 같은 함수가 함께 만든다.** 처음에는 `date` 만 상대값으로 바꾸고 `dateLabel`(`"9/4(금)"`)·`timeLabel` 을 리터럴로 두었다 — **바꾼 그 주부터 이미 8건 전부 일주일씩 어긋나 있었다.** 카드가 `9/5(토)` 를 그리는 동안 `date` 는 9/12 였고, 브라우저로 확인하면서도 못 봤다. 월+4 가 언제나 금요일이라 **요일 글자만 우연히 맞았기** 때문이다. 지금은 `schedule(일수, 시각)` 이 셋을 한 순간에서 만든다 — 리터럴을 적을 자리가 없으면 어긋날 수도 없다 (PR #27 리뷰).

**여기에는 불변식 테스트를 두지 않는다.** 파생시킨 값을 같은 포매터로 다시 검사하면 아래 `timeSlot` 과 달리 **자기가 만든 값을 자기가 확인하는 순환**이다 — 같은 리뷰가 `when` 테스트에서 지적한 것과 같은 형태라, 리뷰의 제안(라벨 불변식 추가) 중 이 부분은 받지 않았다.

`timeSlot`·`scale` 은 반대로 **리터럴로 남기고 교차검증**한다. 갈리는 기준은 **저자 판단이 개입하는가**다 — 규모·시간대는 경계에 걸친 회차에서 저자가 의도를 골라 넣을 수 있어 계산값과 대조할 값이 있지만, `dateLabel` 은 `date` 를 기계적으로 포맷한 것뿐이라 고를 여지가 없다. 그런 값은 **직접 파생이 테스트보다 강한 보장**이다 — 어긋날 경로 자체가 없다.

**대신 포매터를 독립적으로 잠갔다** (`shared/lib/format.test.ts`, PR #27 2차 리뷰). 파생을 택한 순간 `dateLabel` 이 옳은지는 목 안에서 증명할 수 없고, 그때까지 `formatEventDate` 는 **어떤 테스트도 받지 않고 있었다** — 이번 판단의 진짜 빈틈은 거기였다. 목을 전혀 거치지 않는 고정 입출력으로 본다(`derive.test.ts` 가 `weekRangeKst` 에 쓴 것과 같은 전략).

**밟을 수 없는 방어 코드는 떼어내 직접 테스트한다** (PR #27 3차 리뷰). `formatEventTime` 의 `% 24` 는 `hour12: false` 에서 자정을 `"24"` 로 주는 `Intl` 구현을 막는데, 지금 Node 의 ICU 는 고쳐진 버전이라 **이 환경에서는 그 입력을 만들 수단이 없다.** 그렇다고 지울 수는 없다 — `shared/lib` 의 공유 유틸이라 화면에 붙으면 실행 환경이 사용자 브라우저의 `Intl` 이 되고, 구형 엔진에서는 실제로 밟힌다. `getKstParts` 안에 인라인으로 두면 영구히 미검증이므로 `normalizeHour24` 로 떼어 `("24") → 0` 을 직접 잠갔다. **이건 파생값이 아니라 방어 로직이라** 위 `dateLabel` 원칙과 부딪히지 않는다 — 독립적으로 옳고 그름을 말할 수 있다.

⚠️ **`timeSlot` 은 저장 필드지만 개최 시각과 어긋나면 안 된다.** 경계가 시작 시각 기준이라(6.2) 시각 계산이 틀어지면 카드에 `디너` 배지와 `10:30` 이 같이 뜬다. 날짜에 계산이 생긴 이상 이것도 불변식으로 잠갔다(`timeSlot 이 개최 시각과 어긋나지 않는다`) — 실제로 KST 오프셋을 빠뜨린 변이를 이 테스트가 잡았다.

**요일 자체는 계약이 아니다.** 전 날짜를 하루씩 민 변이는 테스트를 통과한다. 문서화된 규칙은 `이번 주/그 이후` 버킷과 시각뿐이고 요일에 기대는 규칙이 없어서다 — 잡히지 않는 것이 맞다. 다만 그 변이가 통과한 진짜 이유를 처음엔 잘못 짚었다: 라벨이 하드코딩이라 **요일 글자가 우연히 맞아** 안 걸린 것이기도 했다. 라벨을 파생시킨 지금은 요일이 정말로 계약 밖이다.

**`when` 테스트에서 순환 단언 하나를 지웠다** (PR #27 리뷰). `applyFilters` 의 `THIS_WEEK` 분기가 이미 `isThisWeek` 로 멤버십을 정하는데 그 결과에 같은 함수를 다시 걸고 있어, 필터가 무엇을 하든 항상 참이었다. 남긴 것은 **전건이 정확히 한쪽에만 속하는가**(합계·교집합)와 5:3 스냅샷이다. 경계 자체의 정확성은 `derive.test.ts` 가 고정 `now` + 절대 ISO 로 목을 거치지 않고 따로 본다 — **5:3 을 "필터가 옳다"의 근거로 인용하지 않는다.**

**전제를 사람이 지키지 않게 CI 가 본다.** `next build` 의 라우트 표(`○` 정적 / `ƒ` 동적)를 버리지 않고 `scripts/assert-dynamic-routes.mjs` 가 검사한다 — `eventApi` 를 import 하는 `page.tsx` 가 전부 `ƒ` 인지 본다. `/design-system` 이 프리렌더된 것을 그 표가 내내 말하고 있었는데 사람이 안 봐서 놓쳤으니, 눈으로 하던 확인을 그대로 자동화한 것이다. `force-dynamic` 을 떼고 빌드해 실제로 실패하는 것을 확인했다.

⚠️ **`shell: bash` 를 명시해야 한다.** GitHub Actions 기본 셸(`bash -e`)에는 `pipefail` 이 없어서, `npm run build | tee build.log` 로 쓰면 `tee` 의 종료 코드가 이겨 **빌드 실패가 통과로 보인다.**

**번복 조건**: 실 API 가 붙어 `MOCK_EVENTS` 가 개발 경로에서 빠지면 이 항목은 소멸한다.

> 그때 **함께 걷어낼 것 셋**을 여기 적어 둔다 — 흩어져 있어 체크리스트 없이는 놓친다.
> ① `/design-system` 의 `export const dynamic = "force-dynamic"` — 목 날짜 때문에 붙인 것이라 실 API 에서는 이유가 사라진다. Next 의 route segment config 는 **정적 리터럴이어야 해서**(`USE_MOCK ? … : …` 는 `can't recognize the exported dynamic field` 로 빌드가 깨진다 — 실제로 확인했다) 스위치에 매달 수 없고, 그래서 이 문장이 유일한 신호다.
> ② `scripts/assert-dynamic-routes.mjs` 와 CI 스텝 — 실 API 응답은 빌드 시점에 굳지 않으므로 검사할 이유가 없어진다.
> ③ `eventApi.mock.ts` 의 `detached` — HTTP 응답은 애초에 새 객체다. 그 전에 목이 **여러 주에 걸친 시나리오**(예: 지난 회차의 후기)를 표현해야 하면 앵커를 하나 더 두게 되는데, 그때도 절대 날짜로 되돌리지 않는다 — 되돌리는 순간 갱신 책임이 다시 사람에게 온다.

## 4.32 `/providers/[id]` 링크와 하단 고정 CTA 를 P1-7 에서 붙이지 않는다 (2026-09-08)

P1-7 은 이름이 `상세 + 하단 CTA` 인데 **상세만 붙였다.** 주최사 블록의 `소개 보기 >`·메타 줄의 주최사명 링크(7.1)와 하단 고정 CTA 3종(7.2)이 빠졌다.

**4.29 와 같은 기준이다** — `누르면 아무 일 없는 컨트롤은 만들지 않는다`. 목적지가 전부 다른 단계다.

| 컨트롤 | 목적지 | 그 단계 |
| --- | --- | --- |
| `소개 보기 >` · 메타 줄 주최사명 | `/providers/[id]` | P5-4 |
| 찜 | 낙관적 토글 | P2-7 |
| 비교 담기 | 비교함 + 플로팅 바 | P3-3 · P3-4 |
| 신청하기 | 외부 이동 확인 모달 (7.3) | **P1-8** |

⚠️ **`/providers/[id]` 는 자리표시자가 아니라 404 다.** 착수 전에는 "지금 누르면 자리표시자로 간다"고 알고 있었는데 `src/app` 을 훑어 보니 **`providers` 라우트가 아예 없다.** `?view=map`(4.29)은 홈 프로모 카드로 이미 도달 가능해서 자리표시자가 있었지만 이쪽은 진입점이 하나도 없어 페이지를 만든 적이 없다. 그래서 4.29 보다 판단이 더 쉽다 — 자리표시자 대 실화면이 아니라 **404 대 실화면**이다.

**한 자리가 아니라 두 자리다.** 7.1 은 `소개 보기 >` 를 "주최사 소개 페이지의 유일한 진입점"이라 쓰지만, 같은 표의 메타 행이 **주최사명도 그 링크**로 지정한다 — "유일한 진입점"은 *화면* 단위의 말이다. P5-4 는 둘 다 켠다.

**미루는 비용이 거의 0 이다** (4.29 의 실질 근거와 같다). 주최사 블록은 링크가 없어도 완성이다 — "누가 여는 소개팅이고 믿을 만한가"에 이름·한 줄 소개·평점이 답하고, 빠진 것은 이동 수단 하나뿐이라 P5-4 가 `<Link>` 두 개를 얹으면 된다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 링크를 붙이고 `/providers/[id]` 자리표시자를 만든다 | 4.29 가 이미 기각한 형태다. 게다가 그 라우트는 지금 아무도 안 만들어 놨는데 **링크를 붙이려고 새 라우트를 만드는 것**은 순서가 거꾸로다 |
| 하단 CTA 를 비활성으로 세운다 | 4.29 — `비활성 컨트롤은 "언제 켜지나"에 답하지 못한다`. 이 제품의 비활성 라벨 규칙(`필수 약관에 동의해주세요`)은 **사용자가 풀 수 있는 미충족 사유**를 말하는 장치라 "아직 안 만들었다"에는 쓸 수 없다 |
| `신청하기` 를 `externalApplyUrl` 로 직결한다 | **결제 비대행 고지(7.3)를 우회하는 경로**가 된다. `P1-8 은 타협 불가` 이고 모달을 우회하는 진입점을 만들지 않는다는 것이 그 항목의 첫 문장이다 |

**CTA 는 P1-8 이 모달과 함께 세운다.** 어느 쪽이든 바는 한 번만 만들어지므로 미루는 비용이 실제로 0 이고, 그렇게 하면 `신청하기` 가 **처음 그려지는 순간부터** 약속을 지킨다. 찜·비교 담기 자리는 P2-7·P3-4 가 각각 채운다. 그때까지 본문 하단 여백에 CTA 높이(`--height-fixed-cta`)를 비워두지 않는다 — 없는 바를 위해 84px 를 비우면 화면 아래가 이유 없이 빈다.

**이번 PR 이 값을 잃지 않는다.** `EventCard` 의 기본 `href` 가 `/events/{id}` 인데 그 라우트가 없어서 **홈·탐색·디자인 시스템의 모든 카드가 404 로 가고 있었다.** 상세만으로도 그게 닫힌다.

⚠️ **하단 여백은 P3-4 가 다시 연다** (PR #29 리뷰). `--height-fixed-cta`(84px)는 `globals.css` 에 이미 있고 아직 아무도 안 쓴다 — P1-8 이 바를 세우며 `EventDetailView` 의 `pb-10` 을 이 값으로 바꾸면 되는, **비어 있는 자리를 처음 채우는 일**이다. 다만 **P3-4 의 비교 플로팅 바가 CTA 위 82px 에 얹히고**(7.2) 담긴 것이 1건 이상일 때만 뜬다.

처음에는 이걸 "여백을 84 + 82 로 다시 계산해야 한다"고 적었는데 **여러 해법 중 하나를 유일한 것처럼 단정한 것이라 지웠다** — 두 바를 한 컨테이너에 넣고 실제 높이를 재 CSS 변수에 써넣으면 `pb-[var(--height-fixed-cta)]` 한 줄은 안 바뀐다. **진짜 미결은 합산이 아니라 두 바의 컨테이너·포털 구조다**: `fixed` 오버레이는 조상의 `transform`/`backdrop-filter` 에 갇히므로 `document.body` 로 포털해야 하는데(4.8), 둘이 같은 포털 타겟을 공유할지는 아직 아무 데도 정해져 있지 않다. **CTA 하나만 만드는 P1-8 이 미리 정할 수 없는 결정**이라 P3-4 의 몫으로 남긴다.

위 "미루는 비용 0"은 **P1-7 → P1-8 구간**의 이야기다 — P3-4 가 여는 재작업은 P1-7 이 무엇을 만들었든 똑같이 생긴다.

**아웃링크 하나는 이번에 나간다** — 참석자 리스트 원본(`attendeeListUrl`, 7.2). 신청·결제 행위가 아니라 단순 참조 링크라 확인 모달의 대상이 아니고(7.4 의 인스타 아웃링크와 같은 취급), `externalApplyUrl` 과는 다른 URL 이다. 위 표의 `신청하기` 금지와 부딪히지 않는다.

**번복 조건**: P1-8 이 붙는 순간 CTA 항목은 소멸하고, P5-4 가 붙는 순간 주최사 링크 항목이 소멸한다. 그 전에라도 `/providers/[id]` 가 **상세가 아닌 곳**에서 값을 갖게 되면(예: 검색 결과에 주최사 행) 다시 본다.

## 4.33 상세의 `참석자 정보` 는 집계값을 다시 쓰지 않고 원본 링크만 맡는다 (2026-09-08)

7.1 의 화면 구성표는 두 행을 따로 적는다.

| 행 | 내용 |
| --- | --- |
| 정보 카드 | 참가비 / **참가 연령(`N~N년생`)** / **모집 정원(`남 N · 여 N`)** / **참석자 직업군** |
| 참석자 정보 | 집계값만 표기 — **출생연도 범위 / 직업군 / 남·녀 정원** |

**같은 세 값이다.** 그대로 옮기면 430px 화면에 `남 7 · 여 7` 이 두 번, `90~96년생` 이 두 번 찍힌다. 두 번 보이는 값은 두 번째가 새 정보인 줄 알고 읽게 만든다.

**두 행이 다른 것을 말하려 한 것이라고 읽었다.** `참석자 정보` 행은 표시 항목의 목록이 아니라 **7.2 원칙의 요약**이다 — 개별 참석자 행 대신 집계값만 다룬다는 선언이고, 그 선언이 화면에서 실제로 하는 일은 정보 카드가 이미 하고 있다. 그래서 블록으로 남는 것은 **7.2 가 유일하게 더하는 것**, 동의한 주최사의 원본 리스트 아웃링크(`attendeeListUrl`)뿐이다.

- 동의가 없으면(`attendeeListUrl === null`) 블록이 **통째로 없다.** 목 8건 중 이 링크가 있는 것은 `evt-007` 하나다
- 집계값은 정보 카드 한 곳에만 있다. 값이 두 곳이면 언젠가 한쪽만 고쳐진다

⚠️ **참석자 리스트를 가져와 그리지 않는다** (7.2 원칙 표). 이미지 게재는 물론 **사실만 뽑아 개별 행으로 재구성하는 것도 금지**다 — 참석자는 그 주최사 계정에 공개 동의한 것이고, 날짜·장소·소규모 인원과 결합하면 식별 가능성이 생긴다. 이 블록이 하는 일은 보내는 것뿐이다.

**번복 조건**: 정보 카드에서 집계값을 빼는 개편이 오면(예: 가격만 남기고 나머지를 접기) 그때는 이 블록이 집계값을 되받는다.

## 4.34 `AppHeader` 에 타이틀이 없으면 그 화면이 `h1` 을 직접 갖는다 (2026-09-08)

`AppHeader` 는 `title` 이 있을 때만 `h1` 을 그리고, 없으면 같은 폭의 spacer 를 둔다 (P1-7).

**발단**: 상세(7.1)의 헤더 액션은 `공유` 뿐이고 **타이틀 행이 없다** — 소개팅명은 히어로가 갖는다. 그런데 `AppHeader` 가 `h1` 을 무조건 그리고 있어 ① 내용 없는 헤딩이 하나 생기고 ② 히어로의 `h1` 과 합쳐 문서에 `h1` 이 둘이 됐다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 헤더에 소개팅명을 넣는다 | 같은 제목이 화면에 둘이 되고, 스크린리더가 `h1`(잘린 제목) 직후 `h2`(같은 제목 전체)를 연달아 읽는다 |
| 히어로 제목을 `h2` 로 내린다 | 화면에서 가장 큰 글자가 `h2` 이고 진짜 `h1` 은 헤더에서 잘려 있다. 헤딩 구조가 시각 위계와 어긋난다 |
| 빈 `h1` 을 그대로 둔다 | 제목 없는 헤딩이 스크린리더의 헤딩 목록에 빈 항목으로 남는다 |

⚠️ **규칙의 나머지 절반은 화면 쪽에 있다.** `title` 없이 `AppHeader` 를 쓰는 화면은 **자기 `h1` 을 반드시 하나 가져야 한다.** 빠뜨리면 그 페이지의 `h1` 은 0 개가 되는데, 이건 빈 `h1` 보다 나쁘다 — 없는 것은 화면에도 콘솔에도 흔적이 없다.

**타입이 이 절반을 강제하지 못한다.** `title` 유무는 props 로 알 수 있지만 "화면이 `h1` 을 갖는가"는 컴포넌트 바깥의 일이고, jsdom 을 붙이지 않으므로(4.10) 렌더 테스트로도 못 잡는다. 지금 소비자는 둘이고 둘 다 지킨다 — `/design-system` 은 헤더가, `/events/[id]` 는 히어로가 `h1` 을 갖는다. **세 번째가 생길 때 이 항목을 본다**(`AppHeader` 주석이 여기를 가리킨다).

**번복 조건**: 타이틀 없는 스택 화면이 다수가 되면 `AppHeader` 가 `h1` 을 아예 그리지 않고 **화면이 항상 갖는 쪽**으로 뒤집는다 — 그러면 예외 없는 규칙 하나가 되어 위 위험이 사라진다.

## 4.35 서버 값을 화면에서 한 번 더 검사할지 정하는 사다리 (2026-09-08)

4.23 이 `openSectionsOnly` 로 처음 쓴 형태를 P1-7 의 `providerRatingDisplay` 가 두 번째로 썼다. 두 번 쓴 이상 **언제 쓰는가**를 정해 둔다.

| 자리 | 계약 | 한 번 더 보는 것 |
| --- | --- | --- |
| `api/eventApi.ts` 의 `openSectionsOnly` | 홈 세 섹션은 모집 중만 (`ports.ts`) | `isOpen` (4.23) |
| `model/labels.ts` 의 `providerRatingDisplay` | `rating` 은 표시 임계가 적용된 값 (12장) | `canShowRating(reviewCount)` (7.4) |

목 데이터는 생성 시점에 이미 거른다(`applyDisplayThreshold`·`isOpen`). **규칙이 두 벌인 것은 맞고**, 그래서 아무 값에나 두면 안 된다.

⚠️ **처음 적은 기준이 틀렸다.** "어긋났을 때 화면이 조용한가" 하나로 갈린다고 썼는데 **`dateLabel` 이 그 기준을 반증한다.** 4.31 이 기록한 대로 리터럴 `dateLabel` 은 8건 전부 일주일씩 어긋난 채였고 **브라우저로 보면서도 못 잡았다** — 조용했는데 방어선을 두지 않았다. 조용함은 조건 하나일 뿐이고, 갈림은 사다리다.

**위에서부터 걸리는 데서 멈춘다.**

| 단계 | 조건 | 답 | 사례 |
| --- | --- | --- | --- |
| 1 | 화면이 그 값을 **직접 파생시킬 수 있다** | 서버 값을 쓰지 말고 파생시킨다. **어긋날 경로 자체가 없어져 방어선보다 강하다** | `dateLabel` — `schedule()` 이 `date` 와 한 순간에서 만든다 (4.31) |
| 2 | 파생은 못 하지만 **재계산 근거**(판정 함수 + 원본 입력)가 응답 안에 있고, **사용자가 이 화면에서 그 축을 제어하지 않는다** | 방어선. 잘못 보여주는 것보다 덜 보여주는 쪽 | 홈의 `status`(홈에 상태 필터가 없다 — 4.23) · 상세의 `rating`(후기 건수가 같이 온다) |
| 3 | **사용자가 제어하는 축이다** | 두지 않는다. 클라이언트가 뒤집으면 화면이 **사용자 자신의 질의와 모순**된다 — `대규모` 로 거른 목록에 `표준` 배지가 붙는다 | 탐색의 `scale` |
| 4 | 재계산 근거가 없다 | 할 수 있는 게 없다 | `popularity` — 산식이 미확정이다 (16장) |

2단의 뒤쪽 조건이 4.23 과 7.4 를 함께 설명한다. 홈에는 상태 필터가 없고(5.4) 상세의 주최사 평점에는 사용자가 건드릴 컨트롤이 없다 — 둘 다 **틀린 값을 걷어낼 수단이 사용자에게 없는 자리**다. 탐색은 반대다.

⚠️ **`event.scale` 은 오늘 어느 화면에도 안 그려진다.** 그리는 것은 `SheetCard` 하나이고 그 화면(마커 시트 6.6)이 **P3-2** 다. `filterChips` 의 `scaleLabel(query.scale)` 은 **사용자가 고른 값을 되읽는 것**이라 이 판단 밖이다. 그래서 `scale` 은 3단으로 굳은 것이 아니라 **1단으로 갈 여지가 남아 있다** — `deriveScale` 과 그 입력(`maleCapacity`·`femaleCapacity`)이 `EventSummary` 에 다 있어서 시트가 서버 값을 안 쓰고 파생시킬 수 있다. **P3-2 가 그리기 시작할 때 1단과 3단 중에서 고른다.**

**번복 조건**: 실 API 가 붙어 계약 위반이 실제로 관측되면 2단을 로깅으로 바꾼다 — 조용히 덜 보여주는 것보다 서버를 고치는 편이 낫다. 지금은 백엔드가 없어 관측할 자리가 없다.

## 4.36 하단 CTA 는 `신청하기` 하나로 세우고 찜·비교 자리는 슬롯으로 비운다 (2026-09-08)

7.2 의 바는 찜(48px) / 비교 담기(flex 1) / 신청하기(flex 1.4) 3분할인데, 오늘 목적지가 있는 것은 **`신청하기` 하나**다 (찜 P2-7, 비교 담기 P3-4). `DetailCtaBar` 가 `like`·`compare` 를 **`ReactNode` 슬롯으로 받고, 안 넘어오면 아무것도 그리지 않는다.**

**4.16 이 같은 제약에서 쓴 해법이다** — 거기서도 찜·신청 버튼을 `action` prop 으로 비웠고, `entities` 가 `features` 를 import 할 수 없다는 제약이 여기서는 위젯과 feature 사이에 있다. 4.16 이 이미 `features/event-apply` 를 이름으로 지목해 뒀고 이번에 그 슬라이스가 생겼다.

**"검증된 형태"는 아니다.** 4.16 의 `action` 슬롯도 프로덕션에서 한 번도 채워진 적이 없다 — `EventSection`·`EventList` 둘 다 안 넘기고 `/design-system` 쇼케이스만 채운다. 죽은 코드는 아니다: `dev-plan.md` 가 P2-7·P3-4 로 채울 티켓을 잡아 뒀다.

⚠️ **두 슬롯의 이유가 다르다** (PR #31 리뷰). 한동안 "같은 제약"이라고 묶어 적었는데 틀렸다.

| | 왜 슬롯인가 | 성격 |
| --- | --- | --- |
| `EventCard` (4.16) | `entities` 는 `features` 를 **영원히** import 할 수 없다 (FSD) | **영구적 제약** — 대안이 없다 |
| `DetailCtaBar` (여기) | 위젯은 feature 를 부를 수 있다. 실제로 바로 옆에서 `ApplyButton` 을 그렇게 부른다 | **일시적 상황** — `features/event-like`·`event-compare` 가 아직 없을 뿐이다 |

그래서 이쪽 근거는 "레이어가 막아서"가 아니라 **"P2-7·P3-4 가 들어올 때 이 파일을 다시 안 열려고"** 다. 티켓이 다 붙으면 슬롯을 걷고 직접 import 로 바꿔도 레이어 규칙에 안 걸린다 — 아래 번복 조건이 이미 그것이다.

| 대안 | 왜 안 되나 |
| --- | --- |
| 세 자리를 미리 잡고 둘을 **비활성 버튼**으로 | 4.29·4.32 가 기각한 형태 그대로다. 상시 노출 크롬에 죽은 컨트롤이 둘 선다 |
| 세 자리를 잡되 빈 칸으로 | 눌리지는 않지만 **바에 이유 없는 여백이 둘** 생긴다. 사용자에게는 깨진 레이아웃으로 읽힌다 |

**슬롯은 자리표시자가 아니다.** 비어 있으면 DOM 에 아무것도 없다 — 그래서 `누르면 아무 일 없는 컨트롤은 만들지 않는다` 와 부딪히지 않는다. 이 구분이 이 항목의 전부다.

⚠️ **7.2 의 `flex 1.4` 는 셋이 다 설 때의 값이다.** 지금은 `신청하기` 가 `flex-1` 로 남는 폭을 다 쓴다 — 혼자 있는데 1.4 를 주면 오른쪽에 이유 없는 빈칸이 생긴다. **슬롯이 차는 순간 여기만 `flex-[1.4]` 로 바뀐다.**

**번복 조건**: P2-7·P3-4 가 둘 다 붙으면 슬롯을 유지할 이유가 약해진다 — 그때 세 버튼을 바가 직접 알아도 되는지 다시 본다. 다만 `entities`/`features` 경계가 그대로면 슬롯이 여전히 유일한 배치다.

## 4.37 마감 회차의 `신청하기` 는 막지 않고 모달이 알린다 (2026-09-08)

7.3 이 **TBD** 로 비워 둔 자리다(목업 미정의). 마감 회차(`status === '마감'`)에서도 버튼은 살아 있고, 외부 이동 모달이 고지를 **한 줄 더** 얹는다 — `이 소개팅은 마감으로 등록돼 있어요. 주최사 페이지에서 아직 신청을 받는지 먼저 확인해주세요.`

| 대안 | 왜 안 되나 |
| --- | --- |
| 비활성 버튼 + 라벨이 사유를 말한다 | 2.5 의 그 패턴은 **사용자가 풀 수 있는** 미충족 사유를 말하는 장치다(`필수 약관에 동의해주세요`·`후기를 10자 이상 작성해주세요`). 마감은 사용자가 풀 수 없고 **영원히 안 켜진다** — 4.29 가 비활성 컨트롤을 기각한 것과 같은 문제다 |
| 마감이면 바를 안 그린다 | 상세까지 온 사용자에게 다음 행동이 하나도 없어진다. 게다가 찜(P2-7)·비교 담기(P3-4)는 **마감 회차에도 유효하다** — 찜 목록은 마감 건을 지우지 않는다(4.23 ⚠️) |

**근거 셋.**

1. **`마감` 은 태생적으로 늦는 값이다.** 주최사는 신청 마감일을 두지 않고 지원자를 심사하다 **임의 시점에 마감을 선언한다**(7.3). MeetMap 의 값은 운영자가 인스타를 보고 옮겨 적은 시점의 스냅샷이라, 틀렸을 때 손해가 사용자에게 간다.
2. **7.3 자체가 막지 않고 경고하는 설계다.** 하단 경고(`조건에 맞지 않는 신청은 주최사에 의해 취소될 수 있습니다`)는 **자격 미달자를 통과시키고 결과를 알린다.** 판정 주체가 주최사라는 뜻이다 — 마감만 프론트가 하드 블록할 이유가 없다.
3. **막으면 유입이 끊긴다.** 성장 단계 ①에서 주최사가 MeetMap 에 등록할 이유는 유입 하나다.

**기존 결정에 대입해 봤다** (규칙을 쓰기 전에).

| 항목 | 부딪히나 |
| --- | --- |
| 4.23 홈은 마감을 아예 거른다 | 아니다. 4.23 의 근거는 `걷어낼 수단이 없는 자리에 걷어내야 할 것을 놓지 않는다` 인데, 홈은 사용자가 고르지 않은 큐레이션이고 **상세는 그 회차를 지목해 연 화면**이다 |
| 4.30 게스트의 가격 정렬은 파싱이 막는다 | 아니다. 거기서 막는 이유는 정책이 아니라 **축이 성립하지 않아서**다(성별을 모른다). 마감은 축이 성립한다 |
| 4.12 `proxy.ts` 는 UX 가드이지 보안 경계가 아니다 | 같은 결이다. 프론트는 강제하지 않고 안내한다 |

**번복 조건**: 주최사 셀프서비스(성장 단계 ②)가 붙어 마감 상태를 주최사가 직접 갱신하면 `마감` 이 신뢰할 수 있는 값이 된다. 그때는 막는 쪽을 다시 본다 — 이 항목의 근거 1이 통째로 사라지기 때문이다.

## 4.38 7.3 우회 경로를 문서가 아니라 린트가 막는다 (2026-09-09)

4.32·4.37 이 "이 모달을 우회하는 진입 경로를 만들지 않는다"를 여러 번 적었지만, **그걸 강제하는 것은 아무것도 없었다** (PR #30 리뷰). 경로가 둘이다.

| 우회 | 왜 뚫렸나 |
| --- | --- |
| `@/features/event-apply/ui/ApplyOutboundModal` 처럼 **깊은 경로로 import** | 배럴 강제 규칙이 `src/app/**` 에만 걸려 있었고, 패턴도 `@/entities/*` `@/shared/*` 뿐이라 `@/features/*/ui/*` 가 아예 없었다 |
| `<a href={event.externalApplyUrl}>` 를 **새로 쓴다** | 더 근본적이다. `externalApplyUrl` 은 `EventDetail` 의 평범한 `string` 필드라 **슬라이스를 import 조차 하지 않는다.** 배럴을 아무리 좁혀도 안 막힌다 |

**둘 다 린트로 막았다.** 배럴 패턴을 `widgets`·`features`·`entities` 까지 넓히고, `no-restricted-syntax` 로 **`externalApplyUrl` 필드 접근 자체**를 `features/event-apply` 밖에서 금지했다.

**이 규칙은 세 번 뚫렸고 매번 같은 이유였다** (PR #30·#31 리뷰) — 방어선을 만든 뒤 *떠오른 형태만* 확인했다. 점 표기만 보고 구조분해를 놓쳤고, 구조분해를 막고 나서 템플릿 리터럴·문자열 키·계산 키를 놓쳤다. 지금은 5분기다.

**그래서 우회 목록을 코드로 고정했다** — `model/outboundGuard.test.ts` 가 `externalApplyUrl` 이라는 **글자가 소스에 나타나는 모든 형태**에 대해 린트를 실제로 돌린다(ESLint Node API). 새 형태가 생각나면 문서가 아니라 그 표에 줄을 더한다. 분기를 하나씩 지워 각각이 실제로 일하는 것도 확인했다.

`ObjectPattern >` 으로 한정하는 것이 요점이다 — 목 데이터의 `externalApplyUrl: "…"` 도 같은 `Property` 노드라, 한정 없이 잡으면 목 8건이 전부 에러가 된다.

⚠️ **이 규칙의 등급은 "실수 방지"다 — 범위를 두 번 고쳤다.** 처음엔 "코드에 그 글자가 없는 것만 못 잡는다"고 적었는데 **틀렸다**(PR #32 리뷰): `Reflect.get(e, "externalApplyUrl")` 은 글자가 소스에 그대로 있고 grep 으로도 잡히는데 `CallExpression` 의 인자라 다섯 분기를 비켜 간다. 정확히는 **`MemberExpression` 과 `ObjectPattern > Property` 두 형태만 잡는다.**

**여기서 선택자를 더 늘리지 않는다.** `Reflect.get`·`getOwnPropertyDescriptor`·제네릭 접근자·lodash `get` … 리플렉션 API 목록은 끝이 없고, **그걸 쫓는 것이 이 규칙이 세 라운드 연속 뚫린 방식이다.** 못 잡는 형태는 테스트에 `caught: false` 로 적어 둔다 — 포기가 아니라 **등급 선언**이고, 누가 규칙을 넓혀 잡히게 되면 테스트가 실패해 이 문장을 함께 고치게 한다.

⚠️ **`no-restricted-imports` 를 별도 블록으로 추가하면 안 된다.** flat config 는 같은 규칙 이름을 **뒤 블록이 통째로 덮어쓴다.** `src/widgets/**` 에 배럴 블록을 따로 두면 그 파일들의 **레이어 경계 규칙이 조용히 사라진다** — 린트는 계속 통과하므로 아무도 못 알아챈다. 그래서 패턴을 합쳐 한 규칙으로 넘기고, `features → widgets` 위반이 여전히 잡히는지 확인했다. 지금 배럴 블록이 `src/app/**` 에만 남아 있는 것은 `app` 이 레이어 규칙 대상이 아니어서다(`LAYERS.filter`).

**타입으로는 못 조인다.** `externalApplyUrl` 을 브랜드 타입으로 감싸도 언랩 함수를 다른 레이어가 깊은 경로로 부르면 구멍이 한 단계 이동할 뿐이다 — 그 이동을 막는 것도 결국 같은 린트다. 그래서 타입을 건드리지 않았다.

**대신 모달이 받는 타입을 좁혔다.** `ApplyOutboundModal`·`ApplyButton` 은 `EventDetail` 전체가 아니라 `ApplyOutboundEvent`(조건 5행 + `id` + `externalApplyUrl`)만 받는다. 우회를 막는 장치는 아니고 — 테스트가 목 8건을 끌어오지 않고 9개 필드짜리 픽스처로 끝나게 하는 것이 실익이다. ⚠️ 새 필드가 필요할 때 `Pick` 을 넓히는 것을 **잊는** 경로는 타입이 막지만(선언된 타입 기준으로 검사된다), `as EventDetail` 캐스팅으로 넓히기를 건너뛰면 지금은 호출부가 실제로 전체를 넘겨서 통과해 버린다. 더 좁은 객체를 넘기는 호출부가 생기는 순간 터진다 — **넓혀야지 캐스팅하지 않는다** (PR #32 리뷰).

**번복 조건**: 실 API 가 붙어 `externalApplyUrl` 의 성격이 바뀌면(예: 서버가 이동 토큰을 내려준다) 이 규칙의 대상 이름부터 바뀐다. 그때 `outboundGuard.test.ts` 의 표를 새 이름으로 옮긴다.

## 4.39 법적 고지가 **그려지는지**는 jsdom 없이도 잠글 수 있다 (2026-09-09)

> 4.38 과 짝이다 — 저쪽은 **접근을 막고**(정적), 여기는 **그려지는 것을 보장한다**(렌더). 합치자는 제안이 있었지만(PR #32 리뷰) 합치면 47줄·⚠️ 5개가 되어 4.31 이 세운 압축 신호에 다시 걸린다. **한 항목이 둘을 다뤄서 커진 것이 지난 라운드의 문제였다** — 번호를 나누고 이 줄로 잇는다.



`copy.test.ts` 는 문자열 상수만 잠근다. 상수를 그대로 두고 JSX 에서 `{false && …}` 로 감싸 **조용히 감추는 변경**을 못 잡는다 — 리뷰가 정확히 짚은 구멍이고, 실제로 그 변이를 넣으면 상수 테스트는 15건 전부 통과한다.

**jsdom 을 붙이지 않고 메웠다** (4.10 유지). 모달 본문을 `OutboundNoticeBody` 로 떼어 `react-dom/server` 의 `renderToStaticMarkup` 으로 렌더한다 — 이미 있는 의존성이고 `environment: node` 그대로다. `Modal` 자체는 `document.body` 로 포털하고 `useIsClient` 로 서버 렌더를 건너뛰어 빈 문자열을 주므로, **본문을 순수 컴포넌트로 떼는 것이 이 방법의 전제**다.

| 무엇을 잠그나 | 어디서 |
| --- | --- |
| 문구가 무뎌지는 것 (`결제를 대행하지 않습니다` 삭제·축약) | `model/copy.test.ts` — `REQUIRED_PHRASES` |
| **문구가 그려지지 않는 것** (본문을 조건부로 감추기) | `ui/ApplyOutboundModal.test.tsx` — `renderToStaticMarkup` |
| **모달이 본문을 안 품는 것** (`<OutboundNoticeBody />` 삭제) | 같은 파일 — 아래 |

⚠️ **본문만 렌더하면 그 본문이 모달에 붙어 있는지는 아무도 안 본다** (PR #31 리뷰). 처음에는 `OutboundNoticeBody` 를 단독으로만 렌더해서, `ApplyOutboundModal` 에서 `<OutboundNoticeBody />` 한 줄을 지워도 스위트가 전부 통과했다 — **고지가 실제 모달에 있는지를 보장하는 테스트가 하나도 없는 상태**였다.

리뷰는 여기서 jsdom + RTL 이 유일한 길이라고 봤지만 아니다. **`ApplyOutboundModal` 에는 훅이 없어 평범한 함수로 부를 수 있다** — 돌려받은 엘리먼트에서 `Modal` 의 `children` 만 떼어 렌더하면 포털·`useIsClient` 를 거치지 않는다. 이걸로 4.10 을 그대로 두고 연결까지 잠갔다. 이 방법이 성립하는 전제는 **`ApplyOutboundModal` 이 훅 없는 순수 함수라는 것**이다. 전제가 깨져도 **조용히 무너지지 않는다** — 훅을 하나 넣고 돌려 보니 그 줄에서 `TypeError: Cannot read properties of null (reading 'useState')` 로 즉시 실패한다(렌더 컨텍스트 밖이라 디스패처가 `null` 이다). 그래서 훅 금지 린트를 따로 붙이지 않았다.

⚠️ **`Modal` 자체의 회귀는 못 잡는다.** 이 테스트는 `Modal` 을 한 번도 호출하지 않고 **호출부가 무엇을 넘겼는지**만 본다. `ApplyOutboundModal` 에서 본문을 빼면 잡히지만, `shared/ui/Modal` 이 `children` 을 그리기를 그만두면 여기도 `copy.test.ts` 도 통과한 채 화면에서만 고지가 사라진다 — **`Modal` 을 건드리는 작업은 이 사각지대를 알고 가야 한다.** 거기까지 덮으려면 4.10 대로 jsdom + RTL 이 필요하다.

**번복 조건**: 컴포넌트 상호작용까지 테스트해야 하면(예: P2-7 찜 낙관적 업데이트) 4.10 대로 jsdom + RTL 을 붙인다. 그때 이 렌더 테스트는 RTL 로 옮겨도 되고 그대로 둬도 된다 — 서버 렌더만 보는 쪽이 더 빠르다.

## 4.40 11.2 의 에러 카드는 `error.tsx` 가 아니라 **페이지**가 그린다 (2026-09-09)

11.2 는 에러 카드에 **오류 코드와 발생 시각**을 요구한다 — CS 문의 식별자라 타협 대상이 아니다. `dev-plan` P1-9 는 그 카드를 `error.tsx` 에 두라고 적었고 P1-7 도 "나머지(네트워크·5xx)는 올려 `error.tsx` 가 받는다"고 예고했다. **둘 다 성립하지 않는다.**

`error.tsx` 는 클라이언트 컴포넌트여야 하고, 서버 컴포넌트가 던진 에러는 **프로덕션에서 `message` 가 일반 문구로 치환된다**(Next 공식 문서 `error.js` — 민감 정보 유출 방지). 넘어오는 것은 `digest` 하나뿐이라 `ApiError` 의 `code`·`occurredAt`·`retryable` **셋 다 경계를 못 넘는다.** 재시도 버튼을 보일지조차 그 안에서는 판정할 수 없다.

**그래서 실패 표면을 셋으로 나눈다.** 처음에는 둘로 적었는데 **틀렸다** — 리뷰가 세 번째를 찾았다(PR #33).

| | 무엇이 오나 | 어디가 그리나 | 식별자 |
| --- | --- | --- | --- |
| **11.2 에러 카드** | 화면 진입의 조회가 `ApiError` 로 실패 | 페이지가 잡아서 서버에서 그린다 (`shared/ui/ApiErrorScreen`) | `code` + `occurredAt` |
| **증분 로딩 실패** | 목록의 `더 보기` 가 실패 | `explore-board` 의 `LoadMoreError` — **목록 아래에** 그린다 | `code` + `occurredAt` |
| **최후 방어선** | 그 밖의 예외 — 렌더 중 버그 | `error.tsx` | `digest` 뿐 (서버 로그와 맞춘다) |

잡는 방법은 `shared/api/loadOrError` 한 형태로 굳혔다 — 페이지마다 `try/catch` 를 쓰게 두면 `catch {}` 로 삼키는 변형이 언젠가 섞인다.

**증분 로딩이 `ApiErrorScreen` 을 못 쓰는 이유는 화면을 갈아끼우기 때문이다.** 실패한 것은 **다음 장**뿐인데 이미 읽던 목록을 에러 카드로 덮으면 사용자가 방금 본 것이 사라진다. 그래서 자리만 다르고 **규칙은 같다** — 코드·발생 시각을 노출하고 재시도는 `ApiError.retryable` 이 정한다. ⚠️ 재시도 불가 실패에서는 `더 보기` 도 함께 사라진다. 다음 장을 받을 방법이 실제로 없어서, 버튼을 남기면 눌러도 같은 실패가 반복된다.

⚠️ **이 자리는 리뷰 전까지 `catch { setState("failed") }` 로 `ApiError` 를 통째로 버리고 있었다.** 버튼 라벨만 `다시 시도` 로 바뀌고 코드도 시각도 안 나왔다 — 8종 표는 화면 진입만 잠그므로 **그 보호망 밖이었다.** 클라이언트에서 조회를 부르는 자리를 다시 훑어보니 이 하나뿐이다(`logOutboundClick` 은 의도적으로 삼키고 근거가 `eventApi.ts` 에 있다). `EventList.test.tsx` 가 코드·시각·`retryable` 셋을 렌더로 잠근다.

**`ApiErrorKind` 8종과 화면은 1:1 이 아니다.** `shared/api/errorScreen.ts` 가 표를 들고 `errorScreen.test.ts` 가 8종 × 2형태 = 16칸을 `Record<ApiErrorKind, …>` 로 적어 잠근다 — 종류가 늘면 **컴파일 에러**로 새 줄을 요구한다.

- **없는 페이지로 가는 칸은 하나다** — `NOT_FOUND` × **자원 하나를 여는 조회**(`getDetail`). 목록 조회의 404 는 "결과 0건"이 아니라 **엔드포인트가 깨진 것**이라 에러 카드다. 판정에 필요한 것은 에러가 아니라 *무엇을 열려던 것인가*라서 `resource: "single" | "collection"` 을 받는다
- 나머지 15칸은 전부 에러 카드이고, 그 안에서 갈리는 축은 `ApiError.retryable`(NETWORK·TIMEOUT·SERVER) 하나뿐이다. 여기서 다시 정하지 않는다
- 문구는 세 갈래다. 11.2 는 네트워크 오류 한 줄만 정의했는데 그 문구를 8종에 다 쓰면 403 을 받은 사용자가 **자기 와이파이를 확인한다**

⚠️ **401·403 을 로그인·권한 화면으로 보내지 않는다.** 보낼 곳이 자리표시자다(P2-1). 누르면 🚧 로 가는 버튼을 만들지 않는다는 규칙(5.4)이 여기에도 걸린다 — 같은 이유로 11.2 가 요구하는 **`고객센터 문의` 버튼도 그리지 않는다**(문의 목적지가 없다. `ErrorState` 의 `onContactSupport` 를 비워 둔다). 둘 다 P2-1·P4-1 이 목적지를 만들 때 켠다.

**`ErrorState` 에 제어형 `retrying` 을 뒀다.** 11.2 의 `다시 시도하는 중...` 라벨은 재시도가 끝날 때까지 유지돼야 하는데, `router.refresh()` 와 `error.tsx` 의 `retry()` 는 **동기 함수라 완료를 알려주지 않는다.** 처음에는 `ref` + 의존성 없는 `useEffect` + 프로미스로 그 시점을 흉내냈는데, 리뷰가 짚은 대로(PR #33) ① 언마운트 시 프로미스가 매달리고 ② 그 장치가 지키려는 전제(트랜지션이 동기 완료되면 `pending` 이 한 번도 안 켜진다)를 **jsdom 없이는 테스트로 잠글 수 없었다**. 가정을 검증하는 대신 **가정을 없앴다** — `useTransition` 의 `pending` 을 prop 으로 그대로 넘기면 장치 셋이 사라지고 라벨 전환은 정적 렌더로 잠긴다. 4.10(jsdom 미도입)도 그대로 간다.

**번복 조건**: Next 가 서버 에러의 식별자를 `digest` 말고 구조화된 형태로 넘겨주게 되면 이 분리가 필요 없어진다. 그때 `loadOrError` 를 걷어내고 `error.tsx` 한 곳으로 모은다.

## 4.41 에러는 **셸마다**, 로딩·없는 페이지는 **화면마다** (2026-09-09)

`dev-plan` P1-9 는 "라우트 그룹별 배치"라고만 적었다. 셋의 성격이 달라 한 축으로 두지 않는다.

- **`error.tsx` 는 화면에 대해 아무것도 모른다** — 무엇이 실패했는지조차 못 본다(4.40). 화면마다 둬도 내용이 같아진다. **다른 것은 셸뿐**이라 셸 단위로 둔다
- **`loading.tsx`·`not-found.tsx` 는 그 화면의 내용**이다 — 홈 스켈레톤과 탐색 스켈레톤은 모양이 다르고, "그 소개팅이 없다"와 "그런 주소가 없다"는 다음 행동이 다르다

| 파일 | 자리 | 이유 |
| --- | --- | --- |
| `(main)/error.tsx` | 그룹 | 레이아웃 안에서 렌더되어 **하단 탭이 남는다**. 실패한 것은 이 화면의 조회 하나이고 다른 세 탭은 멀쩡하다 |
| `(stack)/error.tsx` | 그룹 | ⚠️ **`AppHeader` 를 직접 그린다.** `(stack)/layout.tsx` 는 폭·배경만 맡고 헤더는 각 페이지가 그리기로 되어 있어, 안 그리면 **나갈 수단이 하나도 없는 화면**이 된다 |
| `app/error.tsx` | 루트 | 그룹 `error.tsx` 가 못 잡는 둘 — **레이아웃 자체**가 던진 예외(같은 세그먼트의 layout 은 경계 밖이다)와 `(onboarding)`(자리표시자 한 장이라 자기 경계를 두지 않았다) |
| `app/not-found.tsx` | 루트 | 매칭 안 되는 주소 전체. `/compare`·`/search`·`/providers/[id]` 가 지금 여기로 온다 |
| `events/[eventId]/not-found.tsx` | 라우트 | 문구가 "그 소개팅이 없다"로 구체적이라 다른 스택 화면이 같이 못 쓴다 |
| `(home)/loading.tsx` · `explore/loading.tsx` · `events/[eventId]/loading.tsx` | 라우트 | 셋의 모양이 전부 다르다 |

`global-error.tsx` 는 만들지 않았다 — 루트 레이아웃이 조회 없이 프로바이더만 얹는다. `<html>`·전역 스타일을 다시 들여야 해 성격도 다르다.

⚠️ **`(home)` 라우트 그룹은 `loading.tsx` 때문에 생겼다.** 홈은 `(main)` 세그먼트의 페이지라 그 자리에 두면 Suspense 경계가 `/likes`·`/my` 까지 덮어 **그 화면들이 홈 스켈레톤을 폴백으로 상속**한다. 그룹 하나로 경계를 홈에 맞췄고 URL 은 그대로 `/` 다.

**탐색의 전환 표시 셋(4.24 계열)과 겹치지 않는다 — 확인했다.** 시간대 칩을 눌러 보니 `loading.tsx` 폴백은 **뜨지 않고**(`startTransition` 안의 이동이라 이미 마운트된 경계가 유지된다) 누른 칩만 흐려졌다. 폴백이 뜨는 자리는 최초 진입·새로고침·탭 이동뿐이다.

⚠️ **그래서 `progress.md` 5장이 P1-9 에 넘긴 "결과 수·리스트까지 덮는 폴백"은 이 방법으로 닫히지 않는다.** 조건을 바꾸는 동안 `총 N개 소개팅` 은 여전히 이전 값으로 서 있다. 닫으려면 그 숫자에 표시를 붙이거나(`useLinkStatus` 계열) 이동을 트랜지션 밖으로 빼야 하는데, 후자는 조작하는 자리 셋의 표시를 전부 잃는다. **지금은 열어 둔다.**

⚠️ **`loading.tsx` 를 붙인 라우트의 404 는 HTTP 200 으로 나간다.** 스트리밍이 시작된 뒤에는 상태 코드를 못 바꾼다(Next 공식 문서 `loading.js` — Status Codes). 확인해 보니 `/events/{없는id}` 는 `200` + `<meta name="robots" content="noindex">` 이고 루트 `not-found` 는 `404` 다. Next 가 문서화한 동작이고 색인은 메타가 막는다 — 진짜 404 상태 코드가 필요해지면 `proxy` 에서 존재 여부를 먼저 확인해야 한다.

## 4.42 0건 빈 상태의 액션은 상수가 아니다 (2026-09-09)

11.2 는 필터 결과 없음의 액션을 `필터 초기화` / `조건 넓혀 보기` 로 적었다. 그대로 박으면 **눌러도 아무것도 안 바뀌는 링크**가 생긴다.

`필터 초기화`(= 칩 줄의 `clearAppliedFilters`)가 푸는 것은 **적용 필터 칩 줄에 뜬 축뿐**이다. 그런데 0건을 만드는 축은 그것 말고도 있다.

| 축 | 화면의 컨트롤 | 0건일 때 |
| --- | --- | --- |
| `area` | **없다** — URL 로만 들어온다 | 여기서 안 풀면 **풀 방법이 없다** → 1순위 |
| 칩 줄 6축 (`when`·`scale`·`maxPrice`·`mood`·`status`·`eligibleOnly`) | 칩 줄 | `필터 초기화` (11.2) |
| `district` | 지역 버튼 | `서울 전지역 보기` |
| `slot` | 시간대 칩 | `시간대 전체 보기` |
| 아무것도 없음 | — | 풀 것이 없다. **문구를 바꾼다** (`아직 등록된 소개팅이 없어요`) |

`emptyRelaxation` 이 이 순서로 훑어 **실제로 조건을 바꾸는 것 하나**를 돌려준다. 여러 개를 늘어놓으면 그중 안 넓히는 버튼이 섞인다 — 하나씩 주면 매 단계가 참이고, 눌러 나가면 조건이 없는 상태에 도달한다(테스트가 그 왕복을 돈다).

`emptyRelaxation.test.ts` 는 `Record<keyof EventListQuery, …>` 로 **조회 축 14개를 전부 적는다** — 축이 늘면 컴파일 에러로 판정을 요구한다. 4.38 이 세 라운드를 쓴 이유가 "떠올린 경우만 확인한 것"이라, 이번에는 열거를 먼저 코드로 고정했다. 핵심 단언은 라벨이 아니라 **목적지가 현재 주소와 다른가**다.

⚠️ **`초기화` 가 셋이 됐다** (4.26 의 둘에 하나 더). 대상이 전부 다르다 — 칩 줄 쪽은 칩만, 시트 쪽은 2·3층만, 이쪽은 **0건을 만든 축 하나**. 화면에서 겹치지 않는 것이 근거다: 앞의 둘은 결과가 있을 때도 떠 있고 이것은 0건일 때만 뜬다.

`조건 넓혀 보기` 는 **만들지 않았다.** 완화 규칙이 11.2 에서 TBD 이고, 임의로 정하면 되돌릴 때 화면·URL·건수 규칙이 함께 흔들린다.

**자리표시자는 `/onboarding` 하나만 손댔다.** `EmptyState.action` 이 선택 슬롯이라 `PhasePlaceholder` 전부가 11.2 를 어기는 것처럼 보이지만, 규칙은 "**화면에** 다음 행동으로 가는 길이 있는가"다 — `/likes`·`/my` 는 `(main)` 이라 하단 탭이 출구다. `(onboarding)` 만 탭도 헤더도 없어 갇히고, **게스트가 `찜`·`마이` 탭을 누르면 실제로 거기로 간다**(`checkAccess` 가 보낸다). 거기에만 `홈으로 가기` 를 붙였다.

## 4.43 로그인 버튼은 `accountApi` 포트를 세운다 — 목 역할 쿠키에 묶지 않는다 (2026-09-10)

백엔드에 OAuth 가 없다. 그런데 `누르면 아무 일 없는 컨트롤은 만들지 않는다`(5.4) 때문에 P1-6 은 뷰 토글을, P1-7 은 CTA 를 미뤘다. **여기서 미루면 퍼널 전체(P2-2~P2-5)가 막힌다** — 로그인 버튼이 목적지를 못 가지면 그 뒤 네 화면에 도달할 방법이 없다.

**받지 않은 안: `meetmap_mock_role` 쿠키에 묶기.** 이미 있는 개발용 역할 스위치라 코드가 가장 적다. 두 가지 이유로 안 된다.

1. **`readMockSession` 은 `isNewUser` 를 항상 `false` 로 만든다.** 로그인 버튼을 거기 묶으면 3.1 의 `신규는 약관으로` 분기가 **영원히 안 돈다.** 만들자마자 죽은 코드가 되는 분기를, 그 분기를 검증하려고 만든 화면 다섯 장이 떠받치는 모양이 된다.
2. **그건 화면이 아니다.** 스위치의 값은 `USER`·`PROVIDER:PENDING`·`ADMIN` 이고, 로그인 버튼에 묶으면 "어느 역할로 로그인할래요"를 사용자에게 묻게 된다 — 역할은 **진입점이 정한다**는 dev-plan 3.3 과 정면으로 어긋난다. `/onboarding` 은 USER 전용 진입점이다.

**정한 것: `eventApi`(4.3)와 같은 형태의 포트.** 계약은 `entities/account/model/ports.ts`, 구현은 `api/` 에 mock·http 둘, 분기는 `api/accountApi.ts` 마지막 한 줄.

⚠️ **`eventApi` 와 한 군데가 다르다 — 돌려주는 값이 유니온이다.** 조회는 두 모드가 같은 모양(값을 돌려준다)이지만 **소셜 로그인은 두 세계가 정말 다르다**: 실 모드는 브라우저를 소셜 인증으로 넘기고 세션은 콜백에서 서버가 심는다. 목 모드에는 넘길 곳이 없어 그 자리에서 세션이 생긴다. 그 차이를 `{ kind: "REDIRECT" } | { kind: "SESSION" }` 으로 이름 붙였다 — 감추려고 `Promise<Session>` 한 모양으로 눌렀다면 실 구현이 거짓말을 하게 된다.

**목 세션은 쿠키 `meetmap_mock_session` 한 장이다**(`Session` 을 JSON 으로). 서명이 없는 것은 실 모드와 다르지 않다 — 프론트는 어차피 서명을 검증하지 않는다(4.12). 역할 스위치 쿠키는 **로그인 세션을 이긴다**: 스위치는 로그인이 만들 수 없는 역할을 강제하려고 있는 것이라 지면 존재 이유가 없다. 대신 스위치가 남아 있으면 퍼널을 눌러볼 수 없으므로 지우고 봐야 한다(`phase2-notes.md`).

**`isNewUser` 는 약관 제출에서 내려간다** (`accountApi.finishSignUp`). 프로필까지 기다리지 않는 이유는 프로필이 선택이기 때문이다 — `나중에 할래요`(3.3)·`건너뛰기`(3.4)로 넘어간 사용자가 로그인할 때마다 퍼널로 되돌아온다. `finishSignUp` 의 http 구현은 **의도적으로 비어 있다**: 실 모드에서는 서버가 약관 POST 를 받으며 새 토큰을 `Set-Cookie` 로 심으므로 프론트가 할 일이 없다.

**번복 조건**: 백엔드 OAuth 가 뜨면 `NEXT_PUBLIC_USE_MOCK=false` 한 줄이다. `meetmap_mock_session`·`meetmap_mock_user` 두 쿠키와 목 구현 두 파일이 그때 죽는다.

## 4.44 `viewer` 주입을 P2-4 와 같은 판에 넣는다 — 게이트는 세션이 아니라 프로필이다 (2026-09-10)

`progress.md` 5장이 "둘 자리는 정해졌다"고 적어 둔 그대로 홈·탐색의 `viewer={null}` 을 풀었다. 다음 판으로 뗄 수도 있었다 — 카드 5종·가격 표기·자격 배지·정렬 옵션이 한꺼번에 바뀌므로 리뷰 표면이 넓다. 그럼에도 이번 판에 넣은 이유는 **미루는 쪽이 결함을 남기기 때문**이다.

**P2-1 이 만든 결함**: `parseExploreParams(raw, { isGuest: session === null })` 는 로그인이 불가능한 동안에는 맞는 판정이었다. 로그인이 실제로 되는 순간 **프로필을 건너뛴 로그인 사용자**가 생기고, 그 사람에게 가격 정렬(성별 기준값)과 자격 필터(출생연도 기준)가 열린다 — 판정 근거가 없는데. 목에서는 `MOCK_VIEWER`(1996·F)가 대신 판정하므로 **사용자가 입력한 적 없는 조건이 조용히 걸린다.**

그 결함을 닫으려면 두 화면이 어차피 프로필을 읽어야 한다. 읽고 나면 `viewer` 로 넘기지 않을 이유가 없다 — 넘기지 않으면 프로필을 방금 저장한 사용자가 **저장되지 않은 것처럼 보이는 화면**을 본다.

| 바뀐 것 | 전 | 후 |
| --- | --- | --- |
| 인증 축 게이트 | `isGuest: session === null` | `hasViewer: viewer !== null` (**이름도 바꿨다**) |
| 홈 섹션 B 노출 | `showMyAgeGroup={session !== null}` | `showMyAgeGroup={viewer !== null}` |
| 홈·탐색 카드 | `viewer={null}` | `viewer={프로필}` |

`isGuest` → `hasViewer` 로 **이름을 바꾼 것이 요점**이다. 값만 갈아끼우면 다음 사람이 다시 `session === null` 을 넣는다. 게이트가 파싱 한 곳이라는 4.27 은 그대로다 — 판정의 **입력**이 세션에서 프로필로 바뀐 것뿐이다.

**타입을 새로 만들지 않았다.** `UserProfile` 이 `EventCardViewer`(`gender`·`birthYear`)를 구조적으로 만족한다 — `EventCardViewer` 가 "필요한 두 값만" 받도록 설계된 이유가 이것이다.

**상세(7.1)는 여전히 대기열 밖이다.** 참가비 남·여 병기는 게스트라서가 아니라 그 자리의 규칙이다 (4.32).

⚠️ **프로필 조회 실패는 화면을 죽이지 않는다.** `loadViewerContext` 가 삼키고 `viewer=null` 로 떨어뜨린다(+`console.warn`) — 덜 개인화됐을 뿐 화면으로 성립하는 반면, 에러 카드로 바꾸면 피드가 멀쩡한데 홈이 통째로 죽는다. 부분 성공을 안 그리기로 한 탐색의 목록+패싯(4.40)과 **판단이 갈리는 지점**은 "한쪽만 와도 화면이 성립하는가"다.

**한 가지는 열어 둔다**: 세션은 살아 있는데 프로필 조회가 401 로 죽으면 헤더는 로그인 상태인데 가격은 게스트 기준이 된다. 목에서는 재현 경로가 없어 지금 닫지 않는다.

## 4.45 온보딩의 진입 경로를 표로 세고, `?redirect=` 는 소비 시점 한 곳에서 검증한다 (2026-09-10)

온보딩은 **진입 경로가 여럿**이라 "화면 다섯 개"로 세면 빠진다. 먼저 표로 세고 시작했다.

| 진입 경로 | 떨어지는 곳 | 판정하는 곳 |
| --- | --- | --- |
| 신규 가입 (`isNewUser=true`) | `/onboarding/terms` | `signInLanding` (로그인 액션) |
| 기존 로그인 (`isNewUser=false`) | `safeRedirect(redirect)` ?? `/` | 같은 함수 |
| `checkAccess` 리다이렉트 (게스트의 `/likes`·`/my`·`/compare`·`/reviews/write`) | `/onboarding?redirect=…` → 위 두 줄 | `proxy.ts` → 로그인 액션 |
| 손으로 친 `/onboarding` (누구든) | 로그인 화면 그대로 | — (**리다이렉트하지 않는다**) |
| 손으로 친 퍼널 4단계 (게스트) | `/onboarding` | `(funnel)/layout.tsx` |
| 손으로 친 퍼널 4단계 (세션 있음) | 그 화면 그대로 | 같은 레이아웃 |
| 중간 단계 새로고침 | 그 화면 그대로. **서버에 저장된 것만 남는다** (약관 ✅ 프로필 ✅ 작성 중 폼 ❌) | — |
| `/onboarding/{없는 경로}` | 루트 `not-found` | Next |
| `?redirect=https://evil.com` 등 | `/` | `safeRedirect` |

**`/onboarding` 이 세션을 보고 튕겨내지 않는 것**이 이 표의 요점이다. 완료한 사용자를 홈으로 보내는 편이 자연스러워 보이지만 둘을 잃는다. ① 퍼널 중간에 뒤로가기로 돌아온 사용자가 리다이렉트에 갇힌다(뒤로가기가 안 먹는 화면이 된다) ② 이미 가입한 브라우저에서는 `기존 회원은 홈으로` 분기를 **누를 방법이 없어져** 4.43 이 피하려던 죽은 분기가 다시 생긴다. 그래서 **`isNewUser` 를 판정하는 자리는 로그인 액션 하나뿐**이다.

**퍼널 가드는 화면 넷에 각각 적지 않고 `(funnel)` 라우트 그룹 레이아웃에 뒀다.** `PUBLIC_PREFIXES` 가 `/onboarding` 전체를 열어 두므로(로그인 화면이 그 안에 있으니 그래야 한다) `checkAccess` 는 `/onboarding/profile` 도 통과시킨다 — 세션 없이 프로필 폼에 도달하는 구멍이었다. URL 은 그대로다.

⚠️ **처음에 여기 `P2-6 을 폴더에 넣기만 해도 같은 규칙이 걸린다` 고 적었는데 절반만 맞다.** 레이아웃은 모든 이동에서 다시 돌지 않는다 → 4.49.

### `?redirect=` — 오픈 리다이렉트

`proxy.ts` 는 P0-7 부터 `?redirect=` 를 붙여 보냈고 **아무도 읽지 않았다.** 읽는 순간 `redirect=https://evil.com` 이 통한다.

**막는 자리는 생산 시점이 아니라 소비 시점**이다. `proxy.ts` 가 만드는 값만 믿으면 안 된다 — 주소창에 직접 칠 수 있다. `safeRedirect` 하나가 로그인 액션에서 값을 소비하기 직전에 판정한다.

**막을 것을 열거하지 않고 허용 조건을 좁게 적는다** — "첫 글자가 `/` 이고 둘째 글자가 `/`·`\` 가 아니며, 파싱 후 오리진이 그대로인가". `https://evil.com`·`//evil.com`·`/\evil.com`·`javascript:`·`data:`·상대 경로가 전부 여기 걸린다. 제어문자·512자 초과는 파싱 전에 버린다. 테스트가 적대적 입력 10종을 잠근다.

**온보딩 경로를 제외하는 것은 보안이 아니라 루프 방지**다. 게스트가 `/onboarding/profile` 을 치면 가드가 `?redirect=/onboarding/profile` 을 달아 로그인으로 보내는데, 그대로 돌려주면 같은 자리로 되돌아온다.

⚠️ **신규 가입자에게는 `redirect` 를 적용하지 않는다.** 3.5 가 퍼널의 끝(홈)을 못 박아 두었고, 값을 다섯 화면 너머로 나르려면 단계마다 URL 에 상태가 붙어 새로고침·뒤로가기마다 유실 검사가 생긴다. 잃는 것은 "찜 탭을 눌러 가입한 사람이 찜 목록으로 돌아가는 것"인데 신규 가입자의 찜 목록은 비어 있다.

### 각 화면의 나갈 길 (4.42 를 다섯 자리에 적용)

`(onboarding)` 은 **하단 탭도 헤더도 없는 유일한 셸**이라 화면마다 확인해야 한다.

| 화면 | 출구 |
| --- | --- |
| `/onboarding` | **`로그인 없이 둘러보기`** — 자리표시자에 있던 `홈으로 가기` 가 사라지는 자리다. 게스트가 탭에서 튕겨 오는 실제 경로가 있다 |
| `/onboarding/terms` | ← 뒤로가기 → 로그인 (3.2). `backHref` 로 목적지를 못 박는다 |
| `/onboarding/intro` | `나중에 할래요` → 완료 → 홈 |

## 4.46 네 번째 실패 표면 — 제출 실패는 폼 안에서 알린다 (2026-09-10)

4.40 이 센 실패 표면 셋(화면 진입의 조회 · 목록의 `더 보기` · 렌더 중 예외)은 **전부 읽기**다. 온보딩이 **쓰기**를 처음 들여온다.

기존 셋 중 어느 것도 맞지 않는다. 조회 실패용 `ApiErrorScreen` 은 화면을 갈아끼우므로 **사용자가 방금 채운 폼이 사라진다.** `error.tsx` 는 Server Action 의 실패를 받지도 않는다. 2.5 의 토스트는 1.8초 뒤 사라져 CS 문의용 오류 코드를 실을 수 없고, 비활성 라벨은 **사용자가 풀 수 있는 사유**의 자리다 — 서버가 죽은 것은 사용자가 못 푼다.

**정한 것**: `shared/ui/FormErrorNotice` — 폼 안, 제출 버튼 바로 위에 코드·발생 시각과 함께 한 줄. 폼은 그대로 남고 **제출 버튼 자체가 재시도**라 재시도 버튼을 따로 두지 않는다. 값은 `toActionFailure` 가 만드는 평범한 객체다(`ApiError` 인스턴스는 RSC 경계를 못 넘고, `occurredAt` 은 **실패한 시각**이라 클라이언트에서 다시 만들면 안 된다).

**이 규칙이 적용될 자리를 먼저 다 셌다** — 지난 판(#24)에서 표면을 둘로 세고 셋이었던 실수를 반복하지 않으려는 것이다.

⚠️ **3.1 의 `인증 실패 시 에러 토스트` 는 이번에 만들지 않았다.** 실 모드에서 인증 실패가 드러나는 자리는 **소셜 인증 콜백**이고 그건 백엔드가 만든다. 목 모드에는 실패 경로가 아예 없어 지금 만들면 **한 번도 눌러볼 수 없는 코드**가 된다. 백엔드 OAuth 가 붙을 때 `/onboarding?error=…` 를 읽어 토스트를 띄우는 것이 그 자리다.

## 4.47 `(onboarding)` 그룹 경계는 화면 수가 아니라 **출구** 때문에 붙인다 (2026-09-10)

4.41 이 "자리표시자 한 장뿐이라 자기 경계를 두지 않았다 — P2-1 이 실제 화면을 만들 때 붙인다"고 예약해 둔 자리다. 붙였다. 다만 **근거는 화면이 다섯이 된 것이 아니다** — 4.41 의 기준은 "셸이 다른가"이고, 온보딩 셸의 폭·배경은 루트 `error.tsx` 가 이미 그리는 것과 같다.

붙이는 진짜 이유는 **출구**다. `(main)` 은 하단 탭이, `(stack)` 은 헤더가 출구라 각자 자기 `error.tsx` 에 그것을 그린다. **온보딩은 그릴 크롬이 없는 유일한 셸**이다 — 퍼널이라 일부러 없앴다. 그래서 에러 카드가 출구를 직접 준다(`홈으로 가기`). 루트 `error.tsx` 는 이제 **레이아웃이 던진 예외** 한 줄만 받는 자리로 좁아졌다 — 4.41 의 표에서 두 줄이던 것이 한 줄이 된다.

| 파일 | 만들었나 | 근거 |
| --- | --- | --- |
| `(onboarding)/error.tsx` | ✅ | 위 |
| `(funnel)/loading.tsx` | ✅ **하나만** | 4.41 은 로딩을 화면마다 두라고 했고 근거는 "모양이 다르다"였다. **퍼널 넷은 그 근거가 성립하지 않는다** — 넷 다 제목 + 입력 블록 + 하단 버튼이고 흉내낼 콘텐츠 모양이 없다. 넷으로 복사하면 같은 파일이 넷이 된다. 실제로 폴백이 뜨는 자리는 조회가 있는 `/onboarding/done` 하나다 |
| `(onboarding)/not-found.tsx` | ❌ | 그룹 안에 동적 세그먼트가 없어 `/onboarding/{오타}` 는 **어떤 라우트에도 안 걸리고** 루트 `not-found` 로 간다 — 그게 맞는 문구다("그런 주소가 없다"). 그룹 경계는 `notFound()` 를 부르는 코드가 생길 때 의미가 생기는데 퍼널에는 없다 |

## 4.48 온보딩 입력값은 단계마다 제출한다 — 2.4 의 `일괄 제출` 에서 벗어난다 (2026-09-10)

2.4 는 `온보딩 입력값 | 단계 간 클라이언트 상태(Context) | 마지막 단계에서 일괄 제출` 이라고 적었다. 퍼널을 실제로 그려 보니 셋이 어긋난다.

1. **마지막 단계에 제출 버튼이 없다.** 3.5 의 완료 화면에는 `홈으로 이동` 하나뿐이다. 거기서 제출하면 사용자가 화면을 닫는 순간 **약관에 동의한 적 없는 계정**이 남는다.
2. **`나중에 할래요`(3.3)가 프로필을 건너뛰고 완료로 직행한다.** 일괄 제출이라면 그 경로에서 "약관만 든 일괄"과 "약관+프로필 일괄" 두 모양을 만들어야 한다.
3. **3.5 의 동적 문구가 새로고침을 못 견딘다.** Context 는 새로고침에 사라지므로 방금 프로필을 채운 사용자가 `언제든 마이페이지에서 관심사를 추가할 수 있어요`(= 아무것도 안 골랐다는 문구)를 보게 된다 — **틀린 말**이다.

**정한 것**: 약관은 약관 화면이, 프로필은 프로필 화면이 제출한다. 완료 화면은 **서버에서 프로필을 다시 읽어** 문구를 만든다. 그래서 새로고침해도 같은 문구가 나오고, `건너뛴 사용자 = 프로필 없음`이 **한 값**으로 표현된다 — "건너뛰었다"는 상태를 따로 저장하지 않는다. 값을 둘로 두면 어긋난다.

⚠️ **완료 화면의 조회 실패를 미선택 문구로 덮지 않는다.** `프로필 없음`(정상 경로)과 `조회 실패`는 다른 상태다. 실패하면 11.2 의 에러 카드를 그리되 **`홈으로 이동` 은 남긴다** — 실패한 것은 요약 문구 하나이고 가입은 이미 끝났다.

**남은 어긋남**: 2.4 의 표는 아직 옛 문장이다. 기능정의서를 고치는 것은 사양 변경이라 여기 근거만 적어 두고, 실제 수정은 사양 갱신 때 함께 한다.

## 4.49 `(funnel)` 레이아웃 가드는 **모든 이동에서 다시 돌지 않는다** — 찍어서 확인했다 (2026-09-10)

4.45 에 "그룹 레이아웃에 두면 P2-6 을 폴더에 넣기만 해도 같은 규칙이 걸린다"고 적었다. **절반만 맞다.** PR #35 리뷰가 "레이아웃은 소프트 내비게이션에서 재실행이 보장되지 않는다"고 짚었고, 주장을 좁히기 전에 **측정했다** — 레이아웃에 로그를 심고 개발 서버 stdout 을 읽었다.

| 전환 | 레이아웃 재실행 |
| --- | --- |
| 하드 로드 · 새로고침 · 손으로 친 URL | ✅ 항상 |
| Server Action 의 `redirect()` (약관→인트로, 프로필→완료) | ✅ 항상 |
| **`<Link>` 소프트 내비게이션** (인트로→프로필, 인트로/건너뛰기→완료) | ⚠️ **보장 없음** |

⚠️ **마지막 줄은 두 번 측정해 답이 달랐다.** 한 번은 클릭에 로그가 아예 안 찍혔고, 한 번은 (프리페치로 보이는) 호출이 있었다. 처음에는 `안 돈다` 로 적었는데 그것도 과장이다 — 정확한 문장은 **`보장되지 않는다`** 이고, 결론은 오히려 더 분명해진다. **타이밍에 기대는 가드는 가드가 아니다.**

이게 4.45 의 표에 없던 여덟 번째 경로다 — **퍼널 안에서 세션이 죽는 경우.** 진입할 때는 세션이 있었으니 표의 어느 줄에도 안 걸린다. 표를 먼저 세는 것으로 화면은 다 셌지만 **시간축을 안 셌다.**

**고친 것**: 판정을 `(funnel)/_guard.ts` 의 `requireFunnelSession` 하나로 떼고, **세션에 딸린 일을 하는 단계가 스스로 한 번 더 부른다.**

⚠️ **처음에는 "쓰기를 하는 자리" 로 적어 셋만 셌고, 2차 리뷰가 `done` 을 찾았다** — 폼이 아니라 조회라서 안 걸렸다. 기준은 쓰기냐 읽기냐가 아니라 **세션에 딸린 일을 하는가**다. 넷을 다 적는다.

| 단계 | 세션에 딸린 일 | 스스로 부르는 자리 |
| --- | --- | --- |
| `terms` (3.2) | 약관 **저장** | `_actions.ts` |
| `intro` (3.3) | **없다** — 정적 안내 | 없음 (레이아웃만) |
| `profile` (3.4) | 프로필 **저장** (폼 자체는 빈 폼이다) | `_actions.ts` |
| `done` (3.5) | 프로필 **조회** | `page.tsx` |

Server Action 과 페이지 렌더는 매번 서버에서 도므로 소프트 내비게이션과 무관하다.

**받지 않은 안 둘.**

- **화면 넷에 각각 가드를 적기** — 4.45 가 피하려던 것으로 되돌아간다. 단계가 늘 때마다 사람이 세야 한다.
- **`checkAccess`/`proxy.ts` 로 올리기** — 엣지는 RSC 요청에도 돌아서 구멍이 완전히 닫힌다. 그런데 `PUBLIC_PREFIXES` 가 `/onboarding` **전체**를 열어 두고 있고(로그인 화면이 그 안에 있어야 한다) 프리픽스 규칙으로는 "`/onboarding` 아래는 막되 `/onboarding` 자신은 열어라"를 한 줄로 못 쓴다. 네 줄로 쓰면 그게 곧 "화면마다 적기"다.

**남는 것을 정확히 적는다.** **세션에 딸린 일이 없는 화면(`intro`)은 세션이 죽어도 그려진다.** 데이터가 없으니 새는 것도 없고 다음 걸음에서 걸린다. 빈 프로필 폼도 마찬가지로 뜰 수 있지만 저장은 액션이 막는다. 렌더까지 전부 막으려면 위의 두 안 중 하나를 지불해야 하는데, 발생 조건(퍼널을 지나는 동안 세션 만료)에 비해 비싸다.

**번복 조건**: Next 가 소프트 내비게이션에서 상위 레이아웃을 다시 돌리게 되면 액션 쪽 호출이 중복이 된다 — 지워도 되지만, 지우기 전에 **다시 찍어서 확인한다.** 이번에 찍지 않았으면 틀린 문장을 그대로 뒀다.

## 4.50 서버 액션의 `Set-Cookie` 는 브라우저까지 못 간다 — 계약을 지켜도 연결될 자리가 없었다 (2026-09-10)

4.43 이 `finishSignUp` 의 http 구현을 비워 두면서 "서버가 약관 POST 에서 새 토큰을 `Set-Cookie` 로 심으니 프론트가 할 일이 없다"고 적었다. 2차 리뷰(PR #35)가 그 전제를 코드로 따라가 **틀렸다는 것**을 찾았다.

`agreeTermsAction` → `userApi.saveTerms` → `fetchClient(ENDPOINTS.user.terms)` 는 **Server Action 안에서 나가는 서버→서버 fetch** 다. `fetchClient` 는 요청 헤더만 만들고 **`response.headers` 를 어디서도 읽지 않는다** — 확인했다. 그래서 백엔드가 계약을 완벽히 지켜 `Set-Cookie` 를 내려도 그 헤더는 **Next 서버에서 끝나고** 브라우저의 `meetmap_at` 은 그대로다.

**"프론트가 위반을 감지 못 한다"가 아니라 "계약을 지켜도 작동하지 않는다"** 라 등급이 다르다. 앞의 것은 신뢰의 문제지만 뒤의 것은 구현 누락이다.

**OAuth 콜백은 왜 멀쩡한가** — 브라우저가 직접 백엔드 리다이렉트를 타므로 백엔드가 **브라우저 응답**에 `Set-Cookie` 를 얹는다. 서버→서버 중계가 없다. 이 리포에서 그 차이가 나는 자리는 **약관 POST 하나뿐**이다.

**지금 구현하지 않는다.** 실 백엔드가 없어 눌러볼 수 없고(3.1 인증 실패 토스트를 안 만든 기준과 같다 → 4.46), 무엇보다 **어느 모양으로 받을지가 백엔드 응답에 달렸다.**

| 선택지 | 필요한 것 |
| --- | --- |
| ① 응답 `Set-Cookie` 릴레이 | `fetchClient` 가 헤더를 돌려주는 옵션 + 액션이 `cookies().set()` |
| ② 갱신 토큰을 **응답 본문**으로 | 백엔드 응답 스키마 변경. **서버 액션 구조에는 이쪽이 단순하다** |

**계약과 함께 적었다** — `ENDPOINTS.user.terms` 에 요구사항·왜 지금 안 되는지·두 선택지가 다 있다. 그 파일이 프론트-백 계약서 역할을 하기로 되어 있는 자리다.

**리뷰가 제안한 "제출 후 세션 재조회로 확인"은 순서가 있다.** 릴레이가 없는 지금 붙이면 **항상 갱신 전 세션**을 보므로 감지가 아니라 오탐이다. 릴레이를 만든 **뒤에** `agreeTermsAction` 이 `saveTerms` 직후 `getServerSession()` 으로 `isNewUser` 가 실제로 꺼졌는지 보고 안 꺼졌으면 `ApiError` 를 던져 `FormErrorNotice` 로 드러내는 것이 값싸다. 둘을 묶어서 한다.

## 4.51 세 번 연속으로 같은 실수를 했다 — 규칙을 만들고 적용될 자리를 안 셌다 (2026-09-10)

번호를 붙여 두는 이유는, 이게 우연이 아니라 **반복되는 형태**이기 때문이다.

| 판 | 만든 규칙 | 셌다고 생각한 것 | 실제 | 찾은 사람 |
| --- | --- | --- | --- | --- |
| #24 | 실패는 코드·시각을 노출한다 (4.40) | 표면 **2** | **3** (`더 보기` 누락) | 리뷰 |
| #25 | 온보딩 단계는 세션이 있어야 한다 (4.45) | 진입 경로 **7** | **8** (퍼널 안에서 세션이 죽는 경우 — 시간축) | 리뷰 |
| #25 리뷰 반영 | 위 규칙을 자기가 부르는 자리 (4.49) | 호출 **3** (쓰기만) | **4** (`done` 의 조회 누락) | 리뷰 |

셋 다 **"세는 축을 하나 빠뜨린 것"** 이지 "잊어버린 것"이 아니다. #24 는 화면만 세고 컨트롤을 안 셌고, #25 는 화면을 세고 시간을 안 셌고, 이번에는 **쓰기를 세고 읽기를 안 셌다.**

**그래서 표를 적을 때 축을 먼저 적는다.** 4.49 의 표는 이제 단계 넷을 전부 적고 각 단계가 "세션에 딸린 일"을 하는지로 판정한다 — 쓰기/읽기/없음 셋으로 나뉘고 `intro` 가 "없음"으로 표에 남아 있다. **빠진 칸이 아니라 비어 있는 칸으로 보이는 것**이 핵심이다. `emptyRelaxation.test.ts` 가 `Record<keyof EventListQuery, …>` 로 축 14개를 강제한 것(4.42)과 같은 발상이고, 타입으로 강제할 수 없는 자리에서는 표가 그 일을 한다.
