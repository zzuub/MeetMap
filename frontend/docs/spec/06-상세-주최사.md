> ### ⚠️ 참석자 리스트 취급 원칙
>
> 다수 주최사가 인스타그램 게시물로 **참석자 리스트(출생연도·직업·키 등)** 를 공개한다. 공개돼 있다고 해서 가져다 쓸 수 있는 것이 아니다.
>
> | 행위 | 가부 | 근거 |
> | --- | --- | --- |
> | 리스트 이미지를 그대로 게재 | ❌ | 주최사가 제작한 저작물 — 복제권 침해 |
> | 사실만 추출해 개별 행으로 재구성 | ❌ | 참석자는 **그 주최사 계정에** 공개 동의한 것이지 MeetMap에 동의한 바 없다. 날짜·장소·소규모 인원과 결합하면 식별 가능성이 생긴다. 매주 갱신되는 리스트의 상당 부분 복제는 데이터베이스제작자의 권리도 건드린다 |
> | **집계값만 표기** (연령 범위 / 직업군 / 남·녀 정원) | ✅ | 식별성이 사라진다. 비교 플랫폼에는 오히려 이쪽이 유용하다 |
> | 원본 리스트로 아웃링크 | ✅ | 주최사에게도 유입이 된다 |
>
> **MVP1은 집계값만 저장·표시한다.** 등록 동의를 받을 때 `참석자 리스트 표시 동의` 항목을 함께 받고, 동의한 주최사에 한해 `참석자 리스트 공개` 배지 + 원본 링크(`attendeeListUrl`)를 노출한다.

### 7.3 외부 신청 이동 모달 ⚠️ 핵심 정책 화면

MeetMap은 **결제를 대행하지 않는 중개 플랫폼**이다. 신청·결제는 주최사 외부 페이지에서 이뤄진다.

| 요소 | 내용 | 필수 |
| --- | --- | --- |
| 타이틀 | `"외부 신청 페이지로 이동합니다"` | 필수 |
| 고지 | `"신청과 결제는 주최사 페이지에서 진행됩니다. MeetMap은 결제를 대행하지 않습니다."` | **법적 고지 — 필수** |
| 조건 확인 블록 | 참가 연령(`N~N년생`) / 모집 정원(`남 N · 여 N`) / 참가비(남·여 양쪽) | 필수 |
| 하단 경고 | `"조건에 맞지 않는 신청은 주최사에 의해 취소될 수 있습니다."` | 필수 |
| 취소 | 모달 닫기 | |
| 확인하고 이동 | 외부 URL을 **새 탭**(`target="_blank" rel="noopener noreferrer"`)으로 열고 아웃링크 클릭 이벤트 로깅 | |

- 딤 클릭 시 닫힘.
- 마감된 소개팅(`status === '마감'`)의 `신청하기` — **막지 않는다.** 버튼은 그대로 열리고 모달이 고지를 한 줄 더 얹는다: `"이 소개팅은 마감으로 등록돼 있어요. 주최사 페이지에서 아직 신청을 받는지 먼저 확인해주세요."` 주최사가 임의 시점에 마감을 선언하므로 MeetMap 의 `status` 는 태생적으로 늦고, 위 하단 경고가 이미 **막지 않고 알리는** 설계다 (2026-09-08 확정 → `decisions.md` 4.37)
- `신청 마감` 항목은 삭제했다. **주최사가 별도의 신청 마감일을 두지 않는다** — 지원자를 받아 심사하다가 임의 시점에 마감을 선언하는 방식이다(12장 `applyDeadline` 삭제).

### 7.4 주최사 소개 페이지 — `/providers/[providerId]` 🆕 2026-09-02

> **목업**: [`docs/mockups/Main.dc.html`](../mockups/Main.dc.html) (2026-09-10 신설). 이 문서를 보고 그렸으므로 어긋나면 이 문서가 원본이다.

#### 왜 만드나 — 평점의 귀속 단위가 회차가 아니라 주최사다

배달 앱의 **가게 리뷰**와 같은 구조다.

| 배민 | MeetMap |
| --- | --- |
| 가게 = 반복 주체 | **주최사** = 반복 주체 |
| 주문 = 1회성 | **소개팅 회차** = 1회성 |
| 리뷰는 주문에 대해 쓰지만 **가게에 쌓인다** | 후기는 회차에 대해 쓰지만 **주최사에 쌓인다** |

**회차 평점은 성립하지 않는 값이었다.** 두 가지 이유다.

1. **소비 시점에 값이 없다.** 사용자가 평점을 보는 시점은 그 회차가 **열리기 전**이다. 회차는 1회성이므로 신규 회차는 예외 없이 후기 0건이다. 즉 `EventSummary.rating`은 정의상 항상 0이거나, 0이 아니라면 그 데이터가 잘못된 것이다.
2. **표본이 없다.** 정원 7:7 = 14명이고 참여 인증까지 거쳐야 후기를 쓸 수 있어 회차당 2~4건이 현실이다. 3명이 쓴 4.0은 정렬 축으로도 비교 축으로도 못 쓴다.

주최사로 모으면 회차가 쌓일수록 표본이 는다. 그리고 처음 신청하는 사람의 실제 질문은 *"이 회차가 좋은가"*가 아니라 **"이 주최사 믿을 만한가"** 다. 흩어진 것을 모아 비교하게 해주는 제품에서 비교 축이 주최사로 올라가는 것이 자연스럽다.

**부수 효과 — 등록 동의의 협상 카드가 된다.** 현재 성장 단계는 ①운영자가 주최사에 컨택해 대신 등록하는 단계이고, 지금 주최사가 MeetMap에 등록할 이유는 유입 하나뿐이다. "당신 소개 페이지를 만들어 드립니다, 후기가 거기 쌓입니다"가 컨택에서 내밀 수 있는 카드가 된다.

| 블록 | 요소 | 비고 |
| --- | --- | --- |
| 헤더 | `AppHeader` 뒤로가기 + 주최사명 | `(stack)` 그룹 |

| 평점 요약 | 평균 평점(세리프) + 별 + `후기 N건`. **후기 5건 미만이면 평점을 숨기고 `후기 N건`만** | 아래 임계 규칙 |
| 진행 중인 소개팅 | `status === '신청 가능'`인 회차를 **개최일 가까운 순**으로. `list` 카드(6.5) | `eventApi.getList({ providerId, status: 'OPEN' })`. 마감 회차는 노출하지 않는다 |
| 후기 목록 | 최근 3건 + `후기 전체보기 >` → `/providers/[id]/reviews` | 카드 형식은 10.4와 동일 |

- **인스타그램 아웃링크는 새 탭**(`target="_blank" rel="noopener noreferrer"`)이다. 외부 신청 이동(7.3)과 달리 **확인 모달을 거치지 않는다** — 신청·결제 행위가 아니라 단순 참조 링크이므로 결제 비대행 고지의 대상이 아니다.
- 진행 중인 소개팅이 0건이면 `"지금 모집 중인 소개팅이 없어요"` 빈 상태(11.2). 주최사 페이지 자체는 계속 유효하다.
- **주최사 페이지에 신청 버튼을 두지 않는다.** 신청은 항상 회차 단위이며 상세(7.2)를 거쳐 외부 이동 모달(7.3)로만 간다.

#### 평점 표시 임계 — 5건

**후기 5건 미만이면 평점 숫자를 표시하지 않고 `후기 N건`만 쓴다.**

| 후기 수 | 한 명이 5점 → 1점으로 바뀔 때 평점 변화 | 표준오차(σ≈1.0) |
| --- | --- | --- |
| 3건 | −1.33 | ±0.58 |
| **5건** | **−0.80** | ±0.45 |
| 10건 | −0.40 | ±0.32 |
| 20건 | −0.20 | ±0.22 |

5건에서도 한 사람이 평점을 0.8 흔든다(4.6 → 3.8). 그럼에도 5건을 임계로 잡는 것은 **회차당 후기가 2~4건**이기 때문이다. 10건을 요구하면 주최사 대부분이 3~4회차를 치를 때까지 평점이 뜨지 않아 기능이 사실상 죽는다.

대신 두 가지를 강제한다.

- **평점과 후기 건수를 항상 같이 쓴다** — `4.6` 이 아니라 `4.6 (23)`. 건수 없는 평점은 5건짜리와 500건짜리가 같아 보인다
- **정렬에는 이 임계를 쓰지 않는다.** 하드 컷은 절벽을 만든다 → 6.2 `평점 높은순 정렬`의 베이지안 보정

#### 후기는 회차에 쓰고 주최사에 쌓인다

- **후기 작성 대상은 여전히 회차다** (10.5, `/reviews/write/[eventId]`). 참여 인증이 회차 단위이기 때문이다
- **집계·표시 단위만 주최사다.** `Review`는 `eventId`와 `providerId`를 함께 갖는다 (12장)
- 후기 카드에 `날짜 · 소개팅명`이 이미 있어(10.4) 주최사 페이지에서도 **어느 회차의 후기인지** 드러난다. 회차마다 장소·진행이 다르므로 이 정보가 필요하다
